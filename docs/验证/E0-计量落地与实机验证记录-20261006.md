## 2. 落点细节

**llm_usage 事件**（NumenLlmClient，挂在既有 `llm_response`/`llm_failure` 之后，同一 observation sink）：
- 成功与失败各发一条；字段：`status`(ok/failed)、`durationMs`、`attempts`（新增 AtomicInteger，onAttempt 里取 max）、`provider`、四元 `input/output/cacheRead/cacheWrite` + 派生 `promptTokens/totalTokens/freshTokens`，成功加 `finish`/`toolCalls`，失败加 `errorType`。
- **usage 缺失时不写 0**：`acc.usage` 为空（`LlmProvider.usage(null)` 会给全 0 假值）→ 只报 `usageState:"UNKNOWN"`。
- 发送位置即现有三条监控通道：numen 执行/判断/压缩/重试 → `context.jsonl`；规划 → `rdd.jsonl`；学习 → `learner.jsonl`。

**本地工具结果事件**（ToolDispatcher + LocalToolCallLog）：
- 原状：本地工具只有 `tool_call` 没有 `tool_result`（LocalToolCallLog 注释里说结果由另一侧发，实际全仓无人发）。实测 find_tools 552 次调用 0 结果。
- 现在：dispatch 时记 `startedAtMillis`，`complete()` 发 `tool_result`（字段 `companion_id/tool_call_id/tool/duration_ms/success/journaled_by=client-local`）；`success` 读 resultJson 顶层 `success` 字段，读不到写 `"UNKNOWN"`（不猜）。
- `runsLocally()` 守卫照旧：服务端工具不重复记（服务端已有自己的 tool_result 对）。

**学习侧观测**：LearnerReviewer 原先 `chatStreaming(..., null)` 不带 observation → 现在 `new LlmObservation("learner", companionId, "review", LearnerMonitor::publish)`，与执行侧同一套 llm_usage 逻辑。

**E0.3 中文短状态（同日第二批，api:neoforge）**：
- `EntityAgentLoop.statusHint()` = 短中文状态的**唯一出口**：身体不在/外脑驾驶/整理记忆中/正在&lt;工具译名或服务端任务描述&gt;/重试中/等模型回复（较慢）/模型端点有问题：xxx/已暂停（主人叫停·上轮失败·端点被拒）。只读已有状态，不另造计时器；「等熔炼/生长」由服务端 `currentTask` 描述带入。
- `currentActivity()` 的工具名过 `ToolLabels`（新类，`numen.tool.*` 约定，与聊天栏 chip 同一套；无译文回落原名）；`ChatView.toolLabel` 同步收敛到它。
- 气泡 `SpeechBubbles.View` 改为 `(text, activity, status, pulsing)`；渲染器状态行画「✦ 状态文本」+ 在飞等待的脉冲点（静止的「等模型回复」看着像卡死）。
- 同伴面板 `ItemsView` 状态行改走 `statusHint()`（不再各写各的「忙碌中」）。
- 构建 `mutation-20261006-184802-489607`（api:neoforge）BUILD_OK + DEPLOY_OK；**已实机**（2026-10-06 19:00 烟测，气泡「✦ 等模型回复···」截图证据见 §3）。

**econ-report.js**（新工具）：
- 用法：`node rdd-selfcompile\scripts\verify-tools\econ-report.js [--since YYYY-MM-DD] [--until ...] [--dir <monitor目录>] [--json] [--help]`；默认目录 = live 实例 monitor。
- LLM 表按 `actor|phase|model` 聚合：calls/ok/fail/unknownUsage、四元与 total/fresh、durAvg/durMax、tool_calls 提出数、attempts。
- 工具表按工具聚合：calls/results/rej/fail、avg/p90/max 耗时（本地工具读 duration_ms，服务端按事件时间戳配对）。
- `fail` 只算明确 `success=false`；`UNKNOWN` 不算失败。
- exit 3 = 环境错（目录不存在等）。

## 6. 本次发现的两个起停游戏 bug（未修，留档）

1. **`mc-start.js gpt 60 --wait 0` flag 解析 bug**：数值 0 被 filter 掉 → WAIT=NaN → 等待轮询不跑，但 launch 仍以 detached spawn 发出；18:25 首次尝试静默失败（无新 java、launch-gpt.log 未动）。**规避**：直接跑 `launch-mc.ps1 -Instance gpt -AutoStopMinutes 60`（调用方 shell 会挂住，Bash 超时杀掉外层即可，游戏照常启动——AGENTS 已记此坑）。
2. **`mc-start.js gpt --stop` 不可用**（两层）：① execFileSync 把字面引号带进 `-File "E:/…"` → PS 报非法字符；② 更根本：`mc-instance.ps1` 是纯函数库，**没有 param/dispatcher**，`-Action Stop` 即使引号修好也是空转。**规避**：`Stop-Process -Id <pid> -Force`（与 watchdog mc-watchdog.ps1 到点同款）。已核实 mcp=0、java 消失、仅剩 WineFox 9996。

⚠️ `rdd-selfcompile\scripts\` 改动需用户批准，本次未修。建议后续（或进 harness 时间锁）：`mc-start.js --wait 数值` 解析、`--stop` 改走真实 Stop-RddMcInstance 函数或直发 Stop-Process。
