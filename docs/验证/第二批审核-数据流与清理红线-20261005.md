## 一、数据流全景

第二批干的事，一句话：**让白马自己写的东西，真的能被用掉，而且用掉的结果能回到它眼前。**

在此之前它一直在「裸着写」——写完只有日志，没人看，更没有下一轮。
这批把中间那一段补上了。

先说一条贯穿全局的前提，它解释了为什么全链路都在传**文件**而不是互相调用：

> 各个插件之间**被刻意做成互相看不见**（编译期就封死了直接引用别人代码）。
> 所以它们只能靠**落在同一个配置目录里的普通文件**互相传东西。
> 好处是稳（不依赖谁记得调用），代价是**传错了双方都不会立刻知道**——
> 全篇的坑基本都是这么来的。

### 1.1 一句话版流程

```
游戏里发生的事
    ↓  攒成「备忘录」（谁在什么情况下干了什么）
复盘一次
    ↓  模型读备忘录，给出判定 + 三种草稿
草稿写成文件（投递箱）
    ↓
  ┌──────────────┬──────────────────┐
脚本草稿        携带器草稿         自编译请求
  ↓              ↓                  ↓
进了脚本库     进候选表          ★没人接（见下）
（没上线）      ↓
  ↓           ★人工批准
  ↓            ↓
  ↓          进生效链（同伴危急时真会照着带东西）
人工批准上线
  ↓
真的跑一遍
  ↓
★跑完的结果自动记进「使用账本」
  ↓
┌─────────────┴─────────────┐
↓                            ↓
下一轮复审时告诉它        告诉主人一句
（"你上轮写的，用了没、      （限频 90 秒，
  成没成"）                可一键闭嘴）
```

### 1.2 每一段在干什么、有什么坑

**① 攒备忘录**
游戏里的事会被自动记下来，也可以手记。同一时刻**另一条线**（监督插件）也在记
「哪些阶段它自称完成了」——这两份记录是不同来源的，别混。

**② 复盘一次**（这一段刻意放到后台跑）
主线程上等模型会**卡死整局**（实测能卡 120 秒），所以立刻回一句「在跑了」，
复盘在后台线程做完再回来。顺带一个保护：换存档/重连后，迟到的结果**直接丢弃**，
绝不把旧世界的判定投到新世界里。

这一轮塞给模型的东西有三样：上轮产物的使用结果、**上轮被拒绝的原因**（本批新增，
之前它永远不知道自己错在哪，只会反复犯同一个错）、然后才是备忘录。

出来的判定包含：要做什么动作、七个经验字段、以及三种草稿。

**③ 草稿写成文件**
一份草稿 = 一个 JSON 文件，放在 `配置目录/artifact-outbox/<类别>/<同伴>/` 下。

- **文件名就是防重键**：类别 + 同伴 + 备忘录编号 + 正文摘要前 8 位。
  同一份草稿重投会说「重复」而不是写第二份。
- 正文超过 256KB **直接拒收并说明**——截断会把错误藏起来。
- 写入是原子的（先写临时文件再改名），不会出现写一半的文件。

**④ 三类草稿，三个命运**（这是全批最不对称的地方）

| 草稿 | 有人接吗 | 接到之后 |
|---|---|---|
| **脚本** | ✅ 脚本插件会主动扫 | 解析→校验→**进库但不上线**，状态是「已生成」。上线必须人工批 |
| **携带器** | ⚠️ 有登记，**但运行时能不能真用上还存疑**（见 §2） | 进候选表 → **人工批准**（必须写理由）→ 进生效链 |
| **自编译请求** | ❌ **完全没有下游** | 只能「列出/认领/标注」，**不写代码不编译**。外层工程流还没接 |

携带器那条线的设计意图是对的：**批准过的规则只往后追加、不许被重写悄悄抹掉**，
要撤销就再追加一条停用记录。另外它把「人工批准的规则」排在**内置规则前面**——
因为判断链是短路的，前面几级不成立就直接停，如果把批准的规则排在后面，
**它永远轮不到被判断**（这正是本批修掉的一个静默失效）。

**⑤ 真的跑一遍 → ⑥ 结果自动回流**（本批最有价值的一段）

这里有个**必须记下来**的坑：结果**不在**脚本插件自己的记录文件里。
实机跑完一个脚本，那个文件**行数没变、没有新记录**。真正的结果在**监测台**的日志里。

回流时的两条硬规矩：

1. **只回流能追到自己产物的运行**。追不到就不记，也不猜。
   （监测台的记录里**没有版本号**，只有脚本名。所以同一个脚本名被批准过多次时，
   会因为「分不清是哪一次」而**跳过并明说**，绝不挑一个——这条守卫有个漏洞，见 §2。）
2. **进行中/暂停不算结果**。半截结论一旦写进只追加的账本，事后收不回来。

**⑦ 使用账本：把「用过没有、成没成」记成事实**

只追加、不改写。记四件事：摆给同伴看过 → 被采用 → 真跑了 → 有结果了。
**只能往前，不能往回退**（迟到的旧消息会直接报错，而不是悄悄改结论）。

账本里的**证据等级**分成五档，这里是这个批次的信任链核心：

| 等级 | 意思 | 现在有人能产生吗 |
|---|---|---|
| 什么都没有 | — | ✅ |
| **机器可验证** | 有运行编号能回溯到监测台，不是自己说的 | ✅ 自动产生 |
| **模型声称已审** | 有个模型说它检查过了 | ✅（就是上一档的兄弟） |
| **人审过** | 人真的看过并签字 | ❌ **没有入口** |
| **生产长期验证** | 真实世界长期有效 | ❌ **没有数据源** |

关键设计：**后两档故意留空**。因为「声明有效性」这个工具是**模型能自己调用的**——
如果它能产出「人审过」，那就等于**模型自己给自己签审核通过**，整条信任链塌掉。
所以模型声明只记成「模型声称」，永远升不到「人审过」。

还有一条：**取消之后迟到的成功，不许把结论翻回成功**。
（照着脚本插件一个已知缺陷提前钉死的——同一个病不能在账本里再犯一次。
迟到的消息照样记录，不丢证据，但结论按取消算。）

**⑧ 回喂 + 说话**

- **回喂**：账本里本同伴的记录会写进下一轮复审的提示里，措辞刻意只说
  「用过、成没成」，**不说「所以有效」**。
- **说话**：复盘完给主人发**一句**短回执。三条硬约束：
  只说事实不下结论（「复审了 1 条」，不写「我学会了」）、**限频 90 秒按同伴**
  （否则刷屏等于没说话）、**一键闭嘴**。
  发不出去（主人不在线）会把限频额度**还回去**——这次没发出去就不该占额度。
  ⚠️ 这里已经修过一次「措辞撒谎」：原先把**文件总数**当成「已落箱待采纳」报给主人，
  把已被拒的和已采纳的全算进去了。

### 1.3 旁边那条「对账」支线（只读，而且**一半没接线**）

这条线的意思是：**「它说自己做完了」和「它写的东西真被用了吗」，对一下。**

```
监督插件记的「阶段完成表」 ──┐
                            ├──► 对一下 ──► 一个只读工具
学习者记的「使用账本」   ──┘              ⚠ 现在实机返回「没法对账」
```

- **为什么现在是「没法对账」**：对账器在那张新版本里，
  而实机装着的还是两天前的旧版。它的做法是**明说「对不了」而不是假装一致**——
  这个处理是对的（「读不到」不等于「没问题」）。
- **一个刻意的设计**：它**只报单边自相矛盾**，**不跨边配对**。
  因为两边的键不是同一套来源，「键一样」基本属于巧合。
  （之前版本就是靠这个巧合报差异，结果**报出来的全是假的**。）

**另一半更糟**：为了做「需求 ↔ 已完成 ↔ 已持有」的三方对账，
写了 **4 个类、约 674 行生产代码，加约 700 行测试——而没有任何一处生产代码调用它们。**
详见 §3.1。

## 二、已确认缺陷（按危害排序）

### ★P0-1　「绝不猜」的那道闸从来不会触发 —— 别人的成败会记到自己账上

**位置**：`plugins/learner/.../core/AcxExecutionReflector.java`

- `adoptableRefs()` :185-199 返回 `Map<ref, artifactId>`，第 **196** 行 `out.put(ref, id)`
- `artifactIdsByName()` :206-217 第 **208** 行**每条 run 都重新调** `adoptableRefs()`（全量扫盘）
- 守卫在 :125-131：`if (candidates.size() > 1) { ambiguous++; … continue; }`

**破线判据**：两个已采纳产物的 `consumer_ref` **相同**时，后者覆盖前者 ⇒
`candidates.size()` 恒为 1 ⇒ **:125 的歧义分支永远进不去** ⇒ 运行结果被静默归给
Map 赢的那个产物。

**为什么这不是理论问题**（三步都能在生产触发）：

1. `AcxLoader.java:245`：`String version = str(raw.getOrDefault("version", "1"))`
   ⇒ **模型不写 `version` 时一律落到 `"1"`**。
2. `AcxArtifactAdopter.java:157`：`writeBack(it, "ADOPTED", detail, name + "@" + published)`
   ⇒ 两次同名草稿都拿到 `consumer_ref = "X@1"`。
3. `FileAcxLibrary.java:196`：`e.versions.put(def.version(), v)`
   ⇒ **无重载保护**，第二个 `X@1` 直接覆盖第一个已发布版本。

⇒ 结果：**别人的 AC 运行成败被记到自己账本上**，而报告一切正常。
这正是本工程最怕的「读得出来但读错了」。

**最小修法**（三处都要，缺一处还会再犯）：

- `adoptableRefs()` 改成 `Map<String, List<String>>`（ref → artifactId 列表），
  或按 **name** 建索引而不是按 ref；
- `FileAcxLibrary.publish()`：目标 `name@version` 已存在且内容不同 ⇒ **抛错**，
  要求显式 `version` 递增或先 `reopen`；
- `AcxLoader` 对**缺省 version** 改为报错或自动递增（别静默给 `"1"`）。

### ★P0-2　已批准的携带器规则会**静默消失**，而界面仍显示「已批准」

（本批自己定的「读不到 ≠ 没有」那条红线，被自己破了）

**位置**：`api/common/.../api/carrier/CarrierRuleStore.java`

- `loadApproved()` :336-338：`name` 空或 `carry` 空 → `continue`
- `loadApproved()` :341-344：`compile(when)` 抛异常 → `continue`
- **两处都无日志、无报告、无计数**
- `approve()` 的报错文案 :190 **主动教用户**：「要改就人工编辑 `approved.jsonl`」

**破线判据**：用户照着提示手工编辑 approved.jsonl，打错一个 `when` 词
（`low_hp` 写成 `lowhp`）⇒ 该规则**静默从生效链消失** ⇒ 游戏退回 `CarrierRules.DEFAULT`
⇒ 而 `candidateStatus()` 仍返回 `APPROVED`，审批界面仍显示「已批准」。

`effective()` :83-101 在 `OVERRIDE` 为空时直接返回 DEFAULT，
**没有任何「有 N 条已批准但 M 条加载失败」的出口**。

**最小修法**：`loadApproved` 收集 `List<String> failed`，写日志 +
在 `effective()` 附带一条可见诊断（或 `learner_carrier list` 里加 `approved_broken=N`）。
**不许静默 continue。**

### ★P1-3　`candidates.json` 是本批唯一不用 `ATOMIC_MOVE` 的写路径

| 文件 | 位置 | 原子写 |
|---|---|---|
| `ArtifactOutbox.writeAtomic` | :384 | ✅ ATOMIC_MOVE + 降级 |
| `SelfCompileRequests.writeAck` | :178 | ✅ |

### ★P1-4　`OVERRIDE` 是 `public static volatile` 可变全局

**位置**：`CarrierRuleStore.java:51`

非 `final`、公开可写、进程级共享。施工文档自己记过
「测试里静态 `OVERRIDE` 会跨用例泄漏，一个用例 `install()` 后另一个就读到残留」。

**破线判据**：任何一处 `CarrierRuleStore.OVERRIDE = ...` 都能改掉全服生效链且无痕。

**最小修法**：`private static volatile`，配 `static List<Rule> overrideForTest()`
（package-private + 测试专用注释），或直接改实例化。

### P1-5　诊断文字被写进**数据字段**，而且只改第 0 条

**位置**：`CarrierRuleStore.effective()` :93-98

把第一条规则的 `name()` 改成 `"xxx [carrier-store 未安装，新携带器不会生效]"`。

### 3.3 六份各自私藏的 IO 基建

`ArtifactOutbox` / `UsageLedger` / `SelfCompileRequests` / `AcxExecutionReflector` /

## 六、要预备的红线

沿用 `第二批红线-数据语义-20261005.md` 的编号续写（DL-13 起），
每条都给「破了会怎样」+「怎么验」，**没有验法的红线不写**。

### DL-13　索引的键不许比它的元素更粗

- **内容**：任何 `Map<key, value>` 型索引，若**同一个 key 可能对应多个不同实体**，
  则该 Map 的 value 必须是**集合**，不能是单值。
- **代码锚点**：`AcxExecutionReflector.adoptableRefs()` :196
- **破线判据**：`map.put(identity, singleThing)` 而 identity 并不保证唯一。
  症状 = 下游那个「歧义检测」分支**永远进不去**，而代码里明明写着它在。
- **★ 为什么这条值钱**：它的危险形态是「守卫看起来存在、且有一条测试、
  但测试测的是守卫能工作的那种情况」。**比没有守卫更坏**。
- **怎么验**：`AcxExecutionReflectorTest` 补「两个 ref 完全相同」。
  另加一条通用测试：给索引塞 2 个同 key 元素，断言下游 `size()` 是 2 不是 1。

### DL-14　load/parse 的每个 `continue` 都要有对应的失败计数

- **内容**：跳过一行数据时，必须同时（a）计数、（b）让计数出现在某个可观测出口。
- **代码锚点**：`CarrierRuleStore.loadApproved()` :336-338、:341-344；
  `AcxExecutionReflector.readRuns` 的坏行 continue
- **破线判据**：`catch`/`continue` 后只留注释。症状 = **静默失效**：
  数据在文件里、界面说「已批准」、运行时没有。
- **怎么验**：往 `approved.jsonl` 手写一行坏 JSON + 一行坏 when ⇒
  断言 `effective()` 少一条 **且** 某个出口报 `approved_broken=2`。

### DL-15　「请手工编辑这个文件」的错误文案，必须配一条 loader 的坏行处理

- **内容**：一旦错误信息引导用户手改某个持久化文件，
  **那个文件的 loader 必须能报告「有几行我读不懂」**。
- **代码锚点**：`CarrierRuleStore.approve()` :190 的文案 ↔ :336-344 的静默 continue
- **破线判据**：报错文案教人去手改，而手改的后果是静默失效。
  **这是本工程最阴的一种**：错误信息本身把用户引向静默失败。
- **怎么验**：同 DL-14。

### DL-16　N2/N3 的枚举顺序不许被当成排序依据

- **内容**：`RequirementView.Attention` 刻意把 `NONE` 放最后。
  **同一条纪律要推广到本批新增的每个枚举**：
  `UsageLedger.Phase`（rank 显式，✅）、`UsageLedger.EvidenceLevel`（**无 rank，隐式靠 ordinal** ⚠️）、
  `ArtifactOutbox.Status`、`SelfCompileRequests.AckState`。
- **破线判据**：任何 `sort(ordinal())` / `EnumMap` 迭代序 / `values()[i]` 出现在
  **本批新增**的枚举上。`EvidenceLevel` 目前**没有**被排序，但它是唯一一个
  「顺序看起来有意义（NONE→…→PRODUCTION_VERIFIED 递增）」的枚举 ⇒ 最容易被后来人排序。
- **怎么验**：`grep "ordinal()"` 命中即人工确认；
  再加一条测试断言「`EvidenceLevel.values()` 的声明顺序与业务严重度一致」。

### DL-17　零生产引用的类必须显式标注，不许沉默地留在 main

- **内容**：新增的 `*Audit` / `*View` / `*Reconciler` 若没有生产装配点，
  类注释顶部必须写「**未接线**：无生产调用者，仅离线测试使用」，
  且**不得**被打进任何部署 jar。
- **代码锚点**：`rdd/policy/{RequirementFactAudit,RequirementAssetAudit,RequirementView,PreparationGapView}`
- **破线判据**：一个 674 行、零装配点、还进了 jar 的分析库。
