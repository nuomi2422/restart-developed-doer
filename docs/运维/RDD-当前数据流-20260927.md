# RDD 当前数据流（一页速览 · 2026-09-27）

> 对着真实源码梳理。用途：扫一眼看懂「任务组有什么 / 判定怎么走 / 派任务后下一步 / 怎么拆 / 传什么 / 注入什么经验」。

---

## 0. 一句话

**提交目标 → Stage-A 规划“一级阶段” → 一级到达时懒展开 Stage-B 出“二级” → Detector 每 tick 判定资产并推进 → 打勾 → 下一级。** 经验与规范在**规划请求**和**执行 AI 上下文**两处注入。

---

## 1. 三层任务组（数据模型）

```
Goal(goal-<uuid>)
 └─ PrimaryGoal(primary-<uuid>-N)          ← “一级 / 阶段”，带 waitFor 跨级资产门
     └─ Subtask(primary-…-rM)              ← “二级”，真正可执行 + 完成条件
```

| 层 | 字段 | 含义 |
|---|---|---|
| Goal | id, description, primaryGoals[] | 总目标 |
| PrimaryGoal | id, description, subtasks[], **waitFor[]**, **unexpanded** | 阶段；waitFor=进入该级前的跨级资产硬门；unexpanded=二级还没展开（懒边界） |
| Subtask | id, description, **detectionMode**, **condition**, detectionIntervalSeconds, maxAiChecks, recheckOnUnchanged, **body** | 二级；body={taskType, args} 驱动身体工具 |

**condition（完成判定）常见三种**：`{asset_key, minimum}`（持有个数）、`{minimum, group:"food"}`（食物等价）、`{type:"base"}`（基地成立）。

**状态枚举**（源码 api/）：
- SubtaskStatus = `PENDING, RUNNING, COMPLETED, FAILED, STALLED, COOLDOWN, INVALIDATED, SKIPPED`
- PrimaryGoalStatus = `PENDING, ACTIVE, AWAITING_SUPERVISOR, WAITING, REPLANNING, COMPLETED, FAILED, RECOVERING`
- DetectionMode = `HARD_CODED`（硬编码条件自动判定）｜`AI_ASSISTED`（交还 AI）
- SupervisorDecisionType = `CONFIRM, REJECT, NEED_MORE_EVIDENCE, REPLAN, DEFER`

## 2. 总图

```
[玩家 /goal 或 AI rdd_submit]
        │
        ▼
┌─────────────────────── Stage-A：规划“一级阶段” ───────────────────────┐
│ 入口 RddStagePlanner.planStages(objective)                            │
│ 输入(拼进 prompt)：                                                    │
│   · 真实背包快照 PlanningAssetSnapshot（RL-1 地基，不读空背包）        │
│   · 已持有资产 planningAssets / 村庄上下文 / 可恢复上下文(LOST)        │
│   · 风险预备 prepHint（RddRiskPlanning）                               │
│   · 规划策略块 RddPlanningPolicy.block(objective,"stage_a")            │
│   · 经验知识 RddPlanningKnowledge（见 §5）                             │
│   · v3.2 《安身任务·固定流程要求》annexTaskSpec()（12 步）             │
│ LLM(plan_stages) → parse → RddPlanGuard.filterStages(丢无效)           │
│                 → RddRiskPlanning.injectWaitFor(高风险级补跨级硬门)    │
│ 产出：primaryGoals[]（未展开，等到达再展开）                           │
└───────────────────────────────────────────────────────────────────────┘
        │  某一级到达且 unexpanded → RddGoalDriver.needExpansion
        ▼
┌─────────────────────── Stage-B：展开该级的“二级” ─────────────────────┐
│ RddDecomposer.decomposeSpecs(该一级)                                   │
│ 输入：该一级主题 + 背包快照 + 经验知识 + annexTaskSpec                 │
│ LLM → subtasks[]（每条带 condition + body 工具）                       │
└───────────────────────────────────────────────────────────────────────┘
        │
        ▼
   Detector.onServerTick → tickRuntime（每 tick 判定/推进，见 §3）
        │
        ▼
   打勾 → 一级全完成 → 下一级（懒展开）… 直到 goal 完成
```

## 3. 判定流：`RddDetector.tickRuntime` 精确顺序

服务器每 tick 触发 `onServerTick` → 刷监督开关 → 恢复任务链 → **无条件缓存真实背包** → `tickRuntime`：

1. 扫真实背包 `countInventory` → 缓存（RL-1 数据源）；`surplus.inspect`
2. 节流观测：`populateAssets`（资产登记）、`RddWorldAssetObserver`（世界资产）
3. **双向协商** `tickNegotiation`：士兵回 REJECT/COUNTER → 改单/重规划/停车（命中就本 tick 结束）
4. **收尾/监督态直接返回**：`AWAITING_SUPERVISOR / REPLANNING / COMPLETED / FAILED`
5. `RECOVERING`：先发 `chain_recovering` 事件，再按真实资产照常推进
6. **`PENDING / WAITING` 分支**（依赖门）：
   - 未展开 → `needExpansion` 上报，返回
   - `riskGateAllows`?（下界/末地级才拦，RL-8）不达标 → `primary_waiting`，返回
   - `activateCurrentFromSnapshot(背包快照)` 过 wait_for 依赖门 → 不过 → `primary_waiting(dependency assets not present)`，返回；过了 → `dependency_met`
7. 若 primary 仍非 `ACTIVE` → 返回
8. 二级 `PENDING` → `startCurrent()`（启动）
9. `STALLED` → `stallWatcher.handleStalled`（拍醒/升级失败），返回
10. `FAILED` → 先重跑硬编码条件：此刻已满足 → 直接验收推进；否则 `handleSubtaskFailure`（Level-2 预算内重跑）
11. `RUNNING` → **提前达成连跳**（`early_achievement`）：硬编码二级资产已满足就同 tick 连跳，到一级边界自动过依赖门进下一级
12. 非硬编码（AI_ASSISTED）→ 交还 AI，返回
13. **卡死监督** `stallWatcher.track`（资产指纹连续未变 → STALLED 并拍醒将军）
14. `RddBodyDispatcher.maybeSubmit`（把 body 交给身体执行，supervision+bodySubmission 开关下）
15. `conditionMatches`? → `completeSubtask`（打勾，推进）；否则 `maybeRetryOrFail`

## 4. 两个提交入口

| 入口 | 路径 | 说明 |
|---|---|---|
| `/goal`（宿主目标） | Stage-A 多级规划（§2） | 一次规划出 N 个一级阶段，懒展开 |
| `rdd_submit`（有界） | 直接建 **单** goal/primary/subtask → `RddPlugin.bind` | 必填 goal/primary_goal/subtask/asset_key/minimum/companion；**先过 RL-8 风险门**（高风险级装备不足直接拒） |

## 5. 注入了什么（传入 / 拆分的输入）

**规划请求（Stage-A/B 共用接线点 `RddDecomposer.llmAsk`，正文拼装 `RddPlanningKnowledge.withKnowledge`）**
- 真实背包快照（RL-1）、已持有资产、已完成阶段（GoalLineage）、村庄/可恢复(LOST)上下文
- 风险预备 prepHint + 规划策略块（`planning_policy` 事件报“用了哪些规则/丢了什么”）
- **经验知识**：`RddPlanningKnowledge.HOST` → 宿主 `NumenPlugins.planningKnowledge(PlanningQuery)`（把各插件贡献的参考资料贴进请求正文；取不到=退化成无知识，规划照常）
- **v3.2 全量注入** `annexTaskSpec()`：《安身任务·固定流程 12 步 + 依赖铁律》——接 StagePlanner / Decomposer

**执行 AI 上下文（每轮）**
- `RddV32Directives.attachHarness()` 把 **《执行提示·实测 11 条》** 拼进执行体上下文（`RddPlugin.renderStateContext`）

**经验三段（Memory/FC/AC）**
- 规划侧：经 `PlanningQuery` 拉知识（含 knownFailures）；执行侧工具 `experience_recall / experience_learn / experience_verify`

## 7. 上一处 bug 就在这条链上（RL-3）

- **现象**：primary-0（“挖/采集”阶段）永久 `primary_waiting: dependency assets not present`
- **根因**：Stage-A 的 `RddRiskPlanning.injectWaitFor` 依据 `RiskGate.levelForText` 把含“挖/采集”的**第一级**误判成 `MINING`，给它挂了 `bread4+torch16` 硬门；而该级本身就是要产出它们 → 自己等自己
- **修复** `cf9ee90c`：**第一级从零起步不加跨级前置门**（+回归测试）。修复后 `rdd-tasks` 里 primary-0 的 `waitFor=[]` ✅
- **红线关联**：RL-3「早期阶段不被误挂高风险门」——这次正是踩它

## 8. 判定“怎么算通过 / 怎么算破”（红线回归）

- 任务链正常推进：`subtask_completed` + `dependency_met`，一级按序推进
- 早期级 `waitFor` 必须为空（RL-3）；下界/末地级 waitFor 必须含抗火药/床/两套钻石甲（RL-4）
- 死亡 → `companion_assets_invalidated` + `LOST`（RL-6）；复活在床边（RL-7）
- 看 `monitor/rdd.jsonl` 事件与 `rdd-tasks/*.json` 状态**对得上**（事件≠状态=半坏状态）
