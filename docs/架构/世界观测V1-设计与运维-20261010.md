# 世界观测 World State V1 —— 设计与运维（2026-10-10）

> 目标：**只读查询、显式采集、带时间与覆盖信息的基础存储**。
> 一句话职责：回答「哪里有什么？什么时候看到的？现在是否还能确认？本次到底检查了多少范围？」
> 基线 tag：`worldstate-v1-baseline-20261010`（打在当前代码上，之后再动）。

## 一、模块职责与分工

世界观测只负责 **采集、保存、查询世界事实**，不越界：

| 模块 | 负责什么 |
|---|---|
| **世界观测（本模块）** | 采集、保存和查询世界事实 |
| 基建 settlement | 设施身份、用途、边界、入口、保护规则 |
| RDD 资产 | 哪些事实可作规划资源、资源如何使用 |
| 任务链 | 根据事实判断目标是否完成 |
| 执行工具 | 建造、挖掘、移动、交互 |

同一份观测可被多方读取，但**设施登记、资产决策、任务进度仍由各自模块管理**。
世界观测返回「圈内观测到两只羊」，是否满足牧场要求由基建/任务链判断，不在本模块再写一套任务链。

## 二、四层结构

```text
AI 工具 / 基建 / RDD / 后续新功能
                ↓
        查询服务 QueryService        （读/取分开的对外入口）
          ↙             ↘
观测存储 ObservationStore   采集调度 RefreshService
                               ↓
                      采集器 WorldProvider
                               ↓
                       Minecraft 世界
```

- **采集器 WorldProvider**：按主题拆分（`environment` / `blocks` / `entities` / `containers` / `facilities`）。
  声明支持什么查询、能查多大（`maxVolume`）、返回的数据类型（`payload`）与版本（`dataVersion`）。
  **只读世界**：不强制加载区块、不改世界、不登记、不派工。
- **采集调度 RefreshService**：同类请求合并（去重）、体积预算、超时/取消/排队；不在一次工具调用里把服务端卡住。
- **观测存储 ObservationStore**：存「某次看到的东西」，带来源/时间/覆盖/新鲜度/版本；内存 LRU + 持久层。
- **查询服务 QueryService**：统一对外返回，除数据外还带「有多旧 / 覆盖多全 / 能不能确认」。

## 三、读与取，接口上明确分开

游戏内统一入口 `world_state`，两个动作：

```text
world_state action=read    → 只读已有观测；没有就明确返回没有，不偷偷扫描
world_state action=refresh → 请求采集；完成后写入观测，并返回本次结果
```

示例：

```text
world_state action=read    topic=entities  dimension=minecraft:overworld  x1..z2  entity_type=minecraft:sheep
world_state action=refresh topic=environment dimension=minecraft:overworld
world_state action=refresh topic=entities  x1=.. y1=.. z1=.. x2=.. y2=.. z2=..
```

两者都**不修改游戏世界**；刷新只更新本模块自己的缓存/存档。需要「缓存够新就读，否则刷新」时，
以后再加**显式**策略参数，不默认隐藏扫描行为。

## 四、四条不许违反的语义（红线）

1. **刷新失败 ≠ 清空旧观测。** 例如远处箱子区块未加载时返回
   `本次刷新：未能执行，原因 CHUNK_UNLOADED；历史快照仍在，当前内容：无法确认`。
   不能返回「0」，也不能把旧值说成刚刚确认的。
2. **只有完整检查过范围，才能肯定地说「这里有 0 只」。**
   `Coverage.COMPLETE` 才允许证空；`PARTIAL` 只报「已检查部分观察到 N」，`UNLOADED` 明确失败。
3. **失败模式不许静默。** 每个失败都带 `FailReason`（`DIMENSION_MISSING` / `CHUNK_UNLOADED` /
   `BUDGET_EXCEEDED` / `NO_PROVIDER` / `PROVIDER_ERROR` / `INVALID_REQUEST` / `TIMED_OUT` / `CANCELLED`）。
4. **旧刷新不得覆盖更新的观测。** 观测带单调递增 `revision`（按请求被采纳的先后分配），
   `put` 拒绝更旧的 revision。

## 五、观测键与命名空间

```text
观测键 = 世界存档 worldId + 维度 + 主题 + 目标/范围 + 过滤条件
```

- **世界存档必须进命名空间**：两个存档在同一维度、同一坐标上不能互相串数据。
  `worldId` 取自 `server.getWorldData().getLevelName()`。
- `target` / `filter` 是规范串（如 `box=0,64,0..3,64,3`、`type=minecraft:sheep`），归一化后参与键相等。

一条观测记录 `Observation` 携带：键、有类型载荷、来源、来源类型、游戏 tick、实际毫秒、
覆盖 `Coverage`、新鲜度 `Freshness`、修订号 `revision`、数据格式版本 `dataVersion`。

## 六、两层存储

- **内存层** `InMemoryObservationStore`：LRU，容量 512（本模块），返回不可变快照。
- **持久层** `ObservationJson`：按世界存档隔离、带 `schema_version`、原子写入（tmp + move）、
  容量受限不无限积累。落盘位置：

  ```text
  <gameDir>/config/numen/worldstate/observations.json
  ```

  **重启后载入的观测一律标 `Freshness.HISTORICAL`**：它们是上个进程看到的，不能冒充本轮实时结果，
  要读当前内容必须 `refresh`。

新鲜度按主题 TTL 配置（`TopicFreshnessPolicy.defaults()`：environment/entities 30s、
blocks 60s、containers/facilities 120s）。**TTL 只说明数据有多旧，不保证 TTL 内世界没变化**——
真正要取物/交易/完成后，仍应再刷新，执行工具也仍要检查前置条件。

设施登记继续存在 settlement 自己的真源里；世界观测里的设施摘要即使被淘汰，也不会导致基地或保护规则丢失。

## 七、V1 交付：框架 + 两个真实采集器

跑通的链：**工具请求 → 采集 → 保存 → 读取 → 过期判断 → 重启读取历史 → 再次刷新**。

| 主题 | 采集器 | 说明 |
|---|---|---|
| `environment` | `EnvironmentWorldProvider` | 维度/游戏时间/天气，范围无关，`Coverage.COMPLETE` |
| `entities` | `EntityCountWorldProvider` | 有界实体计数，区分 零 / 部分 / 未加载；`maxVolume=32768` |

选实体计数作第二个采集器，是因为它马上服务已建成的羊圈/牛圈，验证架构不是空架子。

**尚未接入**（`refresh` 会明确返回 `NO_PROVIDER`）：`blocks` / `containers` / `facilities`。

## 八、增量接入规则（从今天起）

1. **旧调用保持现状**：现有工具、扫描、投影继续工作。
2. **新增的世界查询优先注册采集器**，统一走查询服务。
3. **旧模块今后需要修改查询逻辑时，再按主题逐个接入。**

适配旧扫描器前先确认它**确实只读**：有些 `inspect` 会顺手更新设施状态、收尾或登记
（如 `settlement action=inspect` 会回写施工账），**不能因为名字像查询就直接当采集器**。

## 十、离线测试覆盖（6 个测试类）

- `read` **不触发采集**（采集器调用计数为 0）。
- 不同**世界/维度/范围/过滤条件**不会串缓存。
- **空 / 部分 / 未加载**能区分；只有 `COMPLETE` 能证空。
- **旧刷新不覆盖更新的观测**（revision 守卫）。
- 重启后动态观测标 **HISTORICAL**，不冒充实时。
- **并发重复请求**合并成一次采集；**超时**得 `TIMED_OUT`；**取消**可见。
- 持久化坏 JSON 容错、未知主题整条丢弃（向前兼容）。

## 十一、实机验证清单（进游戏后做）

1. 读一个从未采集的位置 → 明确返回「无观测」。
2. 刷新羊圈 → 读到正确范围的数量。
3. 改变羊的数量后：`read` 显示旧快照及时间，`refresh` 才更新。
4. 未加载范围不强制加载、不误报 0（走远一点再 read/refresh 对照）。
5. 重启后保留历史（HISTORICAL），再 `refresh` 得到当前结果。
6. 监测台可看到 `read` / `refresh` / 失败原因。

## 十二、已知限制 / 后续

- `blocks` / `containers` / `facilities` 采集器未接入（契约已就位，按主题逐个加）。
- 大查询的**分批执行 + 返回任务 ID** 未做；V1 对超预算请求**明确拒绝**（`BUDGET_EXCEEDED`），
  请调用方缩小范围——先画清「拒绝而不是硬跑」这条线。
- 异步 `RefreshService.submit` 已提供（去重/超时/取消，供纯逻辑与离线用）。
  **宿主采集器读真实世界必须在服务端线程**：工具走同步 `refresh`（`QueryService.refresh`），
  不要在异步线程里读 MC 世界。
- `world_state` 工具当前为 `Residency.DEFERRED`；若要每轮可见再改 `residency()`。
