# 特殊模式 v3.1 模块蓝图（Special Engineering Loop）

> 文档状态：v0.1 草案（免费 AI 执笔，**待用户/外脑批准**，批准前不写码）
> 日期：2026-09-26 ｜ 档位：**架构级（Architectural）** → 完整九步流 + 人工批准
> 关联资产：自变异系统 v3（`自变异系统v3/README.md`、`INDEX.md`）、`rdd-selfcompile\`、`ai-bridge\`、Codex `gpt-5.6-terra`

---

## 1. 不可偏移的架构方向（用户原话锁定）

1. 在 v3 现有工作流基础上**新增**「特殊模式」，与现有「平常模式」**并存**，二者互不替换。
2. 特殊模式本质：把 **需求分析 → 跨模型研究 → 工程实现 → 代码审核 → MC 实机剧本验证 → 压力测试 → 问题回流** 串成一个**持续循环**；不是普通 Agent，也不是简单多模型聊天。
3. 三个角色固定：
   - **O** = OpenCode 里的免费 AI：真正干活 —— 写代码 → 执行脚本 → 测试 → 进游戏 → 验证 → 据结果继续干活；**不因一次对话结束而停**（靠脚本持续驱动）。
   - **W** = 网页版免费模型 **GLM / Qwen / Kimi**：外部讨论 / 研究 / 方案审核层，**不是直接替 O 写码**；**必须能上网搜资料**，不能只凭记忆。
   - **C** = Codex 里的 **GPT-5.6-terra**：高级审核 / 架构审查 / 难题升级，**不是每步都参与**。
4. 用户给一个模块时提供：主要目的、架构意图、想达成什么、与其他模块的关系、**最重要的约束/要求**。O 先生成**工程文档/要求文档**，再进入 W 讨论。
5. 最终目标不是「功能写出来了吗」，而是 **整体行为真正达到用户最初要求**，并**补全用户原来没想到的需求 / 边界 / 异常 / 模块关系**。

---

## 2. 模块边界

### 属于
- 一条新的 **skills 级能力** + 编排脚本 + W/C 接入层 + MC 实机验证剧本层。
- 与 v3 现有「自编译闭环 / 数字1 轮询 / 数字2 模块模式 / 数字3 外脑」**同层协作**，作为其上一个「工程闭环」编排器。

### 非目标（本期明确不做）
- 不改 Numen 游戏核心逻辑；不替换现有平常模式（两模式并存，由用户或入口选择）。
- 不自动向 MC/MCP 投递执行指令（受「免费 AI 硬约束」：只读观察为主，执行由 O 按既有自编译流程走）。
- 不做封闭自动评分取代人工批准；架构级变更仍留人工批准门。

## 3. 目标与用户故事（验收标准）

| 编号 | 用户故事 | 验收标准 |
|---|---|---|
| US-1 | 我给一个模块的一句话目标，系统能自动产出**工程要求文档** | 文档含：要实现什么 / 为什么这么设计 / 工程要求 / 分几批 / 每批怎么验证 / 与既有架构衔接 / 是否达成原始目的 / 有无遗漏 |
| US-2 | O 与 W（GLM/Qwen/Kimi）多轮讨论并联网补资料 | 每个 W 模型都被问过一遍；其余两家的结果汇总给 GLM；GLM 综合；O↔GLM 1~3 轮后出**最终实现要求** |
| US-3 | O 按工程规范写码并测试 | 遵循 v3 九步流；先测试绿，再交 W 审核，认可后再进游戏 |
| US-4 | 在 **test 存档（创造模式）** 用 MCP 驱动 AI 对话写验证剧本，验的是「这个小区域是否真实现了当初要求」 | 产出验证剧本 + 实机验证报告（实现成功 / 发现问题 / 发现遗漏） |
| US-5 | 每 3~4 个区域/轮后交 C 深度审代码 | C 看代码审核：确认完成 / 指出问题回流 O+GLM / 特别难则 C 加入讨论 |
| US-6 | 大部分模块完成后进入架构级 MC 长跑压测 1~2 小时 | 记录真实问题 → 补剧本 → 重新分析要求 → 补码 → 审核 → 再进 MC，循环直到整体行为达标 |
| US-7 | 持续不中断 | 复用 watchdog；单次对话结束不导致任务停摆 |

## 4. 核心设计

### 4.1 角色与职责

| 角色 | 实体 | 职责 | 输入 | 输出 |
|---|---|---|---|---|
| **O** | opencode 免费 AI | 生成工程文档、写码、单测、驱动 MC、按结果继续 | 用户模块意图、W/C 意见 | 需求文档、代码、测试、实机验证报告 |
| **W** | GLM / Qwen / Kimi（网页） | 独立出方案/问题/工程意见、联网搜资料、审核代码 | O 的需求描述 | 各模型方案、GLM 综合结论 |
| **C** | Codex `gpt-5.6-terra` | 深度代码审核、架构审查、难题升级、可加入讨论 | 阶段要求/架构/代码/验证结果/遗留问题 | 审核结论、问题清单、升级裁定 |

### 4.2 三级循环

```
【一级循环 · 首模块/复杂模块】
用户给模块意图
   → O 生成工程文档（要求草案）
   → O → W(GL M / Qwen / Kimi) 分别问一遍
        （把另两家的输出全部交给 GLM）
   → 各模型联网搜资料 + 出方案/问题/工程意见
   → 汇总 → GLM 综合
   → O ↔ GLM 对话 1~3 轮
   → 形成【最终实现要求】（含自问四问）
   → O 按工程规范写码 → 单测 → 交 W 审核 → 补改
   → 进 MC test 存档（创造模式）写剧本、MCP 驱动实机验证
   → 验证报告回 O → 下一轮

【二级循环 · 后续模块，降本】
O ↔ GLM 两人为主，重复：
需求 → 讨论 → 要求 → 写码 → 测试 → 审核 → 游戏剧本 → 实机验证 → 问题反馈 → 下一轮

【C 审查 · 每 3~4 区/轮 或满 1h】
O 经 MCP 把【要求 / 架构 / 已完成代码 / 验证结果 / 遗留问题】交 C
   → C 直接看代码审核
   → 确认完成 ｜ 指出问题→回流 O+GLM 讨论 ｜ 特别难→C 直接加入讨论

【架构级循环 · 大部分模块完成后】
整体架构 → MC 压力测试（跑 1~2 小时） → 真实问题出现
   → 记录问题 → 补验证剧本 → 重新分析要求 → 补代码 → 审核 → 再进 MC
   → 补全用户原来没想到的需求/边界/异常/模块关系 → 循环直到整体行为达标
```

### 4.3 每模块状态机

```
INTENT          用户给意图（目的/架构意图/关系/约束）
REQ_DRAFT       O 生成工程文档草案
W_SURVEY        O→GLM/Qwen/Kimi 各问一遍；联网搜资料
W_SYNTH         汇总给 GLM 综合
O_GLM_NEGOTIATE O↔GLM 1~3 轮
REQ_FINAL       最终实现要求（含自问四问 + 分批 + 验证方案）
IMPL            O 写码
UNIT_TEST       单测/边界/异常
W_REVIEW        W 审码 → 通过/补改
MC_TEST         test 存档创造模式 + 剧本 + MCP 实机验证
VERDICT         实现成功 / 发现问题 / 发现遗漏
NEXT_ROUND      回流下一轮（或每 3~4 轮触发 C_REVIEW）
C_REVIEW        C 深度审核（可选 ARCH_ESCALATION 升级）
ARCH_STRESS     全模块后架构级长跑压测
```

**回滚/止损边界**：每状态产出落盘可追溯；连续两次失败找不到根因 → 止损汇报，不无限硬磕；架构级/高风险留人工待批。

### 4.4 「最终实现要求」必含自问四问（用户强调）

1. **怎么办？**（实现路径）
2. **为什么这么设计？**（设计理由，对照架构意图）
3. **达成目的了吗？**（对照最初目标自检）
4. **遗漏了吗？**（边界/异常/模块关系是否覆盖 —— 用户原话「yiyu管理」按“遗漏检查”理解）

### 4.5 W 层接入（**待确认**）

现状：`ai-bridge`（MCP 9527，扩展+content.js）仅支持 `doubao / chatgpt / claude`。要接 GLM/Qwen/Kimi 需改四处：
`chrome-extension/default-configs.js`、`background.js` 的 `PLATFORM_URLS`、`manifest.json` 的 `host_permissions`/`content_scripts.matches`、`mcp-server/index.js` 两处 `z.enum`。
**或**按用户原话「用 playwright 直接进浏览器」另建 playwright/CDP 驱动脚本（参考 `scripts/brain-drive.js`、`feed-ds-ws.js` 的 `waitReplySettled`）。

候选站点（**待用户确认登录环境**）：
- GLM：`chatglm.cn`（智谱清言）或 `chat.z.ai`
- Qwen：`chat.qwen.ai` 或 `tongyi.aliyun.com`

## 6. 测试与事实证据要求

- **单测**：首测通过后立即补边界/异常/极端/多数据。
- **debug 埋点**：入口、输入、分支、输出；日志能回答「谁、何时、为何、结果」。
- **事实证据**：编译成功/MCP 返回 OK ≠ 真实行为。须有：监测台（8776）+ MC 世界事实 + 验证剧本 + 报告对撞。
- **W/C 回答**当参考不当真理；函数名/API 必对真实源码核。
- 每轮写 `测试日志.md` + `自变异系统v3/08-更新日志.md`。
