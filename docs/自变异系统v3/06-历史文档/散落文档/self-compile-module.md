# Self-Compile 自变异系统

## 1. 定位（2026-08-30 方向纠正）

**Self-Compile = 你的 AI 编程工具本身（类似 Claude CLI / Codex），不是 Gradle 插件，也不是构建系统里的一个编译任务。**

它是一个**外挂式、可切换的开发模式**，作为统一 AI 开发工具的一个工作流存在：

```text
统一 AI 开发工具
├── 普通开发模式      （读码/改码/编译/测试）
└── 自变异模式        （本模块）
      ├── 分析能力缺口
      ├── 生成/修改原子工具
      ├── 安全编译门（子环节）
      ├── 打包 jar
      ├── 启动/关闭游戏
      ├── 通过 MCP 实际游玩验证
      ├── 验证世界真实结果
      ├── 部署到实验 MC
      ├── 部署到生产 MC
      └── 记录结果 → 循环
```

**主体是"能玩游戏的 AI 编程工具"，编译只是其中一个环节。**

## 2. 之前的方向偏差（已纠正）

之前把本模块实现成了：

```text
source/*.java → 静态检查 → JDK JavaCompiler → classes/ → compile.log
```

这是一个**构建工具**，不是自变异系统。

对照：

| 你的设计 | 之前做的东西 | 状态 |
|---|---|---|
| AI 编程工具是主体 | Gradle 插件是主体 | ❌ 纠正 |
| AI 生成工具代码 | 只编译已有 Java | ❌ 待接入 |
| 通过 MCP 实际玩游戏验证 | 没有游戏、没有 MCP | ❌ 待接入 |
| 产出新 jar 并部署 | 只产出 class | ❌ 待接入 |
| 实验 MC / 生产 MC 双实例隔离 | 只有构建环境 | ❌ 待接入 |
| 工具生命周期管理 | 只有源码→class 编译链 | ❌ 待接入 |

已经做出来的**安全编译门**（`MutationStaticChecker` / `MutationCompiler` / 工作区 / 状态机 / 预算 / 候选产物 / 回滚脚本）**保留**，但定位为自变异流程里的一个**子环节**，不是主体。

## 3. 它解决什么（主体目标）

当现有能力无法完成任务时，Self-Compile 以外部 AI 身份自动：

1. 接收能力缺失 / 失败上下文（从游戏、MCP、监测台或任务链来）；
2. 读取铁律、经验、缺陷模式和工具快照；
3. 在隔离工作区生成/修改候选能力；
4. 过安全编译门，产出 jar；
5. **启动实验 MC 实例**；
6. **通过 MCP 实际游玩，验证真实世界结果**；
7. 限定轮次、时长、失败预算；
8. 通过后部署到生产 MC 实例，重启游戏；
9. 记录结果，继续下一轮或止损。

## 4. 输入

- 能力缺失描述（外部传入或游戏内请求）
- 任务上下文
- 当前工具 / 技能快照
- 历史失败记录
- 经验和铁律

## 5. 输出

- 候选工具 / 能力（jar）
- 版本清单
- MCP 实测验证结果
- 失败归档
- 变更报告

## 6. 与 Numen 的边界

Self-Compile 是**外部主控**：

```text
外部 AI 工具
  ├── 启动/关闭 MC 实例（脚本）
  ├── 通过 Numen MCP 驱动同伴游玩
  ├── 通过监测台读取事件/状态/tools
  ├── 部署 jar 到实验/生产 mods
  └── 经 NumenPlugins.register 挂工具/技能（受控）
```

游戏内 Numen AI 的 `request_compile` 是**备用路线**（游戏内请求 → 外部执行），保留接口，但主控默认是外部 AI 自己玩、自己写码、自己测。

## 7. 受控状态机（保留，作为子环节门禁）

```text
REQUESTED → WORKSPACE_CREATED → GENERATED → STATICALLY_CHECKED
→ COMPILED → CANDIDATE → VERIFIED → DELIVERED
```

`MutationStateMachine` 禁止跳状态；`MutationBudget` 限制尝试次数和时长。

## 8. 双 MC 环境（主体必需）

```text
实验 MC 实例   生产 MC 实例
├── 独立 gameDir   ├── 独立 gameDir
├── 独立 mods      ├── 独立 mods
├── 独立 world     ├── 独立 world
├── 独立日志        ├── 独立日志
└── 验证用          └── 实际部署
```

未实现前，禁止把候选 jar 直接复制到生产 `mods/`。

## 9. 止损原则

- 轮次上限、时间上限、失败预算；
- 编译失败连击、验证失败连击、环境不可用；
- 触发止损后只输出归档结果，不继续盲改。

## 10. 工程化护栏（已落地，作为子环节保障）

- 工作区 / 源码 / 类 / 产物 / 报告分离；
- Manifest 记录每次变异状态和失败原因；
- 未达 `VERIFIED` 不得交付；
- 单模块回滚只改 `active.json`，不整体回退宿主；
- 正常 / 空值 / 特殊字符 / 并发 / 状态跳跃测试覆盖。

测试命令：

```text
:plugins:selfcompile:clean :plugins:selfcompile:test --no-build-cache --no-daemon
```

## 12. 下一步（主体方向）

按优先级：

1. **外部循环编排器**：把"启动游戏 → MCP 操作 → 读监测台 → 验证 → 退出 → 改码"串成一个可审计的脚本/命令；
2. **jar 打包**：把编译通过的 classes 打成可部署 jar；
3. **实验/生产双 MC**：先定义实例目录与启动脚本，避免污染当前生产实例；
4. **MCP 游玩验证**：用 `mc_talk` / Numen MCP 通道在实验实例里实际执行并读回结果；
5. **工具生命周期**：让生成的能力真正注册进 Numen 工具目录。
