## 二、接线点（3 处，全部在 `RddDecomposer.java`）

知识正文必须进入 `userContent`，因为 `RddPlugin.publishPlanningContext(companionId, stage, userContent, ...)`
记录的正是这个字符串——**只写日志不算接通**。

| 位置 | 现状行 | 时点 |
|---|---|---|
| `decompose(...)` | 93 行 `String userContent = decompositionPrompt(objective, RddPlugin.lastInventory(companionId), List.of());` | 首次规划 / 回退路径 |
| `decomposeSpecs(...)` | 141-142 行 `llmAsk(..., decompositionPrompt(themeObjective, ..., completedStages) + hint, ...)` | 阶段展开 |
| 同上 `attempt >= 1` | 136-140 行的 `hint` | 重试 / 回退（已知失败事实要带上） |

## 三、依赖问题（必须先定，否则接线跑不起来）

`buildSrc/numen-plugin.gradle` 明确规定：插件编译期**只看得见瘦 api jar + ai + ui**，
刻意让联动与第三方插件走同一扇门。因此：

> **RDD 直接 `import com.dwinovo.numen.plugins.experience.*` 会破坏这条约定**，
> 且 `plugins/rdd` 与 `plugins:experience` 之间本来就不存在 project 依赖。

两条可行路线，请主线程选一条：

### 方案 B（推荐）：加宿主 API 知识缝，插件互不可见

在 `api:common` 增加与 `contributeState` 同构的一对：

```java
// NumenApi
/** 每次规划请求现算一段参考资料；与 contributeState 同构，只是消费方是任务链规划器。 */
void contributePlanningKnowledge(PlanningKnowledgeContributor contributor);

// PlanningKnowledgeContributor：入参是这次规划的背景，返回可注入正文（可空）
String knowledgeFor(UUID companion, String objective, String stage, List<String> knownFailures);
```

`NumenPlugins` 里照 `STATE` 的写法规整一份 `PLANNING` 列表，并暴露静态汇总方法
（复用现有容错：某个贡献者算炸了只丢它自己那段）。

经验插件在 `setup(...)` 里注册：

```java
numen.contributePlanningKnowledge((companion, objective, stage, failures) -> {
    PlanningKnowledge.Request req = PlanningKnowledge.Request.of(objective, stage, failures);
    return ExperienceKnowledgeSource.recall(companion, req).text();
});
```

RDD 侧（`RddDecomposer`）只调宿主静态方法拿正文，再拼进 `userContent`：

```java
String knowledge = NumenPlugins.planningKnowledge(companionId, objective, "stage_b", knownFailures);
String userContent = decompositionPrompt(...) + knowledge;
```

好处：RDD 与经验插件全程互不可见、符合既定约定；监测台可通过 expmem.jsonl 的
`planning_knowledge` 事件核对选了什么、来自哪。

### 方案 A（低风险替代）：纯逻辑下沉 `experience-core`，走模块依赖

`PlanningKnowledge` / `GuideKnowledge` / `BuiltinExperience` 都不依赖 MC，可整体移到
`experience-core`（与 `plugins/ac → ac-core`、`plugins/rdd → rdd-core` 同构）。
把两处 `FMLPaths.GAMEDIR` 改成方法入参 `Path configNumenDir` 即完成去宿主化。
然后 `plugins/rdd/build.gradle` 加 `implementation project(':experience-core')`，
直接把攻略 + 内置种子拼进 prompt。

代价：RDD 只能拿到**攻略 + 内置种子**，拿不到该同伴的亲历经验（那份在插件侧的
`ExperiencePlugin.memory`）。要拿亲历经验就得让 RDD 自己 `ExperienceMemory.at(...)`
读同一个 jsonl —— 同一文件两个实例，存在写读竞争，**不建议**。

## 四、验收要求（沿用交接文档）

1. 首次规划、阶段展开、重试/回退三处都要带上知识正文。
2. 实际发出的请求里能找到知识正文与来源，且与同一个 `requestId` 配对。
3. 知识异常（空库 / 无命中 / 坏文件 / 缺插件 / 超长）不得卡死规划——适配器侧已保证，
   接线处不要再包一层会抛异常的逻辑。
4. 未跑真机就写“待验证”。
