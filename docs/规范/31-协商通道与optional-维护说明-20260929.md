## 二 · 为什么改（不改会怎样）

**断线机理**（逐行核实，非推测）：

```
士兵在 RUNNING 上报（唯一合理时机）
  → RddDetector.tickNegotiation:454  先 takePending 消费回执
  → RddPlugin.requestReplan
  → chain.enterReplanningFromStuck()   要求 FAILED/STALLED
  → RUNNING 不满足 → 抛 IllegalStateException
  → catch → return false
  → ✗ soldierHint 的拼装在后面，永远执行不到
  → 失败后回执已被消费，不可恢复
```

- 旧症状：**「说了好几次指挥官仍照原计划」**
- 额外伤害：`FailureKind` 曾硬编码 `UNKNOWN` → 走 `attempt>=1` 分支 →
  给规划器注入「上一版生成的子步骤被判定不可执行」这句**假话**（上一版其实完全可执行，
  士兵只是不喜欢）→ 且该假话经 `knownFailures` 进入经验召回查询串，召回方向被带偏。

**optional 机理**：`isOptionalFood` 旧逻辑只放行 `group=food` 或 food 组 asset_key。
规划器在别处标的 `optional=true`（如「顺手砍几棵橡木」）**完全不生效** →
判定层重试到耗尽 → `markFailed` → **整条链卡死**，`rdd_skip_optional` 也被同一限制拒绝。

## 三 · 怎么调（参数与开关）

- **无新配置项**。行为由规划器是否在 condition 里标 `optional: true` 决定。
- `renderPreviousPlanForReplan` 的有界参数是编译期常量：
  `REPLAN_PLAN_ECHO_MAX=12`、`REPLAN_PLAN_DESC_MAX=120`（防止规划 prompt 被撑爆）。

## 四 · 依赖与注意事项

1. **`FailureClassifier` 不加 case 会编译失败**（switch 穷举）——这正是工程规范
   「改接口先查消费者」的实际体现。改 `FailureKind` 必须同步查所有 switch。
2. `enterReplanningFromNegotiation` **不把当前二级强转 FAILED**：那会伪造失败事实、
   污染达成判定与埋点。当前二级状态在 `replaceCurrentSubtasks` / `resumeFromReplanning` 时按既有逻辑处理。
3. **协商预算仍会扣**（`REPLAN_COUNTS.merge` 在入口调用之前）。假失败现在少了，
   但若规划器持续返回空 spec，仍会耗尽预算 → 回落停车（既有行为，未改）。
4. **`RddPlanGuard.filterSubtasks` 仍可能吃掉「有变化的计划」**：士兵建议的替代方案
   若恰好是「背包里已有的东西」，会被当冗余删（`RddPlanGuard:81-93`）。本轮未改，留作下轮。
