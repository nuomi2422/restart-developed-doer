## 2 · 两个盲点（你 2026-09-30 亲手点的，直接影响本批地基）

### 盲点 ① · 观测分不清「LLM 在飞」vs「真没动」

- **现状**：`llm_idle_stall` 只看身体/资产变化，**不看 LLM 是否正在飞**。
- **为什么污染第二批**：记忆库/经验库的价值全在「这次尝试对不对」这个判断上。
  **观测本身会误催、乱判 → 沉淀出来的经验就是脏的。** 脏库比没库更糟（32 号文档已记过
  「空库是所有检索失效的根」的同族坑）。
- **你给的处方**：「先花 20 分钟把 ① 补掉（宿主给一个『LLM 是否在飞』的只读快照，
  接进 `ProgressObserver`），否则记忆库会建立在误判之上。」
- **落点（前置项，本批第 0 步）**：
  1. 宿主暴露一个**只读**快照：LLM 请求在飞 / 空闲 / 失败，**带 generation 号防世界代际串味**
     （照抄 `LearnerReviewTool.java:137-143` 已验证的 `ServerLifecycleHooks.getCurrentServer()` 代际校验）
  2. `ProgressObserver` 订阅它，`llm_idle_stall` 增加「LLM 在飞则不判停滞」的**前置门**
  3. **先只加门不调阈值** —— 36 号文档 GLM 5878 字已证明：空转 35.6s < 有效 44.0s，
     **任何纯时间阈值都区分不了「卡住」与「慢」**。真判据仍是「响应到达时看
     `finish=stop && tool_calls=[]`」，但要先排除「在飞」这个假阳性源
  4. **必读的假阳性清单**（36 号文档 GLM 列，逐条对）：生成中 / 长工具执行 / 合法等待 /
     对话轮 / **等规划器批准**（拍醒会产生未授权动作，比卡住更糟）/ 工具拒绝循环 / 轮询相位抖动
- **验收**：构造「LLM 在飞 30s，资产零变化」场景，**不得**触发 `llm_idle_stall`；
  构造「LLM 已返回 `finish=stop` + 无 tool_calls」，**必须**能触发。

### 盲点 ② · 死亡台账纯内存，重启丢账

- **现状**：`RL-6`（掉落回收，死亡不丢账）的台账是纯内存，重启即丢。
- **为什么影响第二批**：第二批要做「经验持久化」，**这个持久化模式没有现成范例可抄**。
  第一批最大的持久化只到 `TaskChain.toJson`。
- **边界定法**：**本批不修死亡台账**（那是第一批的事，且已固化）。
  但**记忆库持久化不许复用内存台账的写法** ——
  必须照 `MemoQueue` 的三件套落盘：`tmp + ATOMIC_MOVE`、**坏文件原地保留不覆盖**、
  **只允许 append 不允许静默截断**（抄 `experience-guard.js:1-18` 的写入闸）。
- **风险等级**：🔴 高。脏经验一旦静默覆盖库，**不可逆**。已列为本批门禁项。
