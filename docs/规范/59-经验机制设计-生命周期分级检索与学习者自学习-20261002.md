## 二、总体链路

```
目标
  ↓
[规划者] 难度分级 D1–D3（★ 2026-10-02 用户定：三档，L2 那套砍掉）
  ↓
列关键点（分难度决定列几个）
  ↓
按关键点检索经验 → 只拿「活的目录」（卡片层）
  ↓
按匹配度 + 风险 + 语义决定展开深度（注入层 L0/L1/L2/L3）
  ↓
生成方案：快 / 稳 / 激进（★ 仅 D3）
  ↓
结合【资产】【关怀任务】【携带器当前状态】选择/调整方案
  ↓
产出一个可执行任务
  ↓
[执行者] 按任务链执行（硬编码世界状态判定完成/未完成）
  ↓
事件链记录（动作 / 工具参数 / 世界状态前后对比 / 成功 / 失败 / 修正）
  ↓
★ 判定要不要记经验 → 命中触发条件才进【候选队列】
  ↓
[学习者] 读该类工作的指导 + 往日成功/失败案例 → 提炼经验草案
  ↓
[质量门] 通过 / 候选待验证 / 驳回 / 替代旧版 / 标记冲突
  ↓
落盘 + 建索引 → 回到「可被检索」状态
```

**关键：闭环的起点和终点都是「事件链」。** 没有事件链就没有经验；经验不回流到事件链就永远不知道它对不对。

## 三、经验的三层边界（用户第 1 问，已确认「很好」）

| 类型 | 回答什么问题 | 例子 |
|---|---|---|
| **执行经验** | 我在什么状态、什么场景、用了什么动作、结果是什么 | 「站在岩浆边挖黑曜石，先铺水再挖，成功」 |
| **规划经验** | 面对什么目标，如何拆关键点、如何排序、如何在快/稳/激进之间取舍 | 「这种目标要先确认水桶数量，再决定走稳还是激进」 |
| **抽象经验** | 跨任务适用的规律 | 「血量低于 8 时不要开掘非关键方块」「夜间不要在开阔地移动」 |

### 已确认的三条边界规则

1. **规划经验和执行经验分开存，但不互相隔离。**
   执行经验提供**事实和结果**；规划经验提供**拆解、排序、取舍**。
2. **规划经验不全是抽象的** —— 它**也包含具体任务上的经验**（用户原话：「规划的经验有特定的计划上的经验，不是说全部都是抽象性的经验，他也有一些实际任务上的经验」）。
3. **抽象经验是跨层可引用的**，不单独成孤岛。

## 四、事件链与候选队列：什么时候才记经验

### 4.1 进候选队列的触发条件（用户「接受」）

| # | 触发 | 说明 |
|---|---|---|
| T1 | 任务成功，且**用了新路线**或**明显提高效率** | 正例，要记住「怎么做到的」 |
| T2 | 任务失败 / 死亡 / 严重受伤 / 资源损失 | 反例，价值最高 |
| T3 | **同一问题重复出现** | 一次是意外，两次就是模式 |
| T4 | AI 发生**计划修正**，且修正后结果明显改善 | 修正本身是经验 |
| T5 | 执行者**主动标记**「这段对以后有用」 | AI 自己知道哪段特别关键 |
| T6 | 规划者发现**现有经验与当前场景冲突** | 不冲突就没人会发现 |
| T7 | **用户明确说这个很重要** | 最高优先级（用户提议，已并入） |

### 4.2 明确**不进**候选队列的

- 普通的每一步走路、挖方块、调工具。
- 这些只作为**事件链的证据**存在，不单独成为经验。

> **理由**：经验库最怕的就是「什么都能记」。走路记一条、挖石头记一条，一万条以后检索全废。
> **事件链是连续的，单步是碎片** —— 只在链条上出现「转折」时才值得提炼。

### 4.3 触发 vs 证明 —— 两条线不能混

用户补充「任务量确实是硬编码的，有世界状态判定」之后，明确区分：

| | 例子 | 能推出什么 |
|---|---|---|
| **触发经验的条件**（够格把经验捞出来看） | 「目标是黑曜石」＋「附近存在岩浆」 | 值得把这条经验拿出来 |
| **证明经验有效的条件**（够格说这条经验是对的） | 「背包黑曜石数量增加」＋「动作记录显示先铺水」＋「前后世界状态」 | 这套动作导致了成功 |

⚠️ **「背包黑曜石 +1」只能证明「采集目标完成」，不能单独证明「铺水导致成功」** ——
没铺水也可能挖到。后者需要**动作记录 + 前后世界状态对比**，否则学习者会把碰巧成功写成必然规律。

### 4.4 世界状态是这个设计的地基（用户原话：「充分利用了我的世界的特性」）

Minecraft 能直接读到：背包数量、目标方块存在与否、生命值、工具运行结果、附近方块（岩浆/水）。
**⇒ 大量筛选可以由程序完成，只有筛出来的少量目录才需要 AI 阅读。这是成本控制的主要来源。**

用户后续会扩展更多世界状态进判定器 / 任务完成判定。

## 五、学习者：怎么写、有没有指导方案、怎么保证质量

### 5.1 学习者的写作模板（固定 10 项，每次都走）

```
A. 这次解决的目标是什么？
B. 触发条件和前置状态是什么？
C. 实际采取了什么动作？
D. 哪些动作导致了结果？
E. 结果是 成功 / 失败 / 部分成功 / 未知？
F. 这条经验适合【执行者】、【规划者】，还是两者？
G. 适用范围是什么？
H. 反例和危险边界是什么？
I. 是否有足够证据写入正式经验？
J. 应该写入哪一层、哪一级？
```

### 5.2 学习者只能输出这五种状态

| 输出 | 含义 |
|---|---|
| `accepted` | 正式经验，进入检索 |
| `candidate` | 保留候选，证据不足 |
| `rejected` | 丢弃 |
| `supersedes` | 替代旧经验（旧版进归档，不删） |
| `conflicts` | 与旧经验冲突，挂起等处理 |

**学习者没有「直接发布」的权力**（用户第 3 问「接受」）—— 发布由**质量门**决定。

### 5.3 ★ 学习者也学「怎么写经验」（用户第 4 问的关键补充）

用户原话：「学习者在写经验、发送编译请求、写任何携带器的时候，他都会有自己带的一个成功案例和失败的案例，就是往日的案例，每个都是独立管理的。」

**⇒ 设计成：每一类写作工作有自己的「指导 + 案例库」，互不干扰。**

#### 三类写作工作（各自独立管理）

| 工作类型 | 指导内容 | 案例库回答什么 |
|---|---|---|
| **W1 提炼经验** | 怎样从完整事件链提取条件、动作、结果 | 「上次这样写的结果如何」 |
| **W2 编写携带规则** | 怎样选触发条件，避免误触发和重复提示 | 「这条规则上次有没有一直乱触发」 |
| **W3 提出能力缺口** | 怎样描述现有能力做不到什么，并提供证据 | 「这个缺口提上去后来修了吗」 |

#### 两类「成功」必须分开（否则会自欺）

| 案例类型 | 什么算成功 | 什么算失败 |
|---|---|---|
| **游戏经验案例** | 在记录的条件下完成目标，代价和风险都有记录 | 死亡、目标未完成、代价超预期 |
| **学习者写作案例** | 产物**通过质量门**，并在后续使用中得到支持 | 缺证据、适用范围写大了、触发错误、使用后产生反例 |

> ⚠️ **「成功写入文件」不等于「写出了一条好经验」。** 这是必须切断的错觉。

#### 迭代与人工审核

- **经验是迭代版本管理的**，保留版本、来源、变更原因。
- **偶尔需要人工审核** —— 用户明确说「监测台可以审核，所以这个不用在意，后面会加上去」。
  → 这一条依赖 `60` 的监测台可验证化设计。

### 5.4 ⚠️ 编译请求的硬边界（对应 RL-19）

用户提到「学习者发送编译请求」。**RL-19 的意图是：游戏内只有学习者能提交改码请求，
干活/规划 AI 只能往待办目录写一条，不得直接调 `selfcompile_request`。**

> ⚠️ **但 RL-19 现在是 🟡「源码已改、运行时未生效」**（commit `92168ea4` 改了 3 处源码，
> **jar 没重新部署**；见 `30`）。**它现在是「靠工具描述劝导」，不是机制拦截。**
> ⇒ 本设计里「实际编译走外层」这一条，**目前靠约定，不靠机制**。这是待补的债。

**⇒ 学习者可以整理【能力缺口】和【改进建议】（W3），实际编译交外层工程流程执行。**
**⇒ 学习者对自身指导的修改，也必须作为新版本候选过质量门 —— 不能自行降低验收标准。**

## 六、质量门：字段清单与通过条件

### 6.1 正式经验的必备字段（用户「3 质量门」接受）

```
experienceId
experienceType       planner / executor / abstract
taskFingerprint      任务链指纹
sceneFingerprints    场景指纹（可多个）
preconditions        前置条件
actions              动作序列
outcome              结果
evidenceRefs         证据引用（必须能指回原始事件链）
successLevel         成功程度
riskLevel            风险等级
confidence           置信度
scope                适用范围
counterExamples      反例
createdFrom          来源（哪条候选事件）
supersedes/conflicts 与旧经验的关系
```

⚠️ **没有 `evidenceRefs` 的内容只能是候选或推测，不能进入强注入区。**

### 6.2 质量门通过条件

- 至少**一次完整事件链**；
- **或** 多次独立复现；
- **或** 一次高价值失败 / 死亡；
- 经验正文与原始证据**不能互相矛盾**；
- 必须写清**适用条件和不适用条件**；
- **不能只写「应该注意安全」这种不可执行句子。**

### 6.3 ★ 验证要求（用户第 4 问）

**默认需要验证，不能把一次记录直接当成普遍规律。**
**★ 验证次数阈值 = 3（用户 2026-10-02 定：「默认三次。没别的。」）**
即累计 3 次真实成功才算通过；高价值失败 / 死亡类沿用 §6.2「一次即算一次完整证据」的例外。
（与代码现状一致：`ExperienceStore.GENERALIZED_THRESHOLD = 3`。）

### 6.4 ★ 待验证经验规则（用户答「允许」）

用户确认：**一次成功但尚未完成验证的经验，允许进入检索目录。**

```
1. 先过【基础质量门】 —— 允许待验证 ≠ 跳过质量检查
2. 目录里必须明确标注：待验证 / 支持次数 / 反例次数 / 适用条件
   —— 不能显示成已验证经验
3. 分级展开照常可用 —— 规划者和执行者都能主动查看，并知道证据强弱
4. 高风险操作【不能仅靠这条经验决策】 —— 仍需满足现有安全条件
5. 后续结果回流到原经验及其版本：
   成功 → 增加支持
   失败 → 保留反例
   由质量门决定【升级 / 缩小适用范围 / 撤回】，不能只累计成功
```

### 6.5 生命周期（完整链条）

```
事件发生
  → 候选队列
  → 学习者（读该类指导 + 往日成功/失败案例）提炼
  → 基础质量门
  → 待验证经验
  → 分级检索与使用
  → 结果回流
  → 验证升级 / 修订 / 缩小范围 / 撤回
```

## 七、规划者：思维过程、难度分级（D1–D3）、三条战略线

### 7.1 ★ 规划者的「思维过程」要落成可检查的记录

用户原话：「给了一个目标之后开始分难度……然后他就开始列举，列举他这个的关键点，列举完关键点之后，然后他就会去收资料，搜资料。」

**⇒ 不要让思维过程只活在模型内部。要落成结构化规划记录：**

```
难度等级 + 判断依据
关键点清单
查了哪些经验（指纹列表 + 命中/未命中）
缺什么资产
候选方案（快/稳/激进）
选择哪个 + 为什么
```

**这样才能检查「计划为什么产生」，也给学习者留下可用证据。**

### 7.2 ★ 难度分级 D1–D3（2026-10-02 用户定：三档，L2 那套砍掉）

> 用户原话：「L2 没必要存在。三个等级就够了。核心原则：小任务根本没必要走我们这边，
> 只有长任务才走这套。短平快的交给执行 AI 自己，它自己也有脑。」

| 等级 | 做什么 | 检索成本 |
|---|---|---|
| **D1** | **根本不需要划分** —— 小任务直接交给执行 AI，不走规划者这套 | 无 |
| **D2** | 稍微复杂一点，**直接生成一个任务**就行（简单检索即可） | 低 |
| **D3** | 超级难的任务，**需要计划很远很远**：完整思维过程 + 资料收集 + 三条战略线 + 动态重规划 | 高 |

**⇒ 三条硬约束（写进代码判据，不许含糊）：**

1. **D1 不进规划流程。** 短平快任务由执行 AI 自己处理 —— 「它自己也有脑」。
   规划者对 D1 任务的正确行为是**不介入**，而不是「走一遍简化流程」。
2. **D2 只出一个任务**，不出三方案、不要求列全关键点。
3. **只有 D3 才付得起规划的钱**（生成方案 = 花钱）；D1/D2 一律不出三方案。

**⚠️ 记号改名（2026-10-02）**：难度轴原来叫 `L0–L4`，与 §8.1 **注入分层**的
`L0–L3` 撞名。本文件里 L2 既指「难度第二级半」又指「注入的步骤层」，
是本轮 4 个 TBD 里最大的歧义来源。⇒ **难度轴统一改叫 `D1/D2/D3`**，
注入轴保持 `L0–L3` 不变。代码里也请用 `difficulty` 字段名，不要再用 `level`。

### 7.3 ★★ 三条战略线只在 D3（用户明确要求）

> 用户原话：「应该是在第三级各种更高的能力上才出现，不应该让玩家浪费这些钱去生成一个高质量任务，
> 只有在劫难的时候才。」

**⇒ 简单任务和支线任务不该浪费钱和时间走满流程。**

#### 7.3.1 ★★「10 个步骤」与「3 条线」是两码事（TBD-4 用户亲自纠正）

> 用户原话：「我从来没说过『裁剪规则』。你说的那 10 个和 3 条根本不是一回事：
> 那 10 个是步骤（sub-steps）。那 3 条是 3 个整的任务线（三种不同的战略）。
> 流程是：我列举步骤之后，要分成三条线——选三种不同的战略。别把步骤和战略混在一起谈。」

```
列步骤（sub-steps）        ← 数量由难度定，10 个左右只是常见量级，不是阈值
     ↓
分成三条线 = 三种不同的战略   ← 快 / 稳 / 激进，各是一条完整任务线
```

**⇒ 之前文档里写的「候选超过 3 条裁剪到 3 条」是错的，已删除。**
正确的流程是**先列步骤、再按步骤组合出三条不同的整线**，不是从候选里挑 3 条。
每条线都要能独立执行到底（有它自己的步骤序列），而不是「同一条线的三个长度」。

⚠️ 实现时不要写成「把候选数组 slice(0,3)」—— 那是把**步骤**当**战略**，
产出的三条线会高度重叠，规划者等于只拿了一个方案。

### 7.4 每套方案必带的字段

```
预计时间
资源消耗
风险
失败后果
关键依赖
可中断点
恢复方案
```

### 7.5 规划者还要看：资产 / 关怀任务 / 携带器

用户原话：「他把把自己的资产然后传输过去……这个 AI 又会看到资产，又会看到很多的……我有一个我已经选好的这些是经验资料，然后它就会开始生成 3 个任务。」

**⇒ 规划者不是一成不变的，每次都要看当前 AI 的状况：**

- **资产**（用户已有资产传递机制）
- **关怀任务**（没吃饱、食物不足等自动注入的提示）
- **携带器状态**（当前携带的经验 / 日后可携带任务）

## 八、分级注入与多线路触发

### 8.1 四层展开（用户第 6 问「同意」）

| 层 | 内容 | 谁看 |
|---|---|---|
| **L0 目录层** | 标题、任务指纹、适用场景、成功率 / 风险 | **默认给 AI** |
| **L1 摘要层** | 摘要、前置条件、结果、关键警告 | **默认给 AI** |
| **L2 步骤层** | 步骤、关键节点、替代方案 | 匹配度高 / 风险高 / 遇冲突时展开 |
| **L3 证据层** | 完整事件链、原始证据、失败过程 | 同上，或人工审核 |

**执行者默认只拿 L0/L1。**

### 8.2 多线路并行检索

先按多条线路并行跑，再合并、去重、排序：

```
任务指纹 / 阶段指纹 / 场景指纹 / 目标材料或目标实体
当前资产 / 风险指纹 / 历史失败 / 当前携带器触发条件
```

### 8.3 ★ 分层活触发（用户第 6 问的补充，最关键的成本设计）

用户原话：「最薄的最容易触发的一层，加到里面之后再分级第二级，再触发各种各样的分级的多条线路，活的触发加上多条线路，触发之后再根据匹配度给出活的目录，然后 AI 再根据语义选择深的，就模拟了人类的这些触发条件。」

```
【第一层：最薄最易触发】—— 不读经验，只读世界状态
   检测：背包数量 / 目标方块 / 生命值 / 附近岩浆 / 工具参数
        ↓  命中某条线路才继续
【第二层及以后】—— 按线路检查更具体的条件
   ├─ 目标线路：正在采集黑曜石
   ├─ 环境线路：附近有岩浆
   ├─ 移动线路：路径经过危险区域
   └─ 资产线路：有无水桶、工具是否合适
        ↓
【汇合候选经验 → 匹配排序 → 同一经验包去重】
        ↓
给 AI 少量、随当前情况变化的经验【目录】
        ↓
AI 按语义选择展开深度
```

### 8.4 ★ 一个场景可以命中多条线路（用户明确举例）

挖黑曜石同时可能触发：
- 「前面执行了移动」→ 查走路路径旁边有没有黑曜石 / 岩浆
- 「挖掘指向参数是黑曜石」→ 查这个目标的已知方案
- 「环境有岩浆」→ 查防护措施
- 「工具有没有」→ 查水桶 / 钻石镐

**多条线路也可以指向同一个经验包** —— 例如「目标线路」和「环境线路」同时命中「岩浆边挖黑曜石先铺水」。
**⇒ 最终只展示一次，并注明「这次为什么推荐它」。**

### 8.5 注入时机（省钱的另一半）

- **没命中就不额外注入。**
- **状态发生相关变化时才重新检查** —— 避免每一步都重复读同一份经验。
- 目录必须**随当前情况变化**（用户反复强调「活的目录」）—— 不是一份固定清单。

## 九、携带器与关怀任务

### 9.1 携带器：现在携带经验，日后携带任务

- 现状：携带器携带**经验**（`<carry>` 已进上下文，实测 118/118）。

### 9.2 关怀任务与支线任务

- **关怀任务**：AI 没吃饱、当前食物供给量不足等状态 → **自动注入提示**。
- 特点：**可以直接运维**（不经过完整的规划流程）。
- 用户原话：「就会出一个**支线任务**，看一下能不能拿点食物吃之类的。」
- ⚠️ **术语已定（用户 2026-10-02 亲自纠正）**：口述里的「**志愿任务**」= **支线任务**。
  本工程此前叫「浮现任务」的支线路由，就是 `LocalRepairTask` + `RddRepairDispatch` 那条路
  （第一批已摘入，见 `25` 号文档的同名备注）。
  **⇒ 文档里统一叫「支线任务」，不再用「志愿任务」「自愈任务」。**
- **现状：当前的任务链已由另外一个 AI 去执行了**，本份文档不展开任务链细节（用户明确说「任务链那部分你不用太在意，关键是我们的经验和思维注入」）。
