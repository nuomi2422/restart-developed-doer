## 一 · 候选 1：`goto` 无法表达「走到已知坐标的那一个方块」

### 实测证据

```
execute_tool rejected tool=goto
reason=invalid arguments: block means 'walk to the nearest one of these' — no coordinates with it.
       To reach one specific block you know the position of, goto its location (x+z) and interact there.
args={"block":"minecraft:spawner","x":-878,"y":14,"z":-908}
```

### 【驳回】我原方案 A（允许 `block` 与坐标共存、坐标优先）

**GLM 的理由（我采纳）**：
- **语义坍缩**：`{block, coords}` 到底��「coords 附近找最近的 spawner」（这是真实存在的合理需求）还是「coords 处的那个」（instance 语义）？两个真实需求挤进一个参数形状，行为由「带没带坐标」这个隐式开关决定，**出错时无法从参数形状归因**。
- **静默回退的语义漂移（最危险）**：坐标处不是 spawner 时（模型记错/世界变了），工具若退回搜索，模型以为去的是那个笼，实际被拉到**另一个**，后续 `interact` 作用在错误对象上 —— **任务链层面最危险的一类失败，因为它不报错**。
- **纠错信号丢失**：互斥报错本身是清晰的教学脚手架（见下），放宽成「善意解读」后错误用法不再被拒而是被模糊满足。
- **A 会遮蔽候选 2 的 bug**：放开后模型不再走裸坐标路径，悬空判定缺陷**被绕过而不是被修**。

**Codex 的理由（采纳）**：`block` 被静默忽略直接违反 RL-13「工具契约不做假承诺」；且现有执行层语义已不一致 —— 注释说「实心坐标目标应站到方块旁边」，`blockCompiled()` 实际返回 `standOn()`（`MoveToCompanionTask.java:275`）。

**qwen 的理由（部分采纳）**：`{block:"iron_ore", x:0, z:0}` 有歧义；模型若习惯性带坐标会退化成「局部搜索」，失去全局最近语义。

### 【采纳】先做 GLM 指出的那个最便宜的验证（它决定整条修复路径）

> **裸坐标 `goto` 拿到 `y=14` 时，工具到底怎么处理？**
> 接受并用于路径规划 / 接受但忽略 / 拒绝？

- 若 **y 被静默忽略** → 候选 1 的最小修复是**「让 y 生效」**，而不是动 `block` 参数。
- 三家都指向这一条，**这是本轮第一个要查的事**，成本极低。

### 【采纳 GLM 的关键观察】模型其实学会了，报错推荐的替代方案才是死路

我原本写「模型用错」，GLM 指出我漏了证据：**t3/t5 两次失败的目标已经是裸坐标 `(-878,14,-908)`** ——
说明模型被拒后**确实按报错指引改用了坐标方式**。互斥校验 + 那句报错**作为教学信号是起效了的**。

所以 GLM 的定性是：模型那半（把上一个 find 工具返回的对象形状原样回填）是「不算错但也不算没有正确表达方式」；
**真正的缺口是——报错推荐的「goto its location (x+z)」漏了 `y`，而裸坐标 goto 到悬空点正好撞上候选 2。**
**契约推荐的替代方案本身对悬空目标不可用，且文案在教模型忽略 Y。**

> **「忽略 Y」就是 `closeEnoughToSucceed()` 只算水平距离的来源** —— 不是巧合，
> 是同一个设计假设的两面：「目标方块总是可以站在旁边水平接触的」。刷怪笼悬空打破了这个假设。

### 【采纳 GLM 的统一视角】候选 1 和候选 2 是同一个病的两极

- 候选 1：`goto` 参数空间**过窄**（拒绝有意义的组合）
- 候选 2：`goto` 参数空间**过宽**（接受 y 但水平判定让 y 失效，悬空目标被静默投影到地面那根柱子）

### 定案

| 动作 | 决定 |
|---|---|
| 先验证裸坐标带 y 的行为 | **做**（GLM 的验证项，决定后面一切） |
| 方案 A（坐标优先） | **驳回**（三家一致） |
| 方案 C（只改文案） | **驳回**（GLM 论证了推荐路径本身是死路，C 单独 provably 不够） |
| 方案 D（instance 拆给 `interact`） | **本轮不做**（面太大，要动 `interact` 的目标绑定；留作下轮） |
| **Codex 的受限 typed A**（`block`+`x+y+z` = 新 `BLOCK_AT` kind） | **采纳，但排在 y 验证之后** |

理由：Codex 的方案内部新增一种 typed kind（不是让两个字段互相覆盖），保持
`block` 单独 = FIND / `x+z` = COLUMN / `x+y+z` = 精确格 三种旧语义**完全不变**，
只新增第四种；坐标处实际方块 ≠ 请求的 `block` 时**返回明确契约错误，不静默回退**。

## 二 · 候选 2：悬空目标反复失败

### 【修正我自己的错误】`24.2 blocks` 不是容差半径

我原以为「容差是水平面 24 格」。Codex 与 GLM 都否掉了这个说法：

- **Codex**：对 BLOCK 类，代码用的是**三维欧氏距离**（`MoveToCompanionTask.java:511`），
  目标与同伴 x/z 相同、y 差 24，加方块中心偏移 ≈ 24.2。
  **但 `closeEnoughToSucceed()`（`:493`）对 BLOCK/COLUMN 用的是水平距离。**
  → **同一份任务同时用了三维「剩余距离」和二维「接近成功」，几何定义自相矛盾。**
- **GLM 补了判别方法**：grep 报错模板里这个数字的插值来源 —— 是「容差常量」还是「pathfinder 返回的 gap」。
  它赌后者（垂直差 24 + 约 3 格水平分量 = √(24²+3²) ≈ 24.2）。

**这个数字真正的问题不是它错了，是语境杂交**：一个由垂直主导的三维距离，
被塞进一个由水平语义统治的判定语境里，后面紧跟一句准成功的
`arrived at location x=.. z=.., standing on the ground at y=..`。
**模型读到的合理解读是「我已经到了附近，有什么东西暂时挡着」→ 45 分钟后重试，再吃同一句话。**

### 【驳回】派活前就拒绝不可达目标（我原提法 + qwen 的提法）

**GLM 反对，理由我采纳**：
- 可达性在派活前是**猜**，在寻路失败时是**知**。
- 派活前预拒要么贵（全量寻路预演）要么不准（启发式）。
- **不准的预拒是假承诺的镜像**：说「不可达」但其实换个路线、或者之后拿到垫路权限就通 —— **这恰恰是 RL-13**。
- 派活那一刻寻路器手里**没有**「最近可达点 / 垂直差 24 / 缺垫路权限」这些事实。
- **划界**：RL-18 是对任务链构造方的要求，不是工具层的。
  和我划的「经验没注入是注入层的事」同构 —— 「这个任务该不该派」是构造层的职责，
  工具层的职责是**执行 + 如实汇报**。工具层预拒是越界抢职责。

**Codex 独立得出同一结论**（不要全局 3D，按目标类型分层）。

### 定案

| 层 | 动作 |
|---|---|
| 失败分类层 | 结构化失败原因：`{目标, 最近可达点, 水平距离, 垂直差, 缺失能力}`。区分「水平受阻 / 垂直不可达 / 需垫路未授权」 |
| 文案层 | **删掉 `arrived at location` 这种完成语义**（`:570`、`:575-576`），改成 `水平位置已到达；目标在正上方 24 格` |
| 文案层 | 加幂等提示：同目标+同原因第二次出现时，报错开头明说「这已是第二次相同失败，重试无效」—— **摆出重复这个事实，但策略决策留给模型** |
| 到达判定层 | **到达判定必须与导航目标用同一个谓词**（按目标类型分层），但**不全局改 3D** |
| 类型分层 | COLUMN = 水平 + 已解析地表（`MoveToCompanionTask.java:249` 已有，**不要抹掉**）／BLOCK_AT = 目标方块的可交互邻接 + 三维可达性／精确格 = 三维／FIND = 最近候选的邻接 |

> **不全局改 3D 的理由**：会误伤「走到目标 XZ 的地面」「走到矿脉脚下」这类**本来就该忽略 Y** 的用法
> —— 实测 YLEVEL（只给 y）从 y=-13 → +4 → +14 全部 `ARRIVED-IN-PLACE`，爬 39 格高度而**圆石始终 48 没动**，
> 证明升降走的是非搭柱路线。全局 3D 会让这些全变成「不可达」。

### 【采纳 GLM】幂等检测其实是我上轮该做没做的事

GLM 说得很准：这跟我在 10-01 加的 `ToolCallLoopWatch` 是同一类东西，
但那个挂在**拒答漏斗**上，而 `goto` 的失败走**异步 `task_finished` 事件**，根本没经过漏斗
（= 我记的 Bug B）。**本轮把幂等检测挂到 `task_finished` 的失败分支上。**

## 三 · 候选 3：上下文（顺序排反了，改正）

### 【采纳】先做 `find_tools` 用完即弃（2,177），不是砍常驻工具（3,072）

GLM 的理由：
- 它是**一条规则就能吃掉的最大单笔**，且**不需要任何使用率数据**。
- **我把顺序排反了**：砍更多常驻工具 → 让 `find_tools` 展开更大 → 用完即弃反而更紧迫。

### 【采纳 GLM】不要真删历史，改成「组装时重写 + 原件留外部日志」

四个坑，GLM 列的比我全：
1. **恢复链路必须闭环**：模型调了不在 `tools[]` 里的工具，OpenCode Go 通道是硬拒还是转发给模组？
   硬拒 → 报错必须指引「去 find_tools」；宽松转发 → 模组分发器承担「未知工具 → 提示 find_tools」责任。
   **这个实现细节决定用完即弃的成败。**
2. **assistant 消息里的复述会悬空**：模型可能复述过工具定义片段。只删工具消息不删复述 →
   「模型说过一半、另一半没了」——**比全删更误导**。
3. **审计性**：删历史 = 复盘看到的不是模型当时看到的。在我这套观察者方法论下这是真代价。
4. **防瞎填的正确姿势**：摘要里保留**参数名列表**（不含完整 schema），模型知道形状；
   真要调用时靠严格校验 + 报错回填完整定义兜底。

### 【采纳 GLM 的量化盈亏平衡点】常驻工具不能拍脑袋砍

- 常驻成本 ≈ **279 token/工具/请求**（3,072 ÷ 11）
- `find_tools` 一次展开 = 2,177 token；若一次展开多个，**单工具展开成本可能高于常驻**
- 用完即弃下每次使用付约 1~2 轮驻留
- → **使用率低于 ~50% 的工具延迟化才划算；高于这条线是负优化**（token 反增 + 多一轮往返延迟）

**所以名单必须从埋点拉每个工具的调用频率来定，不能凭「低频」二字。**
`tools.jsonl` 已有 per-tool 调用计数（之前分析器用过），可直接拉。

### 【采纳 GLM + qwen】砍 `tools[]` 比砍 system prompt 安全

- **可再生性不对称**：工具 schema 随时能靠 `find_tools` 重新展开，丢了有低成本找回通道；
  system prompt 里的人格/操作纪律/技能表**没有找回通道**，行为漂移后没有任何工具调用能恢复它。
- 架构本来就是「索引常驻 + 详情延迟」设计（`<deferred_tools>` 已存在），
  **11 个常驻是这个设计的例外遗留，砍它是朝架构本来的方向走，不是新发明。**
- **system prompt 排最后**（qwen）：要动只砍冗余描述，不动核心规则。

## 四 · 候选 4：output 占 27%（截图抓到的）

**实测**：68 次调用，completion 合计 **137,848**，平均 **2,027**、中位 1,725、最大 **12,102**，
占同窗口 input 的 **27%**。极端例子 `compl=3360` 而 `tool_calls=[todowrite]`。
截图确认聊天栏被 `RDD:` 散文刷满。

**这是原版模型在违反原版 system prompt 的明文要求** —— `ENTITY_PROMPT` 里写着
`Be capable and concise: get the owner's intent done, then say what happened in a few words.`

### 【驳回】只改 system prompt 加强措辞（我原提法）

Codex：不够。而且**事后截聊天文本不省钱** —— 如果这些 token 已经生成并计费，
渲染层截掉只是不刷屏，账单不变。

### 定案（三层，按 Codex）

| 层 | 动作 |
|---|---|
| **测量（先做）** | 确认这 2,027 completion 是 `content` 还是 `reasoning_content`。若是 reasoning 且通道支持独立预算 → 限它；否则调 `max_tokens`，并监测 `finish_reason=length` 与工具调用截断率 |
| **协议层** | 解析完整响应后再渲染。**存在 `tool_calls` 时丢弃长散文，只保留固定一句派发确认**（如「已开始前往目标，完成后通知你」）。**绝不对原始 JSON 或流式工具调用做字符截断** |
| **提示词层** | 保留「调工具时不叙述、完成后短答」，但只当**软约束** |

**可观测性不丢，反而变好**：工具调用、`task_id`、`task_finished`、失败原因、监测台日志
才是可靠可观测性。Codex 指出「有 tool call 就完全不输出」会让玩家不知道任务是否被接受
→ 保留**固定确认句**，而不是保留模型自由散文。

**必须避免的失败模式**（Codex 警告）：`max_tokens` 压太低 → 工具 JSON/参数被截断 →
重试 → **请求变更多**。所以**先量 token 分布和 `finish_reason`，再设预算**，不能直接把上限砍到几十 token。

## 五 · 跨候选的排序原则（GLM 提出，采纳为本轮纪律）

> **参数校验的严格性，决定了你能对上下文管理多激进。**

- 用完即弃的前提是校验能拦住瞎填；
- 互斥校验的存在本身就是模型学习契约边界的脚手架（候选 1 里它**起效了**）；
- **宽容的参数解读 + 激进的历史删减同时上 = 同时抽掉模型的两类纠错信号，漂移会变得不可见。**

**本轮排序（GLM 给的，我采纳）**：

```
1. 候选 2 的报错归因      ← 正在让模型空转烧轮次
2. 候选 1 的 y 语义       ← 先验证裸坐标带 y 的行为
3. 候选 4 的 output 三层  ← 先量 content vs reasoning
4. 候选 3 的 find_tools 用完即弃（2,177）
5. （下轮）常驻工具延迟化 —— 必须先拉 per-tool 使用率
6. （下轮）候选 1 的 BLOCK_AT typed kind
```

**明确不做的**：D 方案（动 `interact`）、全局 3D 到达判定、派活前可达性预拒、
拍脑袋砍常驻工具数量、动 system prompt 的核心规则。
