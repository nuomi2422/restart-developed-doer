# 13 · 埋点（第八系统）与监测台链路

> 用户要求：关键路径埋 debug **接到监测台**（让用户看见整条线路）；把埋点打到**独立日志区域**（不混）；链路要**讲清是什么**，以后一看就知道在哪。

## 一、埋点系统（第八系统）现状（真实源码）

- 组件：`RddInstrumentation`（Nuemen `plugins\rdd`）。
- 输出：`<实例>\config\numen\monitor\instrumentation.jsonl`（**独立日志区域**）。
- 每行：`schema_version + game_time + type + data`；fail-silent、自带 dropped 计数、限流、6MB 轮转。
- 事件类型：`starvation_death / death / loop_detected / repeat_gather / resource_waste / asset_mismatch / recovery_failed / instrumentation_change`。

## 二、监测台链路讲解（各日志是什么）

| 文件（`config\numen\monitor\`） | 是什么 | 谁写 |
|---|---|---|
| `rdd.jsonl` | 任务链事件（`taskchain_snapshot/dependency_met/primary_waiting/subtask_*/planning_*/asset_snapshot`） | RddPlugin/RddMonitor |
| `instrumentation.jsonl` | **埋点（第八系统）** 六事件 | RddInstrumentation |
| `ai.jsonl` | AI 回合（`turn/tools/convo_msgs`） | Numen AI |
| `tools.jsonl` | 工具调用与结果 | 工具层 |
| `context.jsonl` | 注入给 AI 的上下文（含 `<rdd>` instruction） | 上下文层 |
| `state.jsonl` / `events.jsonl` | 状态快照 / 世界事件 | 状态层 |

**链路**：规划请求/检测/执行/死亡 → 各层写 JSONL → 监测台（8776）聚合展示 → O 巡检（`redline-watch.js`）+ 用户旁观。

## 五、★ 埋点先行原则（探针优先 · 用户 2026-09-28 定）

> 用户原话意旨：**架构时（尤其贵模型）想到了一些边界问题，但更好的做法是先进游戏验证，而不是把所有防护都写出来、一直停在架构阶段。**
> → 那就**先埋一个探针 + 统一记录**：真出问题会**立马看到**；没问题就**没写什么代码、不用担心**；除非以后真又出问题，才去写修复。

**核心：把"猜出来的边界"从"写代码"降级为"埋探针"。** 探针是廉价观测，推测性防护是昂贵死代码。

**流程**：
1. **规划/架构期**推演出某边界风险（但**未在真机复现**）→ **默认不写防护代码**。
2. 在**第八系统**（`RddInstrumentation` → `instrumentation.jsonl`，**独立日志区**）加一个**只读探针**：
   记清 `入口 / 输入 / 分支 / 命中条件 / 输出`（对应用户"链路要讲清是什么"）。
3. 探针**接入监测台「埋点」分页**（`13` §四 已通）→ 一旦命中，**用户与 AI 当场可见**（带时间/同伴/上下文）。
4. **真命中了** → 拿**真实证据**（而非推测）去写**最小修复** + 补**边界/压力测试**（`01` §三.3）。
5. **一直没命中** → **零代码成本**，系统不背"为臆想问题写的死代码"。

**例外（必须预先防护，不能只探针）**：
- **基准红线 RL-1..8**（见 `01` §四）；
- 会导致**死亡 / 不可逆损失 / 生产安全**（如装备不足硬派、绕过风险门）的路径。
- 这些按规范**照常预先防护**，探针只作补充。

**与工程规范的关系**：这是对 `01` 第 4 条「关键路径同步埋 debug」的**扩展用法**——
不只是"给已写的代码埋点"，而是"**用埋点代替早期过度设计**"。与"先进游戏验证、别停在架构"（`10` 总流程）一致。

> 归类：模块级(Bounded) 方法论；落点 `01`（第 4 条）/ `10`（流程）。
