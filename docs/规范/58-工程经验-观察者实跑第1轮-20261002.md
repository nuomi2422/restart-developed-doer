## 一、★★ 写码链：编译「静默死亡」的真凶（最费时间的一条）

### 症状
`run-mutation.ps1` 连续 4 次死在 `:api:neoforge:compileJava`，存活 18 / 35 / 38 / 42 秒，
**`phase-build.log` 每次字节数完全一致（2408）**、无任何 `error:` 行、`jar`/`deploy` 目录全空。

### 两个叠加的坑

**坑 1：`Start-Process` 拉起的进程树会被调用方 shell 回收。**
真凶不是 OOM（把 `-Xmx3G` 降到 `-Xmx1600m` 照样死）、不是代理 7897、不是磁盘、不是事件日志
（`hs_err_pid` / WER / System 2004 / 2019 全部为空 —— **因为是正常终止，不是崩溃**）。

**解法：需要活过 ~40 秒的 detached 进程一律走计划任务**
```powershell
schtasks /delete /tn rddbuild /f
schtasks /create /tn rddbuild /tr "powershell.exe -NoProfile -ExecutionPolicy Bypass -File `"<wrapper>`"" /sc once /st <+2min> /f
schtasks /run /tn rddbuild
```
短任务（<30s）用 `Start-Process` 没事。

**坑 2（更隐蔽）：`build-jar.ps1` 用 `*> $logFile` 吞掉 javac 报错。**
⇒ **编译错误和「进程被杀」表现完全一样。**

**判据三条（同时成立 = 大概率是编译错误，不是被杀）**：
1. `phase-build.log` 停在某个 task 名上
2. 里面没有任何 `error:` 行
3. `jar` / `deploy` 目录是空的

**定位手法：回退改动做二分** —— 先退一个文件试，比查代理 / 内存 / 事件日志快一个数量级。
我靠这招 10 分钟定位，实际病因是我自己两个编译错误：
- `CompactSplit` **没有 `estimateTokens(String)` 重载**（只有 `estimateTokens(Msg)` 和 `estimateTokens(List<Msg>)`）
- `slimExpanded` 声明成包级私有却被跨包调用（同文件另一个方法写了 `public`，这个忘了）

### 配套判据
- **`javap -c` 看不到 `+` 拼接的字符串**（编译成 `invokedynamic makeConcatWithConstants`）→ **必须 `javap -v` 查常量池**
- JDK 两个位置：编译用 `D:\rdd\tools\jdk21\jdk-21.0.11+10`（`gradle.properties` 的 `org.gradle.java.home`），`javap`/`jar`/`java` 在 `D:\bin`
- 解 jar **必须保留包目录结构**（先 `Set-Location` 到解包目录再 `javap -cp $out`），压平会静默无输出
- `run-mutation.ps1` 的 `-Module` 必须是 `group:name`；`rdd-core` 在仓库根目录不符合，
  **但只需构建 `plugins:rdd`** —— 它的 `build.gradle` 有 `from({ project(':rdd-core').sourceSets.main.output })`，rdd-core 的 class 会被打进插件 jar
- 本机 7,916MB，**游戏 1,753MB + `-Xmx3G` 不能同时跑** → 编译前先优雅关游戏

## 三、★★ 成本分析的两次自我推翻（方法论教训）

### 推翻 1：候选 4 的前提是错的
计划阶段写「output 占 input 的 27%，聊天被散文刷满」→ **实测 `output/input = 11.2%`**，可见散文只占 output 的 **0.8%**（中位 **1 token**），94.6% 是埋点排除的 reasoning 残差。钱在 prompt（**8.9 : 1**），三层方案全部落空。

### 推翻 2：「压缩频繁、压得过头」是误判
我从 prompt 序列的「掉幅 >30%」数出 22 个压缩点、每次丢 9,821 token（占 172 次调用的 12.8%）。
**查日志直接证伪**：`latest.log` 里 `auto-compacting` / `compaction started` **一次都没有**，而 `replay` 限流日志有 **145 条**。
根因：`modelWindow()` 返回 `providers.json` 的 `contextWindow`，`ctx: 1000000` ⇒ 自动压缩闸门触发线 **987,000 token，永不触发**。
**真实图景**：`replayWindowTokens=20,000` 才是硬约束，锯齿是限流器的正常行为，**不额外花 LLM 调用**。

### 方法论（比结论值钱）
1. **先 dump 埋点看结构再写统计** —— `llm_response` **没有 `usage` 对象**且 `excluded:["credentials","hidden_reasoning"]`（reasoning 只能算残差）；`llm_request` **没有 `promptTokens` 字段**（prompt 只能自估）。我第一次照 `latest.log` 的 `tokens=X/Y` 解析就猜错了字段名。
2. **下结论前先确认那个现象的真名** —— 「掉幅」到底是压缩还是限流，日志一查就分清。
3. **A/B 必须严格** —— 拿 `latest.log` 里相邻两回合比是**噪声**（会话长度不同）。我一度报「prompt −19%、延迟 −89%」，严格 A/B 后是 **+0.6%**。正确做法：按游戏重启时间切 `context.jsonl` 全部 `llm_request`，比**中位数**。

## 四、★★ 任务链判定失灵（RL-22）：`rdd_submit` 不拍 acquire 基线

### 事故
AI 13:11:41 做出石镐、13:11:52 正确汇报「正好满足 done_when」→ 13:12:45 系统判 **`subtask_failed` / stalled after nudges** → 13:12:46 `subtask_retry` → **逼她又合成一把**（背包 2 把）→ 依然不成功。3 分钟 prompt 从 9,820 涨到 25,027。

### 根因（纯代码推导，100% 确认）
```
HardCodedEvaluator.java:74-78   if (baseline == null) return false;    ← 无基线 = 恒 false
TaskChain.java:313-324         startCurrent() 不拍基线（activateCurrent 才拍）
RddSubmitTool.java:80          调的正是 startCurrent()                  ← 这条路永远没基线
```
**`mode=acquire` 走 `rdd_submit` 永远是死条件。**

### 用户比我想得准
> 「他的检测不是硬指标吗？只要背包里有一个石膏，不就可以成功了吗」

**判定器本来就有这条硬指标**（`counts.get(key) >= minimum`），**是我派活时选错了 `mode`**。
acquire 的本意是「防假完成」（接活前就有一堆也算交差），但**合成类任务「她背包里有」就是真完成**；
而且那个「防假完成」的保护自己坏了（无基线），变成**「谁都别想完成」**。

### 改法 4 处
1. `TaskChain` 新增 `startCurrentWithCounts()` —— 也拍基线（幂等安全）
2. `HardCodedEvaluator` —— acquire 无基线时**降级为 hold 语义**（「宁可通过一次，也不要让子目标不可完成」）
3. `RddRuntime` 透传
4. `RddSubmitTool` 改用新方法 + **工具说明重写**：默认不传 mode = hold = 硬读背包（craft/equip/build 用），acquire 只用于 collect/farm，明写 "Do NOT use acquire for craft/produce"

### 验证（两条路都通）
| 任务 | 结果 |
|---|---|
| `stone_axe`（不传 mode = hold） | `matches=false RUNNING` → `matches=true COMPLETED`（assets 153→154） |
| `stone_shovel`（`mode=acquire`，出发前 `rdd_get_inventory` 确认她没有） | `matches=false RUNNING` → `matches=true COMPLETED`，条件里 `mode:acquire` 确实进去了 |

**全程无 stall / retry / 被迫重做。**

## 七、工具用法备忘（本轮踩到）

- **`stager put` 的正确用法是 `stager put <文件路径> --kind <类型>`**，不是 `--title`（用 `--title` 会报「给文件：stager put <文件|-> --kind plan」）
- **`rdd-docs` 仓库里有另一个并行会话的东西**（同名副本目录、`_stage/巡检记录`、`rdd存放/` 同步批次…）→ **必须精确 add**，本轮只 add 了 `rdd架构/自编译统一版/` 下的 9 个文件
- **`redline-1` 分支没有 upstream**，直接 `git push` 会失败，要 `git push -u backup redline-1`
- `origin` 指向**原作者** `Dwinovo/minecraft-numen`（403 无权限，本来也不该有）；我们的远端叫 `backup` = `nuomi2422/minecraft-numen`
- 追加内容到 md 时**别在 node 模板字符串里写反引号**（会被解析成字符串结束）→ 先用 write 工具写片段文件，再让 node 读它追加
- `.ps1` 必须 UTF-8 BOM；`Start-Process -ArgumentList` 会把带空格的值拆开 → 整段包成 wrapper 文件；内联 JSON 被 PS 引号拆坏 → 一律写 `.js` 用 `execFileSync(NODE, [CLI, ...])` 传 argv 数组
- `numen-mcp.js call` 只吃 a1/a2 两个参数 → `companion` 必须写进 JSON 里
- `rdd_submit` **必填 6 个**：`goal / primary_goal / subtask / asset_key / minimum / companion`（`additionalProperties:false`）
- 判 AI 活跃度看 `latest.log` 的 `[numen-llm]` 行，**不要看 jsonl 的 mtime**
- `ApricityUI` 的 `NoSuchMethodException: NbtIo.writeCompressed` 每 4 分钟一次 = **已知第三方噪音**（ApricityUI 1.2.0.2 的 LocalStorage）
- `Flashback-0.39.7-for-MC1.21.1.jar` 会造成确定性崩溃（ImGui 断言），已改名 `.jar.off` 停用
