### 1.2 三个术语（用户 2026-09-30 亲口定 · 全部是原话，别再自己猜）

#### ① 「浮现」= 浮现任务 = 自动课程（Automatic Curriculum）

> 用户原话大意：**「浮现」指的就是浮现任务**，即网络上说的
> **「看到猪 → 想到饿 → 决定杀猪」这种由环境和自身状态触发任务的行为**。
> AI 领域叫 **自驱动任务生成 / 自动课程（Automatic Curriculum）**。

⚠️ **这关闭了 `38 号 §5-4` 的悬案**（「浮现到底携带什么」）。答案是：
**浮现不是携带器携带的一件东西，浮现是一种「任务被自发创造出来」的行为。**
承载它的底座 = **支线任务**，而**支线任务我们的任务链已经做了**（见 ① 之底座说明）。

#### ② 「关怀任务」= 状态不满时注入的软提醒 ★

> 用户原话大意：AI 进游戏后自己有缺陷，**决策时可以优先写一些携带器逻辑** ——
> **检测到自己的食物/状态不好、或者状态不是满的时候，就直接给它注入一个软的提醒**，
> 比如「尽量还是吃food，让自己悬崖勒马」「我有点饿了，让我吃一点」，
> **而不是一直不吃**。这个叫**关怀任务**。

| 项 | 内容 |
|---|---|
| **触发源** | 自身状态不满（饿 / 血少 / 状态非满） |
| **动作** | **注入一条软提醒**（不是硬指令、不是直接塞食物） |
| **底座** | **支线任务**。用户原话：**「这个任务都是支线任务的底座，我们的任务链已经做了，你只需要弄就知道了，后面那个 AI 会自己查明白的」** |
| **对规划的含义** | **不需要新建机制**。任务链已有，规划 AI 只需把「自身状态」接到支线任务触发源上。**别重造。** |

#### ③ 携带器分级 = **判断链**，不是内容清单 ★（我第一版理解错过）

> 用户原话：**「携带器第一级、第二级、第三级是指的判断，是分级判断连带着来的。」**

| 我原来的错解 | 正解 |
|---|---|
| 第 1 级 = 安全位 / 第 2 级 = 装备 / 第 3 级 = 血量（三件东西摆着） | 级 = **一个条件判断** |
| 每级独立、互不相关 | **连带着来** —— 第 1 级不成立，**第 2 级根本不用问**（短路） |
| 级 = 携带物 | 级 = **判断**；**通过判断之后携带什么，是判断的结果** |

`25 号` 那三级「指向谁 → 装备 → 血量」按正解读是：

```
第1级判定：这轮该干的事，目标是谁？        → 不成立：根本不该动
第2级判定：目标要用的装备，够不够？        → 成立才轮到问
第3级判定：血量/状态撑得住这次行动吗？      → 成立才轮到问
```

**「安全位」不是「第 1 级」**（用户确认：**「他应该是某一句判断携带的内容」**）——
它是**某一级判定成立时携带的内容**。例如「判定这轮要出门冒险」时携带撤离用的安全位。
→ `38 号 B5`「本批不定级数」的留白**保持**；
本批只要求**判断链结构 + 分级可插拔**，具体挂什么由游戏内真问题决定。

## 2 · 经验记录格式（用户定的字段 · 不可省）

用户明确要求经验库**不能只记操作步骤**。每条经验必须有这 7 个字段：

| 字段 | 含义 | 反例（不合格） | 正例 |
|---|---|---|---|
| **机制** | 这条经验背后的世界规律是什么 | 「先挖矿再下界」 | 「下界岩在无支撑时会因重力掉落形成天然垂直通道」 |
| **前置条件** | 满足哪些条件才能用 | 「有钻石镐」 | 「镐等级 ≥ 该方块 tier；且脚下 3 格有可站立面」 |
| **失效条件** | 什么情况下这条经验会害你 | （常被漏） | 「开阔熔岩湖上方；末影人直视范围内」 |

| **效率** | 相比朴素做法省多少 | 「更快」 | 「一次下潜 12 格 vs 3 格×4 次；时间 -70%」 |
| **证据** | 从哪来的 | 「经验」 | 「ep7 t2000 commentary 原话 + 完整帧截图路径」 |

## 3 · 用户的五层框架（C 档 · 用户原创思考，非社区标准）

用户自己提出这个结构，**并明确说这是他个人的思考方式，不是现成社区术语**：

```
机制 → 资源链 → 自动化 → 效率 → 验证
```

| 层 | 要回答的问题 | 判「学会了」的信号 |
|---|---|---|
| **L1 机制** | 世界怎么运作？什么导致什么 | 能说出**反例**：什么条件下这条机制不成立 |
| **L2 资源链** | 从原始资源到目标产物，缺哪一环 | 能诊断**卡点在哪一环**，而不是笼统说「资源不够」 |
| **L3 自动化** | 哪一步该交给机器 | 能说出**该自动化的判据**，而不是「能自动就自动」 |
| **L4 效率** | 同样产出少多少时间/损耗 | 能给出**可测量的对比数**（不是「更快」） |
| **L5 验证** | 怎么知道自己真学会了 | 能说**世界上的可观察差异**（不靠 LLM 自评） |

> **L5 是用户框架里最值钱、也是我们系统最弱的一层。**
> Astra 给了 L5 一个现成的、正好用的答案范式 —— 见 §5.6。

| ~1250s | *"A ghast killed me **during the interruption**."* | 挂机/被打断时被远程火球打死 → **无安全位概念** |
| ~1500s | *"I stepped off a ridge and fell."* | **上一句刚说「check each drop」，转头又踩空** → 规则没落进动作 |

> t1250 那句 **"during the interruption"** 是最狠的一条：
> 它**知道自己被打断了**，但整个系统里**没有一个「安全位/挂机位」概念**。

**2 段死循环（A 档 · 这是第二批最该抄的教训）**：

| 时长 | 原话 | 模式 |
|---|---|---|
| **4.5 分钟**（9 次连续重复 30s） | *"The obstructing rung is removed. **I'm completing the support and the correctly aligned rung now.**"*（前一句：*"The misplaced rung is occupying the support space. I'm targeting that rung directly so I can replace it with the proper support and ladder."* ×5） | 微调 → 没成 → 再微调 |
| **2 分钟** | *"The boat placement is **still failing** from the bank. **I'm adjusting the position in small steps** to get a clear launch point."* | 同上 |

> **这两段是 `llm_idle_stall` 闸（commit `883c0784`）的真实需求来源。**
> 该闸目前只有**单测通过**，`38 号 盲点①` 要求的实机验收**尚未做**。
> 建议第二批把 ep7 这两段做成**实机验收场景**（见 §6.3）。

**它做对的 3 件事（A 档）**：

1. **系统设计式修正**（不是硬扛）
   *"I'll **move the Overworld portal closer to the known pearl traps**, then **protect the Nether arrival point from ghast fire**."*
   → 搬一次门，让「珍珠狩猎」和「下界落点防护」**同时成立**。
   并且给新点位定了坐标：*"roughly 250 blocks west and 430 blocks south, aligned with the known trap area."*
2. **双用检查点**
   *"the next checkpoint can serve **both pearl hunting and the eventual stronghold trip**."*
   → 一次布置服务两个目标。
3. **自建安全脚手架**
   *"The two-column shaft is working: I can **check one side below while standing on the other**. I'm down about twenty blocks with full health."*
   → 这是 §1.1 里「并行/条件触发」缺失的**手工替代方案**。

**一条执行层缺陷（★ 很可能和我们的 harness 同源）**：

> *"I've verified that **the jump input works with 'SPACE'**; I'll use a water descent to reach the ground."*

跳跃输入不可用 → 被迫**用水下下降落地** → 随后 *"The descent caused **heavy fall damage**."*

→ **这和我们 `36 号` 记的「视角/输入没对齐动作批次」是同一族问题。规划时请当成一类。**

**keepInventory 规则再次坐实（A 档 · 带具体数量，可交叉核验）**：

ep7 给出**第二条独立证据**。

## 5 · 跨案例提炼的机制级结论（C 档 · 我的推断 · 请你验证）

> 以下 6 条是我从 A/B 档归纳的。**这是本文件最需要你批判的部分。**
> 每条我给了「反驳它需要什么证据」，方便你直接拿去验。

### 5.1 Astra 的失败有**同一个根因**：没有「无进展」概念

4 次死亡里，2 次是**它自己刚说过的规则没落到动作**（t1500「check each drop」→ 踩空；
t2760 死在水下放船而床在船上）。2 段死循环是纯微调不换方案。
**推断**：它的循环体里**缺少一个「连续 N 轮无进展 → 换方案/上报」的分支**。
**证伪方法**：构造场景让它卡在同一动作 ≥3 轮，看它是否**自己**换方案；
若它永远微调，则本条成立。

### 5.2 「说出的规则」≠「执行的规则」

t1500 是硬证据：它**能正确说出**该检查落差，**但没执行**。
→ 对我们的含义：**经验库不能只验证「AI 能不能复述这条经验」**，
必须验证**「世界上的行为有没有变」**。这和 `38 号` 盲点① 是同一个病根的两个症状
（观测/验证不区分「在说」和「在做」）。

### 5.3 「系统设计式修正」是比「变强」更高一级的学习

ep1 换备用船而不抢船、ep7 搬传送门让两个目标同时成立 ——
两者都**没有提升操作能力**，而是**改环境让失败模式消失**。
→ 对我们的含义：L3 自动化 的验收判据应该是
**「同类失败是否不再发生」**，而不是「是否建成了某个机器」。

### 5.4 观测层的厚度直接决定决策精细度

`40 号 ★3` 已列：它的面板有 `Biome` / `Facing`（含语义）/`Targeted Block + tags`/
`XYZ` / `Chunk` / `distance` / `exposure`。
对比之下我们的 `RddPlugin.renderStateContext` **薄得多**。
**观测薄 → 决策只能粗 → 于是回到手点 → 于是回到 §1.1 的三个缺失。**

### 5.5 控制层缺陷会被 AI 当成世界规则吸收

ep7 那条 jump/SOURCE 事件是最好的例子。**这不是 AI 的错，是 harness 的错被误归因。**
→ 规划建议：**执行层要把「我发出的输入」和「世界实际发生的」分开报告**，
让 AI 有办法说「我的 jump 没生效」而不是「这里只能走水路」。

### 5.6 L5 验证的现成答案范式 ★

> *"I'm moving the search **higher into the netherrack, above the cavern openings that caused the falls**."*

这一句是**全场最值钱的一句**：它**记得具体的失败位置**、**据此改变了搜索区域**。
**判据不依赖 LLM 自评，而是世界上的实际坐标变化 —— 可查、可复核、公开可查。**
→ 建议第二批的验收场景**全部按这一类设计**（比 `33 号 §二③` 更好）。
