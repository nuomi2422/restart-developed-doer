## 0. 结论摘要（先看这个）

第二批用户骨架（语义一字不改）：

```
干活AI遇问题 → 写原始备忘录(带环境快照) → 攒队列
   → 学习者清空队列、逐条复盘、自己判定（可多选/多写，各自独立管理）
        ├ 调 AC   ├ 调携带器   ├ 写经验(进记忆库)   └ 自编译
携带器 = 分级检测(1指向谁→2装备→3血量) + 只携带不存储(记忆/工具/备忘录/浮现)
记忆库 = 抽象结论 + 语义检索 + 携带器式检索，做法抄 Voyager
全局锁 = 防左右脑互搏
顺序：记忆库/学习者/携带器 在前，AC 最后
```

**v1 落点 = 新建 `plugins/learner`（不扩 experience，不动 rdd-core）。**

三条硬约束决定了这件事只能这么落（全部本次实测/读码确认，非推测）：

| 约束 | 证据 | 后果 |
|---|---|---|
| **跨插件 import 被 gradle 刻意封死** | `buildSrc/src/main/groovy/numen-plugin.gradle:37-44` 只给瘦 api jar + `:ai` + `:ui`，注释原文「别图省事换成 `project(':api:neoforge')`」；`plugins/rdd/build.gradle:22` 与 `plugins/experience/build.gradle:19` 各自零互依 | rdd / experience / ac 彼此**永不可见**。唯一通信面 = `NumenApi`（`api/common/.../api/NumenApi.java`，8 方法）。且历史上 rdd 内嵌 ac-core 直接撞 JPMS `ResolutionException`（`AC_EXECUTION_LAYER_EXTRACTION.md:77-80`）→ **绝不能再内嵌** |
| **rdd-core 是零依赖纯 JVM** | `settings.gradle:39-40` 注释 "no Minecraft/NUMEN dependency" | 学习者要调 LLM 就**不能**放 rdd-core（塞进去就破边界 = 架构级污染） |
| **`:ai` 已在插件 compileOnly 上** | `numen-plugin.gradle:43` `compileOnly project(':ai')` | 新插件**不用改 build.gradle 约定**就能用 `NumenLlmClient` |

## 1. 学习者为什么是「LLM 主动调」而不是「事件驱动」

先否掉一个看起来更优雅的方案：**挂 tool_result 事件自动提炼**。

实测事实：工具结果事件由引擎写进 `config/numen/monitor/tools.jsonl`（`api/common/.../network/payload/ExecuteToolPayload.java:147-149`），但
① 它在**引擎侧**，插件订阅不到（`MonitoringJournal` 只写文件不回调）；
② `result` 被 `truncate` 到 300 字（`ExecuteToolPayload.java:180-183`），做不出高质量提炼；
③ 想改成回调，得动引擎 api jar 加事件常量（`CompanionEvent.java:18`），那是**架构级**改动。

→ **v1 不做自动事件提炼**。学习者由 AI 主动调（`learner_review`），读**自己写的备忘录队列**。
这与 AC 现状一致：`plugins/ac/**` 全目录搜 `ServerTick|EventBus|@Subscribe` **零命中**（AC 也没有任何事件驱动）。

**这不是倒退**：干活 AI 遇到问题时本来就在决策上下文里，它写备忘录是顺手；学习者是**离线的第二大脑**，不必抢实时。

## 2. 关键设计：plan-only（学习者不自己动手，只出「判定+建议」）

这是本方案**最重要的一条**，直接关系红线 RL-9（单驾驶员）。

> RL-9 原文：RDD 规划/监督层不得自动提交身体工具（`bodySubmissionEnabled` 默认 false，`RddPlugin.java:69`）。
> 破线判据：日志出现「已提交身体任务」而 `rdd-bodydispatch.flag` 不存在。**理由：双驾驶直接导致原地左右横跳。**

**如果学习者自己去「调 AC」（AC 会真调 mine/goto/attack）**，它就成为**第二个发指令的主体** = 第二个驾驶员 = 破 RL-9。第二批明写「全局锁 = 防左右脑互搏」，用户自己已经点明了要防这个。

→ **v1 学习者 = 只读复盘 + 出结构化建议**，不执行任何身体动作：

```
learner_note    干活AI → 写备忘录（带环境快照）→ 队列          ← 写
learner_review  学习者 → 清空队列 → 逐条 LLM 复盘 → 出判定     ← 读+LLM，不动手
                 判定 = {verdict, confidence, 建议动作, 建议写经验草稿, 建议AC脚本, 建议自编译}
learner_status  查队列深度 / 上次复盘结果                       ← 只读
```

- 建议写经验 → AI 自己调 `experience_learn`（**已在 `plugins/experience` 上线，工具现成**）
- 建议调 AC → AI 自己调 `ac_execute`（**已上线**）
- 建议自编译 → AI 自己调 `selfcompile_request`（**已上线**）

**好处**：学习者零新增执行面，`AC 排最后`这条用户排序天然成立，且第二阶段开「自动执行」时，有 RL-9 那条全局锁当唯一开关（见 §5）。

## 3. v1 三个工具的契约

| 工具 | 方向 | 关键入参 | 出参 | 是否动手 |
|---|---|---|---|---|
| `learner_note` | 干活AI → 学习者 | `problem`(必), `stage`, `tried`(必), `snapshot`(可选 JSON: 血量/背包/附近实体/维度) | `memo_id`, `queue_depth` | 只写队列 |
| `learner_review` | AI → 学习者 | `max_memos`(1-20,默认5) | `reviewed`, `verdicts[]`, `queue_depth_after` | 只读+LLM |
| `learner_status` | AI/监测 | 无 | `queue_depth`, `last_review_at`, `last_verdict_count` | 只读 |

`verdict` 取值（**多选**：一条备忘录可同时给出多个动作建议）：
`WRITE_EXPERIENCE` / `USE_AC` / `USE_CARRIER` / `SELF_COMPILE` / `NO_ACTION` / `NEEDS_HUMAN`

**质量门（v1 必须有，防刷屏）**：
- 队列上限 `MAX_QUEUE = 64`，超出拒收并回报（不静默丢）
- 一次 `learner_review` 最多 5 条（`max_memos` 上限 20）
- 复盘失败**不丢队列**（写回原处，等下次），保证「学习者清空队列」不等于「数据丢失」
- LLM 不可用（无 apiKey / 端点失败）→ 明确回报 `LLM_UNAVAILABLE`，**不伪造判定**（对齐经验库 §11 验收「检索服务不可用时明确报 UNAVAILABLE，不能伪装成没有相关经验」）

## 4. 携带器 v1（只携带不存储 · 分级检测）

用户定义：`分级检测(1指向谁→2装备→3血量) + 只携带不存储(记忆/工具/备忘录/浮现)`

**约束**：`Menace` / `Battlefield` / `AttackPlan` / `Loadout` 全在 `core/common`，而**插件 compileOnly 类路径里没有 core**（`numen-plugin.gradle:41-42` 刻意封死）。所以学习者**不能 import 它们**。

→ **v1 携带器 = 学习者侧自算，只用只读工具喂进来的原始数据**：
- 入参是宿主给的**原始快照**（`hp`/`max_hp`/装备槽/附近实体列表），不是 MC 实体对象
- 分级检测三段：`1 指向谁`（nearest hostile，按距离+类别）→ `2 装备`（armor/hasWeapon/weaponTier）→ `3 血量`（hp/max_hp 分档）
- **只输出一个「携带清单」**（该带哪些记忆/工具/备忘录），**不落盘、不存状态** —— 严格守住「只携带不存储」

这样 `USE_CARRIER` 判定在 v1 就能给出真实内容（用队列里备忘录自带的 snapshot），不依赖任何未接通的接缝。

## 5. 全局锁（第二批第一件该做的基建，但 v1 不自动执行所以先不装）

用户：全局锁，防左右脑互搏。现状 `bodySubmissionEnabled`（`RddPlugin.java:69`，flag `config/numen/rdd-bodydispatch.flag`，刷新在 `:928-945`）只锁 RDD 一家。

v1 结论：**先不装**，理由是 v1 学习者不执行任何身体动作（§2），锁无对象可锁。装一个锁住空气的锁 = 假红线。

阶段二（开自动执行）时，全局锁应是**独立于 RL-9 的第二个开关**，锁住「谁可以发身体指令」，且必须：
- 默认关
- flag 缺失/内容异常 = 关（fail-closed，抄 `refreshBodyDispatchFlag` 的判定方式）
- 与 `rdd-bodydispatch.flag` **同时**满足才允许自动执行（两个锁串联，不是替换 —— 替换会把 RDD 自己的保护拆掉）

## 6. 记忆库语义检索（Voyager 做法）v1 只做一半

Voyager 底稿（`储备-Voyager-20260929/取用说明-备用.md`）确认三条金脉：①描述向量索引 + top-5 检索 ②自动课程 ③代码即动作空间。

**v1 约束**：`NumenLlmClient` 只有 `chatStreaming` / `chat`，**没有任何 embedding 接口**（本次读 `ai/src/main/java/com/dwinovo/numen/agent/llm/NumenLlmClient.java` 全量方法确认：只有 `forEndpoint/reset/chatStreaming×2/pickProvider`）。上真向量 = 新增 embedding 端点 + 本地模型 = 架构级。

→ **v1 用「LLM 改写 query + 现有词法检索」这条最小可行替代**：
- 已有 `LexicalExperienceRetriever`（`experience-core/.../core/LexicalExperienceRetriever.java`）是纯词法，零依赖，已上线
- 学习者复盘时**顺手产出改写后的检索词**（这正是 Voyager「描述向量」在本架构下的廉价对应物）
- 语义检索的接缝文档已标「未实现」：`docs/rdd-architecture/references/rdd-experience-memory-architecture.md:438`（`VectorExperienceRetriever` 接缝已留）
- **v1 不声称做了向量检索**，测试日志里写明这是「query 改写 + 词法」的替代路径

## 8. 本方案已知风险（不藏）

1. **学习者在服务端 body 工具里调 LLM** —— 依据是 `RddPlugin.java:261` → `RddDecomposer.llmAsk` 已在 `rdd_submit`（body 工具）里跑通（单人存档客户端/服务端同 JVM）。**但这是从 RDD 现状推断，未在本轮实机复验**。若专用服务器场景失败，降级方案 = 学习者只出 prompt、由 AI 侧发起 LLM。
2. **LLM 复盘质量未验证** —— 本轮只验「链路通 + 产出结构合法 + 不丢队列」，**不验判定内容是否聪明**。判定质量要等真出现失败案例才有意义。
3. **外脑没参与** —— Codex 本轮 429（`exceeded retry limit, last status: 429`，已重试到上限）、ai-bridge 未连接（需用户手动开浏览器插件，用户已离场）。**本方案是自审产物，未经外脑背书** —— 这是本轮最明确的欠账，写进测试日志。
