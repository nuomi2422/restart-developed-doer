## 1. 改前是什么样（观察者抓到的现场）

```
[10-02 10:38–10:47 观察者实跑]
t="20:02" id="t3" task="goto" status="failed">blocked: got within 24.2 blocks of lo...
t="20:47" id="t5" task="goto" status="failed">blocked: got within 24.2 blocks of lo...
```

目标刷怪笼 `(-878, 14, -908)`，同伴 `(-878, -10, -908)`：**x/z 完全相同，差 24 格高**。

读代码确认的病根（不是推测）：

| 位置 | 事实 |
|---|---|
| `MoveToCompanionTask.java:514` | `repDistance()` 对 `BLOCK` 用**三维欧氏距离** `Math.sqrt(player.distanceToSqr(bx+0.5, by, bz+0.5))` |
| `MoveToCompanionTask.java:650` | 旧文案把它写成 `blocked: got within <三维数> blocks of location x=<bx> z=<bz>` —— **三维数配水平坐标** |
| `MoveToCompanionTask.java:498` | `closeEnoughToSucceed()` 对 `BLOCK/COLUMN` 只算 `horizontalDistSqr(bx,bz) <= 3.0²`，**Y 完全不看** |
| `MoveToCompanionTask.java:570` | `successMessage()` 首词 `"arrived at location ..."` → 站在目标正下方 24 格也算「成功」 |

→ `24.2` 这个数**完全由垂直差主导**，但被写成「离目标还有 24.2 格、前面有东西挡着」。
模型合理读成「快到了，再试一次」→ 45 分钟后重吃同一句。

## 2. 改了两刀

### 刀 1 · `MoveToCompanionTask.java`（`core/common` → `core:neoforge`）
备份 `MoveToCompanionTask.java.pre-geommsg-20261002.bak`

- `blockedMessage()`：把**单一三维数**换成**水平/垂直两个数**，`YLEVEL` / `FIND` 各自给对应几何。判定仍用同一份 `repDistance()`，只是不再让垂直主导的三维数冒充水平距离。
- `successMessage()` 的 `BLOCK` 分支：首词 `"arrived at location"` → `"reached the HORIZONTAL position"`，垂直差顶到最前面，给可执行出路，末尾显式加 `"I did NOT reach it."`；`COLUMN` 分支首词同步改。

### 刀 2 · `MoveToTaskRecord.java`（`core/common` → `core:neoforge`）
备份 `MoveToTaskRecord.java.pre-errmsg-20261002.bak`

`resolveKind()` 里 `block` + 坐标互斥的报错重写。**互斥规则本身保留**（四家外脑一致认为规则对、且在教模型），只把「该改成什么」讲全：
- (a) 要「最近的那个」→ 只发 `block`，不带坐标
- (b) 要「指定的那一个」→ 发它的位置，并明说 `x+z` 只走到**那一列的地表**、悬在半空会落在它**底下**、`x+y+z` 是**站进那个格子**（会掏掉里面的方块，别对着箱子/刷怪笼用）

### 刀 3 · 验证时发现我自己引入的两个瑕疵（同批修掉）
- `MoveToTaskRecord.java`：直接把 boxed `Double` 拼进文案 → **没给 y 时印出字面量 `-878.0,null,-908.0`**。报错文案里出现 `null` 就是在教模型填错值。加私有 helper `coords(x,y,z)` 只拼实际给了的轴。备份 `.pre-typo-20261002.bak`
- `MoveToCompanionTask.java:575`：格式串多一个 `)` → 文案变成 `build a way up))`。备份 `.pre-typo-20261002.bak`

### 4.4 ★ 候选 1 的 y 语义验证（GLM 点名的第一个动作）

原问题：裸坐标 `goto` 给 `y=14`，这个 y 到底被用了吗？

**答案：用了。** 证据就在 4.2 那条：

```
no path to target, not even by digging or bridging
  (from -878, -10, -908 toward -878, 14, -908, about 24 blocks away; …)
```

`from` = 起点，`toward` = **含 y=14 的目标**。所以 y 没被忽略、没被吞，是真的拿去寻路了，
失败原因是**寻路确实到不了悬在半空的格子**。

→ **GLM 的判断成立**：候选 1 和候选 2 是同一个病的两极 —— 参数空间「过窄」（`block`+坐标无法共存）
与「过宽」（`closeEnoughToSucceed` 完全不管 Y），而「忽略 Y」正是「过宽」那一侧的设计假设来源。
**所以最小修复不是动 `block` 参数，是让文案如实说出垂直差** —— 这正是刀 1 做的。

## 5. 局限（写清楚，别把这一轮的成功当普适结论）

1. **只验了一个悬空目标场景**。`successMessage()` 的 `COLUMN` / `YLEVEL` / `FIND` 三个分支只验了 FIND，COLUMN 改了首词但没单独取证。
2. **「模型会怎么读」是推断，不是观测**。我证明了文案变了、且新文案如实陈述了垂直差；**没有**证明模型的下一轮行为因此改变。要证明需要观察接下来几轮它是否换手段 —— 本轮没等到那个时间窗。
3. `AUTO_STOP_MINUTES=240` 的看门狗脚本会残留（实测过 4 个 `restart-mc.ps1` + 2 个 `mc-watchdog.ps1` 同时活着），本轮已按命令行关键字杀过，但**僵尸自退这个问题还没修**。
4. `Get-CimInstance Win32_Process` 对 `java.exe` **时灵时不灵**（本轮先返回空、后返回 1），`launch-mc.ps1` 的 `running` 判据依赖它 → 会误跳过启动。这是待修的启动链缺陷之一。
5. 本轮**没跑单元测试**（`run-mutation.ps1` 不跑 test）。上一轮改的 `RddV32DirectivesTest` 四个新测试至今没跑过。
