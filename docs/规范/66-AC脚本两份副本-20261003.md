# 66 · AC 脚本的两份副本（2026-10-03 实机抓出）

## 一句话

**磁盘上的 `.ac` 与库里的 `library.json` 是两份独立拷贝，改一份另一份不动，
而且没有任何提示说「你改的那份没生效」。**

## 实机证据（2026-10-03 17:22）

| 位置 | mtime | `move` 步带 `block` 参数吗 |
|---|---|---|
`config/numen/acx/lib/stable/mine_nearest_ore.ac`（种子，我改过的）| 17:2x | **False** ✅ |
`config/numen/acx/library.json`（库里的副本）| **08:09:05** | **True** ❌ 旧版 |

⇒ 同一个 `acx_execute ac_name=mine_nearest_ore`：
- 走 `ac_name`（库）⇒ 跑旧版 ⇒ `move` 步 `STEP_FAILED FAIL`，
  原因 `goto: block means 'walk to the nearest one of these' so it cannot be combined with coordinates`
- 走 `ac_json`（内联，绕过库）⇒ 跑我改的版本 ⇒ `move` 步 `STEP_FAILED **PAUSED**`
  （= 受理即 PAUSED，是「真在走过去」的正常语义）

## 为什么会有两份

`AcxPlugin.java:262-264`：
```java
store   = new JsonlRecordStore(base.resolve("records.jsonl"));
FileAcxLibrary library = new FileAcxLibrary(base.resolve("library.json"), registry);
library.load();
autoApproveBundled(library, load);   // ← 启动时把种子「复制进库」
```
`autoApproveBundled` 只在**插件启动时**跑一次。

## 三条后果（按危险程度）

1. **★ 改完不生效且无提示**。最危险的一种：磁盘上是对的、库里的不是，
   而运行时报的是**旧版的行为**，读的人会以为「我明明改了」。
2. **修好的脚本要等重启才生效** —— 这跟普通的「缓存没刷新」不同，
   它是**两份持久化副本**，不是内存缓存。
3. **`ac-library.json` 与 `acx/library.json` 两个文件都在**
   （后者 27564 字节 = 真库；前者 234 字节 = 另一个东西），
   **看错文件会以为「我的修改没保存」**。

## 怎么分辨「我跑的是哪一份」

| 调用方式 | 跑的是 | 适合 |
|---|---|---|
`acx_execute ac_name=X` | **库里那份**（可能是旧的）| 验证「发布出去的东西」 |
`acx_execute ac_json=<整段脚本>` | **你传进去的那份**（绕过库）| 调试一份刚改的脚本 |

⚠️ **验证一个刚改过的脚本时，必须用 `ac_json` 内联**，
否则你验的是旧版 —— 而且失败信息会指向一个你已经修好的地方。

## 与既有教训的关系

与 E8 那次「`ENTRY_KEYS` 没同步导致 learner 侧一直红，而验收记录写的是全绿」同族：
**同一个事实存了两份，改了一份，另一份在下次「加载」之前一直是旧的。**

> **纪律：改任何一个「有副本」的东西之后，
> 先确认「跑的时候读的是哪一份」，再决定要不要重启。
> 不确认就等于在验旧版。**

## ★ 五条坑（owner 说「我真的无语了」，所以逐条记清楚）

### 坑① `goto` 的 `block` 与坐标**不能合用**（真 bug，在脚本里）
`goto` 的 `block` 语义是「**自己找最近的这些之一**」，
所以它与坐标是**二选一**。同时给两者，运行时会**当场拒绝**并把三种正确用法列全：

```
IllegalArgumentException: block means 'walk to the nearest one of these' so it cannot
be combined with coordinates. You asked for block=minecraft:iron_ore AND a position,
which is the one combination I cannot express. Pick the one you actually mean:
 (a) 我要最近的这种 → 只给 block="minecraft:iron_ore"，不给坐标
 (b) 我要那一块     → 给它的位置；x+z 只用来走到那个柱子的地面（y 自动取地面）；
     如果那块悬空，surface-walking 会落在它下面，那时需要 interact 或垂直移动，
     不能用普通 goto；x+y+z 才会站在那个格子里（会把占用它的方块挖掉
     —— 千万别瞄准宝箱或刷怪笼这类要留的东西）
```
★ 这个报错本身**质量很高**：它不只说「不行」，还给出三种正确写法。
所以这次失败**不是系统的锅，是脚本写错了**，而系统把错误讲清楚了。

### 坑② ★ **覆盖 `library.json` 也没用** —— 一共**三层**
owner 问「应该可以直接给他覆盖了吧」：**不行。**
1. 种子 `lib/stable/*.ac`（磁盘）
2. 库 `acx/library.json`（磁盘，**启动时从种子拷来的一份**）
3. **内存里的 `entries` map**（`load()` 读进去的，**之后再也不读磁盘**）

⇒ 改第 1 层不影响第 2、3；**连覆盖第 2 层也不影响第 3**。
唯一能立刻生效的路是 **`ac_json` 内联**（**完全绕开库**，直接把脚本喂给执行器）。

### 坑③ ★ 我那一次 `edit` **返回成功但文件没变**
我用 `edit` 删掉 `"block": "minecraft:iron_ore",` 那行，工具回「Edit applied successfully」，
我据此以为改好了就去跑 —— **文件里那行还在**。
⇒ **回读文件确认是必须的**。这与本工程反复出现的教训同族：
「工具说成功」不等于「文件真的改了」。

### 坑④ `PAUSED` 不等于「失败」
AC 里 `goto` 是异步的：**受理即 PAUSED**，那表示「**真在走过去**」，
不是出错。分真假要看有没有 `reason`：
- `STEP_FAILED` + `PAUSED` + **无 reason** = 正常受理
- `STEP_FAILED` + **`FAIL`** + **有 reason** = 真失败

⚠️ 这个组合很容易读反 —— 我第一次看到 `STEP_FAILED` 就以为挂了。

### 坑⑤ `needs a 'companion' argument` **偶发就是偶发**
游戏和 MCP 都正常（`list_companions` 两只同伴都在）时，这个报错**照样出现过一次**，
**原样重跑就通了**。
⇒ 遇到它**先重试一次**再开始排查参数，否则会把时间浪费在参数上。
（真错的时候也是这个报错，所以「重试一次」是成本最低的分辨手段。）
