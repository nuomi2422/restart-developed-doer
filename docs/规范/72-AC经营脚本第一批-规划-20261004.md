## 1 · 规划经验（四条纲领）

这四条来自 54 号那份生电对照的实测结论，**不是这次新想的**，写成纲领是因为它们同时约束「经营脚本」和「机器设计」。

### 1.1 社区方案当 SOP，不当设计题

**依据**：54 号 §3F —— Forgematica 已经能产出我们读得懂的 `.schem`，但我们执行层在载入期剥活物、剥液体、红石不初始化。所以正确做法不是「让 AI 设计一台刷铁机」，是「把社区验证过无数次的步骤抄成原子动作序列」。

**落到脚本上**：每个脚本开工前必须回答一句 —— **「社区/原版机制有没有现成流程？」**
- 有 → 抄步骤（例：牛羊引诱 = 原版手持小麦，20 格内生效）
- 没有 → 才允许自己设计，且要写进 `planner_notes`

### 1.2 生物机制可以替代机械运输

**依据**：54 号 §6 —— 丐版刷铁机（围地→床→引僵尸→僵尸踩船困住→篝火烤死铁镗→旁边箱子捡铁）**逐件物料全落在现有工具内**，一次性绕开了「红石不初始化 / 液体硬拒 / 载具驱动」三堵墙。绕法是**用 mob AI 代替机器**。

**落到脚本上**：经营脚本同此。例 —— `herd_cattle_sheep` 用「丢麦 + 走开 + 回头看」代替「拴绳 / 矿车 / 围栏流水线」；代价是「不保证 100% 跟上来」，所以**必须有拉黑换目标**（§4.4）。

### 1.3 物品是量产的，调用不是

**依据**：54 号 §3D —— 绿宝石换钻石套按现有粒度 ≈150 次调用/组。

**落到脚本上**：每个脚本规格里必须写清三栏：
- **单次执行产出**（跑一次赚多少）
- **调用预算**（一次执行最多几个 tool call）
- **回本条件**（跑几次才回本 / 供给多久）

没有这三栏的脚本不算规划完成 —— 因为「能跑一次」和「经营」差着两个数量级。

### 1.4 失败模式不许静默

**依据**：AGENTS 硬规矩 + `RddBodyDispatcher.java:80-86` 的 `subtask_capability_gap` 口径 + `guard` 步不满足即 `PAUSED`。

**落到脚本上**：
- 牛没跟上来 → `PAUSED` + 写明「试了 N 头、被拉黑 M 头、最后停在谁那里」，**不许**「走过去就算完成」
- 箱子满 / 箱子不存在 → `PAUSED` + 报坐标，**不许**静默丢弃
- 材料不齐 → `PAUSED` + 报缺什么，**不许**种一半

## 2 · 执行层底账（写脚本前必须知道的事实）

### 2.1 ACX 是什么、跑在哪

| 项 | 事实 | 证据 |
|---|---|---|
| 定位 | **宿主无关的原子工具编排执行层**。不生成工具、不做任务规划、不替 Supervisor 判语义 | `AC_EXECUTION_LAYER_EXTRACTION.md:9` |
| 门面工具 | **8 个 `acx_*`** | `plugins/acx/AcxPlugin.java` |
| **LLM 调用** | **零**。grep `llm\|Chat\|prompt\|Provider\|Model` 只命中 2 条注释 | `AcAuthoringService.java:14`「不引入 LLM 依赖」 |
| 脚本落盘 | `config/numen/acx/lib/stable/*.ac`（jar 内置脚本自动铺到此，已存在的不覆盖，升版留 `.stale-<ts>`） | `AcxPlugin.java:233-237,356-383` |
| 版本库 | `config/numen/acx/library.json`，`GENERATED/PENDING/STABLE/REJECTED` 四态，**只有 `STABLE` 可 active** | `FileAcxLibrary.java:31-47`、`AcxLifecycleState.java:15-32` |
| 执行记录 | `config/numen/acx/records.jsonl` —— **只落 PAUSED / FAIL / TIMEOUT，SUCCESS 不落盘** | `JsonlRecordStore.java:63-67`、`AcxStatus.java:29-31` |
| 事件流 | `config/numen/monitor/acx.jsonl`（旁路观测，写失败静默） | `AcxMonitor.java:16,37` |
| 内置脚本现状 | `stable/` **10 个**（`do_while_scan` / `hp_guard_goto` / `ignore_failure_demo` / `inventory_if` / `mine_nearest_ore` / `numen_smoke_read_move_read` / `ore_goto_mine` / `ore_scan_inspect` / `subac_nesting` / `timeout_demo`） | 目录实测 |

**⚠️ 与旧 AC 的落盘目录刻意分开**（`AcxPlugin.java:40-41`：「防互相清库」）。旧 AC 在 `config/numen/ac-library.json`，**别写错地方**。

### 2.2 五种控制块（够写状态机了）

| 块 | 语义 | 证据 |
|---|---|---|
| `if` | 条件执行一次 | `AcxStep.java:22` |
| `while` | 循环，**三终点**：条件为假→正常退出 / `max_iters`→PAUSED / 连续 `stagnant_limit` 轮无进展→PAUSED | `AcxStep.java:23`、`AcxRunner.java:686-691,698-729` |
| `for` | 遍历列表，`$loop.total` 给总数 | `AcxStep.java:29`（AC-B11，2026-10-04） |
| `guard` | 步骤级守卫，不满足 → `PAUSED`（默认）或 `FAIL`（`on_fail:"fail"`） | `AcxStep.java:25`、`AcxRunner.execGuard:403-459` |
| `set` | 变量写回，**进 `AcxRunRecord.vars` → resume 后仍在** | `AcxStep.java:27`（AC-B9） |

**停滞检测认变量**（`AcxRunner.java:517-528`）：`while` 里反复 `set` 同一个值**不算进展**，会被停滞判定误杀 → 「变量真变了才算进展」。这是经营脚本唯一能收敛的机制，**必须用对**。

**进度字段只有 11 个**（`AcxProgress.FIELDS`，`AcxProgress.java:18-20`）：
```
mined, found, collected, placed, smelted, gathered, moved, removed, progress, count, gained
```
**产量指标必须落进这 11 个名字之一**，否则停滞检测看不见 → 循环会被误杀。⚠️ **没有 `harvested` / `planted` / `tilled`** —— 「收割了几块地」这个数进不了进度表。

### 2.3 参数绑定层（`AcxParamBinder`，574 行）

| 键 | 作用 |
|---|---|
| `$from` / `$as` / `$default` | 来源 / 类型转换 / 兜底 |
| `$filter` `{field,op,value}` | 列表元素筛选 |
| `$pick` | `first`(默认) / `last` / **`nearest`**（配 `$origin` 做 3D 欧氏距离） |
| `$take` | 从元素对象投影标量（如 `"x"`） |
| `$calc` / `$len` | 算术表达式 / 取长度（AC-B10） |

真实用例见 `stable/mine_nearest_ore.ac:68-79`。

### 2.4 工具目录是**故意不全**的

`NumenToolCatalog` 只声明 **17 个**工具（`NumenToolCatalog.java:43-169`）。类头注释 `:25-26`：「没有实测到参数形状的工具宁缺毋滥 —— **禁止臆造 schema**」。

- **目录外的工具仍能调**（`AcxPlugin.ensureReady():242-251` 对 `ToolRegistry.all()` 全量桥接），但**拿不到声明的 outputs**
- **`$ref` 在运行时照常解析**（`AcxValueResolver:117` 从 `allOutputs` 取），所以「outputs 未声明」**不阻塞写脚本**，只是少了一层加载期校验
- 已知未声明 outputs 的关键工具：**`scan_nearby_entities`**（`:156` 明写「输出字段未实测，故意不声明」）

**经营脚本会用到但不在目录里的**：`build` / `interact_at` / `drop_items` / `eat` / `sleep` / `transfer` / `follow` / `scan_nearby_entities`(在目录但无 outputs)。
→ **规划要求**：每个脚本落笔前先把用到的工具的**真实输出形状**在真机上打一遍，补进 `NumenToolCatalog`。**不补就写 = 臆造 schema，违反该文件自己的纪律。**

### 2.5 ★ 默认限额对经营脚本来说太小

`AcxLimits.java:16-25`：

| 限额 | 默认 | 对经营脚本的后果 |
|---|---|---|
| `max_steps` | **200** | 8×8 农田一个格子 1 步、翻倍算 128 步就顶到 200 |
| `max_timeout_ms` | **30_000（30 秒）** | ⚠️ **一个 `goto` 就能吃掉 30 秒**（`MovementOps.DEFAULT_TIMEOUT_TICKS` 就是 30s 基线）→ 默认值 ≈ 只够跑一个 `goto` |
| `max_iters` | **20** | 种田要循环的轮数远超 20 |
| `stagnant_limit` | **3** | 「等作物成熟」期间本来就零进展 → 3 轮后 PAUSED |

**规划要求：8 个脚本每一个都必须在 `limits` 里逐项显式覆盖，且在 `planner_notes` 写清为什么是这个数。** 这不是优化，是**不写就会在第一次真机跑时被熔断**。

### 2.6 三个已钉住、还没修的真缺陷（长任务最会踩）

```
1d2465fc  「恢复会重发已受理的动作」
09d3b45f  「取消后迟到的成功回执会把运行翻回成功」   TODO AC-B19
f9d658e2  「动作还在飞」被记成 STEP_FAILED          TODO AC-B20
```

**这三条正好是「农场 / 长循环」场景的三个坑。** 经营脚本必然长时间在飞 → 必然踩。规划要求：**每个脚本的验收清单里必须有一条「跑一半 resume，验证不重发」。**

### 2.7 单驾驶员冲突

`RddPlugin.java:70` `bodySubmissionEnabled = false`（`RedlineContractPinTest.java:138-145` 钉字面量）—— 这条红线**只约束 RDD**，ACX 直接调 `tool.onServerCall`（`NumenToolBridgeX.java:105`），**从不读它**。

⚠️ **但 ACX 与 RDD 会抢同一个身体通道**（`NumenToolBridgeX.java:41-42` 用 `mcp-acx-` 前缀标记外部调用），**代码里没有互斥锁**。
→ **规划要求**：经营脚本运行期间，**不允许 RDD 同时派发身体任务**。这条要写进运维约定。

## 3 · ★ 结构性缺口：无周期调度器（**已决定：先不解决**）

### 3.1 事实

- `plugins/acx` 全量 grep `ServerTick|tick|schedule|Scheduler|Timer|cron|ScheduledExecutor` → **0 命中**（唯一 `tick` 命中是测试夹具 `Fake.zero("tick")`，`AcxTestMain.java:3262`）
- 一次 `acx_execute` 是**一次性 `CompletableFuture`**（`AcxFacade.java:81`）→ 跑完就结束，**要再来一轮必须有人再调一次**
- 唯一的「周期」原语在 **goal 层**，不在 ACX：`EntityAgentLoop.java:836-839` 一轮收尾判一次，没过就再推一轮，最多 30 轮（`GoalState.MAX_GOAL_TURNS = 30`）。**且 goal 层有 LLM 评估器，ACX 零模型调用 —— 两者性质不同，不能简单套用**
- `set_timer` 只是个被 ACX 当积木调的**宿主工具**（`NumenToolCatalog.java:116-121`），**ACX 不订阅它的回调**

### 3.2 后果（写进规格，必须如实标）

| 脚本 | 常驻？ | 说明 |
|---|---|---|
| `eat_if_hungry` | ❌ 单次 | 跑一次查一次。**要常驻必须有人再调一次** |
| `night_sleep_check` | ❌ 单次 | 同上 |
| `herd_cattle_sheep` | ✅ 天然适合 | 循环收敛在**一次执行内**（拉黑换目标，直到跟到或拉黑完） |
| `farm_batch_wheat` | ❌ 单次 | 一轮种完就结束 |

### 3.3 将来要解决时的三条候选（**本批不做**）

| 方案 | 做法 | 代价 |
|---|---|---|
| A. goal 层当驱动 | 经营目标交给 `/goal`，ACX 只当执行器 | goal 层每轮一次 LLM 评估器 → token 烧 |
| B. ACX 加 tick 调度器 | `AcxPlugin` 里加 ServerTick 驱动的周期注册（cron / 间隔） | **新代码**；且要在 `guard`/熔断体系之外另立一套超时 |
| C. 外部轮询 | 外部每分钟调一次 `acx_execute` | 游戏不跑就断；8776 监测台要承担调度职责 |

## 4 · 八个脚本规格

> **本节只给规格，不写 `.ac`。** 每个脚本给：目的 / 前置 / 步骤骨架（人话）/ 状态 / 三栏账 / 缺口。
> **共用的参数绑定约定**：`$input.*` 传阈值与坐标；`$read.*` 指上一同步步输出；`$step_id.*` 指任意命名步输出。

### 4.1 `eat_if_hungry` —— 状态提醒吃东西

| 栏 | 内容 |
|---|---|
| **目的** | 饥饿值低于阈值时吃点东西，并在包里没食物时**响亮报错** |
| **前置** | 无（纯只读 + `eat`） |
| **步骤骨架** | ① `get_self_status` → ② `if` `$read.hunger < $input.min_hunger` → ③ `rdd_get_inventory` → ④ `if` 没有任何可吃食物 → `guard` 报 `PAUSED`（**不许静默**，纲领 §1.4）→ ⑤ 否则 `eat`（`item_id` 走 `$input.food` 或从背包挑）→ ⑥ 再 `get_self_status` 复核 `hunger` 是否上升 |
| **状态机** | 不需要。单次决策 |
| **输入** | `min_hunger`（默认 15）、`food`（可选，缺省自动挑） |
| **单次执行产出** | 不产出物品，**产出「一次不吃就掉的血」** —— 防饿 |
| **调用预算** | 3~5 次 |
| **回本条件** | 每游戏日（20 分钟）跑 1~2 次即够 |
| **缺口** | ⚠️ `eat` 不在 `NumenToolCatalog` → **需先补真实 outputs**（§2.4）；⚠️ **「可吃食物」没有工具级判据** —— 得靠背包 `items` 键名匹配一个白名单（面包/熟肉/苹果/胡萝卜…），**这份白名单要落在脚本里，且没有外部维护点** |
| **单次/常驻** | ❌ 单次（§3.2） |

> **⚠ 用户的原话是「身上的状态美满的时候要提醒吃东西」** —— 语音转写，语义按「状态**不**美满时提醒吃东西」理解。
> 落地成：**饥饿值低 → 吃东西**。若实际要的是「血量低 → 撤退/吃药」，那是另一个脚本，本批不含。

### 4.2 `night_sleep_check` —— 晚上睡觉提醒

| 栏 | 内容 |
|---|---|
| **目的** | 天黑时检查床 → 有床就睡，没床就**响亮提醒**而不是硬撑到天亮 |
| **前置** | 需要一张**玩家能睡的床**（1.21.1 里**床必须在村庄/建筑附近才「安全」**，野外床会被标「你在做梦…」的提示，且**会跳过夜晚**） |
| **步骤骨架** | ① `get_self_status`（`dimension`）→ ② `if` 不是主世界 → 跳过（本批不下界/末地睡眠）→ ③ `get_world_info` → ④ `if` `is_dark_outside == false` → 跳过（**白天不打扰**）→ ⑤ `scan_blocks radius=48 block_ids=[white_bed,red_bed,blue_bed,…]` → ⑥ `if` 零张床 → `set_timer` + `guard PAUSED` 报「无处可睡」→ ⑦ 有床 → `$filter+$pick nearest + $take x/y/z` → ⑧ `goto` 床边 → ⑨ `sleep` → ⑩ `get_world_info` 复核 `is_dark_outside` 是否转亮 |
| **状态机** | 不需要。但**天黑这个条件本身就是「等」** —— 见下条 |
| **输入** | `bed_radius`（默认 48）、`skip_day=true` |
| **单次执行产出** | 不产出物品，**产出「一个完整的夜晚」**（跳过夜晚 = 跳过刷怪 = 保住命） |
| **调用预算** | 5~8 次（`scan_blocks` 半径大时更贵） |
| **回本条件** | 每天 1 次 |
| **缺口** | ⚠️ `sleep` 不在 `NumenToolCatalog` → 需补真实 outputs；⚠️ `scan_blocks` 只扫**已加载区块**，未加载会返回 `note:"...are not loaded"`（`ScanOps.coverageNote:44-58`）—— **到了陌生地第一次跑必然扫不到床，这是假阴性**，脚本必须把 `note` 读出来透传，不能当「没床」处理；⚠️ **`is_dark_outside` 是布尔，但「该不该现在睡」需要玩家自己判断**（例如正在被追打时不该躺下）—— **本脚本是提醒不是决策**，这一点必须在 `safety_notes` 写死 |
| **单次/常驻** | ❌ 单次（§3.2）。**这是本批最需要常驻、也最拿不到常驻的一个** |

### 4.3 `farm_batch_wheat` —— 批量种田，收进箱子

> **用户决定：只负责种，收进箱子。** 不做分配、不做加工。

| 栏 | 内容 |
|---|---|
| **目的** | 把一块已耕地（`farmland`）**成批播种**，跑完把收成**存进指定箱子** |
| **前置** | ① 一片已耕地（人工用锄头 `interact_at right item_id=hoe` 打好）② 水源在 4 格内（**见下方硬缺口**）③ 一个箱子坐标（走 `$input.chest_x/y/z`）④ 手里/包里有种子 |
| **步骤骨架** | ① `get_self_status` → ② `scan_blocks radius=48 block_ids=[farmland]` → ③ `set total = $len` + `set done = 0` → ④ `for` 遍历 `matches`：<br>　a. `inspect_block` 复核这块还是 farmland（**不能只信扫描**）<br>　b. `goto` 到这格旁边<br>　c. `interact_at button=right item_id=minecraft:wheat_seeds x/y/z`<br>　d. `set done = done + 1`（**变量真变了才算进展**，否则被停滞检测误杀 —— `AcxRunner.java:517-528`）<br>　e. 拉黑已种的格子，防重<br>⑤ `goto` 箱子 → ⑥ `inspect_gui` → ⑦ `transfer` 把产物塞进箱子（**无 `to` = QUICK_MOVE 整叠路由**）→ ⑧ `set_timer` 提醒成熟 |
| **状态机** | ✅ 本批唯一真状态机：`for` + 计数器 + 拉黑表 |
| **输入** | `chest_x/chest_y/chest_z`、`seed`（默认 `minecraft:wheat_seeds`）、`radius`（默认 48）、`max_plots`（**必填**，防跑飞） |
| **单次执行产出** | `max_plots` 块地已播种；下一轮收成 ≈ `max_plots × 收成率` 入箱 |
| **调用预算** | **每个地块 5~6 次** → 16 块地 ≈ **90~100 次调用**。⚠️ 单次 `max_steps` 至少要 250 |
| **回本条件** | 播种本身不回本，**回本在收成那一轮**。一轮播种 + 一次收割 = 2 次执行 |
| **★ 三个硬缺口** | ① **浇水没原语**：`LiquidBlock` 被 `BuildStates.unbuildableReason` 硬拒（`BuildStates.java:277-297`），且 `BuildStates.normalize` 把 `WATERLOGGED` 强制 false（`:36-89`）→ **`farmland` 离水 4 格以上就退回 dirt，必须靠天然水源或下雨**<br>② **「等成熟」在 ACX 里没有原语**：`while` 空转会撞 `stagnant_limit=3` 直接 PAUSED；`set_timer` 不被 ACX 订阅 → **「等」必须交给外层重入**（§3）<br>③ **`harvested` / `planted` / `tilled` 不在 `AcxProgress.FIELDS`** → 「种了几块」这个数只能塞进 `count` 或 `placed` 字段名里，**否则停滞检测看不见** |
| **单次/常驻** | ❌ 单次。**且因缺口②，「播种一轮 + 等 + 收割一轮」这个完整循环目前无法在一次 AC 内闭合** |

### 4.4 `herd_cattle_sheep` —— 状态机引诱牛羊

> 用户指定：**用状态机来做**。

| 栏 | 内容 |
|---|---|
| **目的** | 把附近的牛/羊**赶到目标点**（进圈/回栏），走 mob AI 引诱路线 |
| **前置** | ① 包里有 `wheat` / `wheat_seeds`（牛羊都吃小麦）② 目标点在已知半径内 |
| **★ 状态机（本批的核心）** | 状态 `S0 定位` → `S1 锁定一头` → `S2 投喂` → `S3 走开` → `S4 回头看跟没跟` → 回 `S1` / 前进到 `S5 达成`<br>**转移条件**：<br>· `S1`：目标列表里还有没试的（`$for.total - 拉黑数 > 0`）<br>· `S2`：`drop_items item_id=wheat count=1`（**只能丢脚下**）<br>· `S3`：`goto` 往目标方向挪 6~10 格<br>· `S4`：`scan_nearby_entities` → `$filter` 目标 species → `$pick nearest + $take` → 判断距目标点距离<br>　　- 跟上了 → `S5`（`set reached = true`）<br>　　- 没跟上 → **拉黑这头**（`AcxTargetBlacklist`）→ 回 `S1`<br>· `S5`：`set reached=true`，`while` 条件为假 → 正常退出 |
| **为什么这个状态机是对的** | 纲领 §1.2 —— 因为 `drop_items` **只能丢在身体正前方**（`DropItemsTool.java:21-24`，无 `direction`/`target_pos`），所以「持麦走一段」这个原语不存在。**唯一能做的就是「丢 → 走开 → 回头验 → 不行换一头」**，而这正好是 `while` + 拉黑表 + 停滞检测的形状 |
| **输入** | `target_x/y/z`、`radius`（默认 32）、`species`（`cow`/`sheep`，可给多个）、`food`（默认 `wheat`） |
| **单次执行产出** | **0 或 1 头**。这是本批产出最差的脚本，坦白写出来 |
| **调用预算** | 每头试一次 ≈ **6 次**（scan + drop + goto + scan + 判 + 拉黑）→ 32 格半径内 6 头 ≈ **36 次** |
| **回本条件** | **不回本。** 它的价值是「把已经在附近的牲口收拢」，省的是**主人手动牵牲口的工夫**，不是物料 |
| **缺口** | ⚠️ **`scan_nearby_entities` 的 outputs 故意未声明**（`NumenToolCatalog.java:156`）→ 写脚本前**必须真机打一次拿真实字段名**，不拿就写 = 臆造 schema（§2.4 纪律）<br>⚠️ `drop_items` / `follow` 不在目录<br>⚠️ `AcxTargetBlacklist` 在 `while` 里是**拉黑失败目标换目标**（`AcxRunner.java:776-781`），**不是重试** —— 语义要对齐，否则会被误读成「会重试」 |
| **单次/常驻** | ✅ **天然单次收敛**（循环终点在同一次执行内）—— 本批唯一不依赖周期调度器的状态机 |

### 4.5 `farm_supply_check` —— 经营总检（组合 1 + 2 + 4）

| 栏 | 内容 |
|---|---|
| **目的** | 一次调用做三个体检：**饿不饿 / 天黑没睡 / 牲口在不在目标点** |
| **前置** | 无 |
| **步骤骨架** | ① `get_self_status` → ② 分派三个子 AC（`acx` 支持嵌套子 AC，见 `subac_nesting.ac`）：`eat_if_hungry` → `night_sleep_check` → `herd_cattle_sheep`（带 `may_skip=true` 时跳过）→ ③ `set_timer` 登记「N 秒后再查一次」 |
| **状态机** | 不需要（编排层） |
| **输入** | `interval_s`（默认 1800）、`may_skip` |
| **单次执行产出** | 一份体检结论（**以 `PAUSED` 的形式透出最先出问题的那一项**） |
| **调用预算** | 12~20 次（三个子 AC 的和） |

| **单次/常驻** | ❌ 单次（§3.2） |

### 4.6 `bed_and_bell_routine` —— 床与钟（养村民前置）

| 栏 | 内容 |
|---|---|
| **目的** | 54 号 §1 的 B 阶段：把村民的床拆下来搬进围栏、敲钟把村民叫出来 |
| **前置** | ① 一片围墙（**6×7×2，且不封顶** —— 铁镗高 2.7 格，封顶就生成不出来，54 号 §6 已核实）② 村民在附近 |
| **步骤骨架** | ① `scan_nearby_entities type_filter=passive` 找村民 → ② `scan_blocks` 找床 → ③ `for` 每张床：`interact_at button=left` 拆床 → `goto` 围栏内 → `drop_items` 放下 → ④ 敲钟：`goto` 钟坐标 → `interact_at button=right item_id=bell` |

| **回本条件** | 不回本，是**前置投资**（床 = 铁傀儡召唤的硬资格条件，54 号已核实） |

| **单次/常驻** | ❌ 单次（但单次就够，重复执行反而会把村民从围栏里引出来） |

### 4.7 `breed_villager_loop` —— 繁殖到目标数量

| 栏 | 内容 |
|---|---|
| **目的** | 用面包把村民喂到 N 个 |
| **前置** | ① 围栏已完成（4.6）② 床已进围栏（**床不是装饰，是召唤资格硬条件**）③ 包里有面包/胡萝卜/甜菜根 |
| **步骤骨架** | ① `get_self_status` 背包 → ② `set target = $input.count` → ③ `while` 村民数 < target：<br>　a. `scan_nearby_entities type_filter=passive` 数一遍<br>　b. `set fed = 0` → `for` 每只村民：`interact_entity button=right entity_id=<id> item_id=bread` → `set fed = fed + 1`<br>　c. `if` fed == 0 → `guard PAUSED`「没有可繁殖对象 / 食物不够」<br>　d. `set_timer` 登记「繁殖冷却 5 分钟后再来」→ **退出 while（无法在一次执行内闭合）** |
| **★ 为什么不能一次跑完** | 村民繁殖**有 5 分钟冷却**，幼崽**要 20 分钟长成**。`interact_entity` **只点一次就收工，不等冷却、不等幼崽、不等成年**（`InteractEntityTaskRecord.java:16-17`）。**ACX 又没有周期调度器** → 这个脚本在结构上**不可能**一次跑到 N 个 |
| **单次执行产出** | **1 轮投食**（一轮最多让 N 只进入求爱态） |
| **调用预算** | 每只村民 3 次（scan 可复用 → 实际 ≈ 2 次/只）→ 5 只 ≈ 10 次 |
| **回本条件** | 不回本，是**前置投资**（5 个村民 = 交谈召唤铁镗的硬门槛，54 号已核实） |
| **缺口** | ⚠️ `interact_entity` 不在目录 → 需补 outputs<br>⚠️ **「数村民」没有专门原语** —— 只能 `scan_nearby_entities` + `$len`（⚠️ `$filter` 后 `$len` 的组合要真机验）<br>⚠️ **「确认生出 baby 了」没有判据** —— `scan_nearby_entities` 能不能区分 adult/baby ⚠️ 未核实 |
| **单次/常驻** | ❌ 单次，且**结构上必须多次**（§3） |

### 4.8 `night_watch` —— 夜间守卫 ❌ 本批不做

| 栏 | 内容 |
|---|---|

### 5.2 三个「本批做不了」的诚实结论

| 结论 | 为什么 |

| **没有一个脚本能常驻** | §3 无周期调度器（**用户已决定先不解决**） |
