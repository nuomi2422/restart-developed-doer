## 1 · F2 死亡台账落盘（数据丢失级）

### 改了什么

| 模块 | 文件 | 改动 |
|---|---|---|
| rdd-core | `RddDeathLedger.java` | 新增 `LedgerSnapshot` 记录 + `snapshot(UUID)` / `restore(UUID, snapshot)` |
| plugins/rdd | `RddDeathLedgerStore.java`（新） | JSON 落盘：`config/numen/rdd-ledger/<uuid>.json`，原子 tmp+move |
| plugins/rdd | `RddPlugin.java` | `ledgerDir` + `LEDGER_LOADED` guard + `ensureLedgerLoaded` / `saveLedger` / `warnLedgerStore` |

### 为什么

`LEDGER`/`SEQ` 是静态 `ConcurrentHashMap`：停服即丢账。死亡台账是 RL-6/RL-7 的真身，
丢了它，"东西还在地上、还剩 200 秒"这条最关键的事实就没了。

### 怎么调的（三条硬约束，违反其中任何一条都会出更坏的错）

1. **core 不碰 IO**：`rdd-core` 只给 `snapshot/restore` 数据契约，`Path`/JSON 一律在插件侧。
   反向依赖会让纯 JVM 模块长出 Minecraft 依赖。
2. **必须先 restore 再 record**：`ensureLedgerLoaded` 用 `LEDGER_LOADED` 做一次性 guard。
   反过来会用旧账覆盖本次运行刚记的死亡 → 假"没死过"，比丢账更坏。
3. **`nextSeq` 语义是"下一次 record 将要用的 seq"**（不是"已用最大值"）。
   内部 `SEQ = nextSeq - 1`。宁可跳号也绝不撞号 —— seq 是批次身份，撞号 = 判据串批。

### fail-soft 的真实形状（这里踩过一次）

`warnLedgerStore` / `RddDeathLedgerStore.load` 的兜底 catch 的是 **`Throwable`**，不是
`RuntimeException`：在裁剪 classpath 下 `RddMonitor` 抛的是 `NoClassDefFoundError`（`Error`），
用 `RuntimeException` 会让"fail-soft 的兜底自己炸掉"，正好把最该保住的死亡路径带崩。
`RddDeathLedgerStoreTest.malformedJsonFailsSoftToEmptyLedger` 实测到了这个形状。

### 入口 / 出口

- 入口：`RddPlugin.onCompanionDeath` → `ensureLedgerLoaded` → `RddDeathLedger.record(...)` → `saveLedger`
- 出口（成功）：`RddRepairDispatch.onRepairSuccess` → `confirmRecovered(seq)` → `RddPlugin.saveLedger`
- 异常出口：`ledger_load_failed` / `ledger_save_failed`（日志 + 监测台，不阻断）

### 怎么验

```powershell
# 单测
gradle :rdd-core:test :plugins:rdd:test
# 实机：死亡一次 → 完全退出游戏 → 重进 → 监测台 rdd.jsonl 里
# companion_assets_invalidated 的 deathSeq/deathAt 仍在，且 config/numen/rdd-ledger/<uuid>.json 存在
```

## 2 · F6 回收判据精度（假完成）

### 改了什么

- `RddDeathLedger.Death` 新增 `Map<String,Integer> lostItems`（这一次丢了哪些、各多少）
- 新增纯函数 `openDeath(seq)` / `latestOpen()` / `checkBatchRecovery(...) -> BatchRecovery` / `repeatDeathWithin(...)`
- `RddRepairDispatch`：新增 `OPEN_DEATH_SEQ`（支线 ↔ 死亡批次）、`checkBatchRecovered`、`reportBatchProgress`
- `RddDetector.deathDropsBackInInventory`：改调 `checkBatchRecovered`
- `RddPlugin.onCompanionDeath`：用**死亡瞬间的真实背包**（`deathInstantCounts(body)`）填 `lostItems`

### 为什么（旧判据两处错）

| 旧判据 | 后果 |
|---|---|
| "背包里**任何一件**当初标 LOST 的东西 >0" | 33 格掉落里捡回 1 格就算整条支线成功 |
| 扫 `AssetHistory`（长期累积表） | **上一批**的物品回来替**这一批**结账 |
| `confirmRecovered(companionId, **-1**, …)` | `-1` = "最近那条"，连死两次时必然结错批 |

### 现在的判据

只认**当前支线对应的那一次死亡**，按该批次自己的 `lostItems` 逐项核对
`min(当前持有, 当次丢失数)`，**全部可核对条目都回到背包**才算满足；
部分找回只发 `repair_task_progress{deathSeq, trackedItemKinds, outstandingItemKinds, fraction}`。

**刻意不做的事（GPT-6 审核 R2）**：不引入 `0.8` 之类未经验证的法定比例。
现在这条判据是"逐项核对"，比例策略要单独一批、有实机数据再定。
`lostItems` 为空的旧批次 → `tracked=0`、永不自动判成功，需宿主显式
`confirmLost/confirmRecovered` 收口（宁可保守，不假装已核对）。

### 入口 / 出口

- 入口：`RddRepairDispatch.onDeath(…, death)` 记 `OPEN_DEATH_SEQ`
- 出口：`RddDetector.tickRuntime` → `deathDropsBackInInventory` → `onRepairSuccess`
- 事件：`repair_task_progress`（进度）、`repair_task_succeeded`（结账，带 `deathSeq`）

## 3 · F5 `asset_key` 持有 vs 累计（假完成）

### 改了什么

- `HardCodedEvaluator`：新增 `MODE_HOLD` / `MODE_ACQUIRE` / `modeOf` / 三参重载 `matches(condition, counts, baseline)`
- `TaskChain`：新增 `acquireBaselines`（`Map<subtaskId, Map<assetKey,Integer>>`）+ `captureAcquireBaseline`，
  进 `toJson`/`fromJson`，`validateRestoredState` 校验引用完整性；
  `resumeFromReplanning` / `replaceCurrentSubtasks` 清掉作废二级的基线
- `activateCurrent*` 三个入口在把二级置 RUNNING 时**顺手捕获基线**（单一捕获点，不会漏）
- `RddChainFactory.validateCondition`：建链期就拒未知 `mode`
- `RddDetector.conditionMatches` + `acquireBaselineFor`

### 为什么

实机派"收集 wheat_seeds x10"，她背包天生 33 个 → `hold` 判据当场秒过 → 二级 COMPLETED，
**她一件都没种**。持有语义对"现在手里够不够"是对的，对"这一步有没有真干活"是错的。

### 关键取舍

- **`mode` 缺省 = `hold`，与改动前逐字一致**（两参重载完全没动，测试逐条断言等价）。
- **`acquire` 算净增量**（当前 − 基线）："边做边消耗"会抵消收益。这是刻意的职责划分 ——
  `hold` 管"不消耗型目标"，`acquire` 管"采集型目标"。
- **基线不挂 `Subtask` record**（GPT-6 审核 R4）：`Subtask` 是计划规格，
  baseline 是运行时观察事实，混进去会污染"计划"并放大构造器/JSON/旧存档兼容面。
- **无基线 → 判未达成**（不是判达成）：拿不到基线时绝不假装达成。
- **未知 `mode` → 明确拒绝**：不静默降级成 `hold`（那正是要消灭的那类假完成）。

### 怎么用（派活时显式写）

```json
{"asset_key": "minecraft:wheat_seeds", "minimum": 10, "mode": "acquire"}
```

## 4 · F4 复活自我保护前置 + 床位维度可诊断

### 改了什么

- `RddPlugin`：`REPEAT_DEATH_WINDOW_TICKS = 180s` / `REPEAT_DEATH_RADIUS_BLOCKS = 8.0`
  + `publishRepeatDeathHint`（发 `repeat_death_nearby`）
- `RddRepairDispatch.onDeath` 新增 `repeatDeath` 分支：nudge 与支线步骤改成
  「① 立刻离开附近 ② 回基地补血/吃饱/换装备 ③ 再回来捡」，**倒计时照样带进文案**（R07）
- `BED_RESPAWN_PREFERENCE` 的值 `BlockPos` → `BedAnchor(BlockPos, dimension)`；
  维度不等时发 `bed_anchor_dimension_mismatch`（不再静默 return）；
  SPAWN 时维度不符发 `bed_respawn_skipped_dimension` 并**明确不发 TP**
- `setBedRespawnPreference` 补维度（用同伴当前维度）

### 为什么

实机 #3→#4 只隔 62 秒、坐标差 1 格：复活后没补给没撤离就回了同一个危险点，于是又死。
而"床偏好缺维度处理"是另一件事：床在别的维度时旧代码**静默 return**，
"床偏好为什么没生效"永远查不出来。

### 明确不做（GPT-6 审核 R3 + 用户已定）

- **真跨维度复活**不在本轮：`api/common` 的 `Companions.respawnDead` 在**主人所在维度**复活是
  明确设计（注释："covers dimension follow — it returns in whatever dimension the owner is now in"）。
  要改成回自己的床，同伴得独自跨维度 → 门框不完整时卡虚空 / 维度困死的死亡循环风险。
  本轮只把它从"静默丢弃"变成"可诊断"。
- **RiskGate 的接线方式**：本轮不把 `RiskGate` 塞进死亡路径。
  `RiskGate` 是"能不能进高风险维度"的前置门，而这里是"复活后先去哪"——两者不是同一件事，
  硬套会让"补血吃饭"被判成高风险动作而卡住。真正的自我保护前置 = **改变恢复决策顺序**
  （先撤离补给再回收），已由 `repeatDeath` 分支实现，且有纯函数判据 + 单测。

### 怎么验

```powershell
# 单测：RddDeathLedgerBatchTest.repeatDeathDetectedOnlyInsideWindowAndRadius
# 实机：rdd_debug_kill 连杀两次（间隔 <180s、距离 <8 格）→ rdd.jsonl 出现
#       repeat_death_nearby；同一次死亡后的 nudge 文案含"先撤离/补给"且不含"先捡包"
```

## 5 · F3 会话头按同伴隔离

### 改了什么

- 新增 `SessionHeaderResolver`（纯函数）：值含 `${session}` 才替换，`sessionValue()` 取
  `前缀 + 同伴 id 前 8 位`（不把完整 uuid 写进网关日志）
- `HttpLlmTransport`：`postSse` / `postSseAttempt` / `retryAfterDelay` / `baseRequest`
  逐层加 `perRequest` 头映射，用 `setHeader` 覆盖（同名只留一行）
- `NumenLlmClient`：缓存 `siteHeaders`，`perRequestSessionHeaders(observation)` 每次请求现算
- `numen_providers.json`：`"x-opencode-session": "numen-minecraft-${session}"`
- **`api/common` 无需改动**：`EntityAgentLoop` 4 个调用点本来就都传了 `observeRequest(...)`，
  它带同伴 uuid

### 为什么

`headers` 是 provider 级静态的：`"x-opencode-session": "numen-minecraft"` 对所有同伴是同一个值，
网关看到的是"一个会话"而不是"N 个同伴各自的会话"。

### 关键取舍

- **per-request 覆盖，不改共享 transport 的 `extraHeaders`**：transport（及其 `HttpClient`）
  被所有解析到同一 endpoint 的同伴**共用**，改实例字段会让 A 的会话值漏进 B 的并发请求。
- **只有含占位符才替换**：16 个 provider 的现有配置一个字节不用改；
  没有会话概念的站点（openrouter 的 Referer/X-Title）零影响。
- **无同伴身份（设置面板 ping、连通性测试）→ 保持配置字面值**，不猜、不炸。

### 怎么验

```powershell
gradle :ai:test --tests "*SessionHeaderResolverTest*"
# 实机：两个同伴同 provider 同模型 → 网关侧两个不同 x-opencode-session；
#       单同伴连发两轮 → 同一个值（不抖动）
```
