#### 2.0.1 ★ 起游戏只用一个命令：`mc-start.js`

```powershell
node "E:\restart developing doer\rdd-selfcompile\scripts\mc-start.js" gpt 10
```

**只有一个位置参数 = 实例名 + 运行时长（分钟）。其余全封在脚本里。**

| 你要 | 命令 |
|---|---|
| 起（默认 gpt / 120 分钟 = 2 小时） | `node …\mc-start.js` |
| 指定实例和时长 | `node …\mc-start.js gpt 60` |
| 只查状态（秒回） | `node …\mc-start.js gpt 120 --status` |
| 关掉 | `node …\mc-start.js gpt 120 --stop` |
| 只脱离启动不轮询 | `node …\mc-start.js gpt 120 --wait 0` |

**★ 不要再手写 `Start-Process … launch-mc.ps1`**（下面 2.0.2b 说明为什么）。
脚本已封死 **11 个坑**，每个都注了 memory 图谱的 entity 名，其中三个最贵：

| 坑 | 现象 | 脚本怎么处理 |
|---|---|---|
| **shell 阻塞** | 直接跑 launch-mc 等返回 → 卡死 10 分钟，而 MC 其实早起来了 | `spawn(detached)+unref`，父进程秒退，句柄不继承 |
| **参数绑定失败** | `@args` 数组 splat 是**按位置**传参 → `Instance='-Instance'`、`AutoStopMinutes='gpt'` → 游戏**从没启动**，外面只看到 java 一直是 0，**极易误判成 OOM** | 用**哈希表 splat**（按名字传参） |
| **内存不足伪装成 mod 崩** | MC 加载中途消失、零异常、没有 crash-report | 起之前查空闲内存，**<1200MB 直接拒起并说清原因** |

其余八个（已在跑还启动会撞单实例锁 ／ fallback 到底是 test 还是 gpt ／ AutoStop 默认值（2026-10-02 起为 120 = 2 小时）／ 查实例和起实例写成两个 ／ 路径含空格被拆开 ／ 退出码 0 不等于起来了 ／ `build\libs\*.jar` 整目录进 mods …）都封了，脚本注释里逐条列了对应 entity 名。

#### 2.0.2 ⚠ 为什么不能手写 `Start-Process`

```powershell
# ❌ 这条命令本身就会把 shell 卡死
Start-Process powershell -ArgumentList '…launch-mc.ps1' -Instance gpt -AutoStopMinutes 120' -WindowStyle Minimized
```

`launch-mc.ps1` 内部再 `Start-Process cmd.exe`，**子进程继承句柄不释放 → 调用方一直等**。
加长 timeout 不是解法（给 600s 就实打实等 600s）。

**2026-09-30 亲历**：用户两次当场纠正，我把它写进本文档，但**当天还是犯了第三次** ——
「写进文档」不等于「改掉习惯」。所以现在改成 **`mc-start.js` 一个命令**，让手写这条路径没有存在理由。

#### 2.0.3 判据：只看「实际发生」，不看退出码

`mc-start.js` 自己会轮询这四步，连续两次齐了才算起好：

```
① java 进程在        ② latest.log 在增长
③ session.lock 时间更新  ④ MCP 8765 可连
```

**加长 timeout 不是解法；`--status` / `--wait 0` 都是秒回或立即返回，不会卡。**

#### 2.0.4 ⚠ 两种假象：别顺着它查下去

| 你看到 | **真实原因** | 不要做 |
|---|---|---|
| **`java 进程一直是 0`** | **launch-mc 根本没被成功调用** —— 参数绑定失败，游戏从没启动过 | 别查 OOM、别查 mod 崩、别改代码 |
| **屏幕黑了 / 加载不动** | 内存不够（`FreePhysicalMemory < 1200MB`） | 直接告诉用户「关点浏览器」，别改代码 |

**参数绑定那个坑的真因**（`mc-instance.ps1:65-83` 有完整注释）：

```powershell
# ❌ 错的（2026-09-30 连坑三次）
$args = @('-Instance', $Instance, '-AutoStopMinutes', [string]$AutoStopMinutes)
& launch-mc.ps1 @args
#   ① $args 是函数内【保留自动变量】，赋值不会变成普通变量
#   ② @(...) 是【按位置】传参，不是按名字
#      → Instance='-Instance'、AutoStopMinutes='gpt'
#      → ParameterArgumentTransformationError: 无法将"gpt"转换为 Int32
#      → 游戏从来没启动，外面看只是 java 一直是 0

# ✔ 对的：哈希表 splat（按名字传参）
$launchParams = @{ Instance = $Instance; AutoStopMinutes = $AutoStopMinutes }
& (Join-Path $PSScriptRoot 'launch-mc.ps1') @launchParams
```

★ **判断依据永远是「实际发生没发生」，不是「命令返回成功没成功」**：
起没起看 **java 进程 + latest.log 在增长**（§2.0.3 四步判据），不看脚本退出码。

#### 2.0.5 脱离启动 → 短命令轮询状态

```powershell
# 进程活着吗
Get-Process java,javaw -ErrorAction SilentlyContinue |
  Select-Object Id,@{n='MB';e={[int]($_.WorkingSet64/1MB)}},StartTime

# 日志在写吗（大小 + 时间；世界加载完成的判据）
Get-Item "E:\.minecraft\versions\The Best of Twilight Forest\logs\latest.log" |
  Select-Object Length,LastWriteTime

# 世界锁更新了吗（= 服务器真的进了那个存档）
Get-Item "E:\.minecraft\versions\The Best of Twilight Forest\saves\rdd\session.lock" |
  Select-Object LastWriteTime

# 起来了没有：MCP 端口 + 关键启动行
Test-NetConnection 127.0.0.1 -Port 8765 -WarningAction SilentlyContinue
Select-String -Path "E:\.minecraft\versions\The Best of Twilight Forest\logs\latest.log" `
  -Pattern "numen-llm|\[rdd\]" | Select-Object -First 10
```

**判定顺序**：`java 进程在` → `latest.log 在增长` → `session.lock 时间更新` →
`日志里出现 [rdd]/[numen-llm] 行` → `MCP 8765 可连`。四步齐了才算起好。

**三条纪律**

| 规矩 | 理由 |
|---|---|
| **先查有没有在跑，别重发** | 重发会被单实例锁挤掉，上一轮就是这么把先起的实例弄丢的（2026-09-30 记） |
| **等状态用短命令 + 明确 sleep**，不许"一条命令等 10 分钟" | 等的是进程不是游戏；卡住的是 shell，不是 MC |
| **起游戏前先查空闲内存** | 2026-09-30 实测：总内存 7916MB、空闲仅 2379MB 时，MC 启动器 `-Xmx1536m -Xmn256m` 能挤进去，但极易 OOM 无声退出（上一轮就这么丢过一次） |

> 若某次 `launch-mc.ps1` 真的需要改（让它自己返回而不挂住），
> `scripts\` 是闭环真源，**改动要用户批准**——先问，别自己动手。

## ★ 进游戏验证 · 启动链踩坑实录（2026-10-02 实测，全部是「看起来成功其实没有」）

> 这一节记的都是**工具集自己骗人**的地方。共同形状：某个脚本打印了成功/OK，而真相在别处。
> 判据统一：**别信 LAUNCH_OK，信 java 进程 + 8765 在听 + latest.log mtime 在长。**

### 1. LAUNCH_OK 是假阳性 —— 最坑的一个

launch-mc.ps1:49 只 Start-Sleep -Seconds 3 就打印 LAUNCH_OK。
它证明的只是「cmd.exe 起来了」，**不证明 Minecraft 活着**。

2026-10-02 实测：它报了 LAUNCH_OK，游戏确实加载到 mod 阶段，然后**崩了**。

| 怀疑 | 实测 | 结论 |

## 十一、外接大脑 MCP：外部 AI 直接开同伴、派活、观察（2026-10-03 真机实测）

> 这一节是**实测结论**，不是抄文档。踩过的坑都写进去了。

### 11.1 这是什么

Numen 自带一个 **MCP server**，端点 `http://127.0.0.1:8765/mcp`。打开后，**外部 AI（我）不经过游戏内置大脑**，直接控制同伴的身体：建同伴、派动作、说话、收事件。

关键机制（源码：`api/common/src/client/java/com/dwinovo/numen/mcp/server/{McpServer,McpMode,McpConfig}.java`）：
- 外部驾驶时**内置 LLM 完全停轮**（`EntityAgentLoop.paused() = dead || isExternallyDriven()`，日志打 `tryStartTurn skipped: 停牌 (dead=, external=)`）→ **这才是省钱的机制**，不是「让 AI 自己少干活」。
- `McpMode.QUIET_AFTER_MS = 120_000`：外部客户端 120 秒没动静才算安静；`quiet_fallback=true` 才在安静期把控制权还给内置大脑（那就开始烧钱），**本机默认 false**。
- 本机 `config/numen/mcp_server.json` 的 `enabled` 已是 `true`，启动日志会打：
  `[numen-mcp] 外接大脑模式已开启 · 端点 http://127.0.0.1:8765/mcp · 外部客户端经 npx mcp-remote http://127.0.0.1:8765/mcp 接入`
  → **不需要进游戏按 G 键开面板**。
- ⚠️ 网上/旧版文档里的 `acquire_companion` / `release_companion` **本版本没有**。现在的语义是 `create_companion` 之后「直接开，无接管步骤」——对同伴调工具即接管。

### 11.2 MCP 级 6 个工具（不经游戏内 AI，最容易被忽略的一层）

| 工具 | 参数 | 返回 | 坑 |
|---|---|---|---|
| `list_companions` | 无 | **人类可读文本**（`Live companions:\n- ACX (id: …)`），**不是 JSON** | 想按名删同伴，解析它会炸；直接按 id 删更快 |
| `create_companion` | `name` [REQ] 3–16 位字母数字下划线 | 新同伴 id | 建出来是 **survival 模式、满血、跟玩家脚下** |
| `delete_companion` | `companion` [REQ] name 或 id | 文本确认 | **会丢背包**；删之前先确认它不是在烧钱 |
| `get_events` | `companion` [REQ]、`wait_seconds` 0–60（默认 2） | 长轮询：主人说话=`<query>`、世界动静=`<event>` | **读掉即消费不丢**；开车时每 2 秒调一次 |
| `say` | `companion`+`text` [REQ] | 文本 | 以同伴身份说话（聊天行+气泡+语音），连发排队 |
| `enqueue` | `companion`+`text` [REQ] | 文本 | Assist 模式注入内置 AI；**驾驶模式下会被拒**（`TO_EXTERNAL_BRAIN`） |

另外 40+ 身体工具（goto/mine/build/attack/…）+ 各插件工具（`acx_*` 8 个、`rdd_*` 7 个等）也全部经这个端点暴露。

### 11.3 开车三步（真机跑通过的顺序）

```powershell
# 1) 起游戏（MCP 在起完后 ~90-175 秒就绪）
Start-Process powershell.exe -ArgumentList '-NoProfile -ExecutionPolicy Bypass -File "E:\restart developing doer\rdd-selfcompile\scripts\launch-mc.ps1" -Instance gpt -AutoStopMinutes 40' -WindowStyle Minimized

# 2) 建/查同伴
node rdd-selfcompile\scripts\numen-mcp.js call list_companions
node rdd-selfcompile\scripts\numen-mcp.js raw  tools/list '{}'      # 76 个工具的完整 schema

# 3) 派活
node rdd-selfcompile\scripts\numen-mcp.js call goto '{"companion":"ACX","x":938,"z":791}'
```

⚠️ **PS 里内联 JSON 会被引号拆坏**（报 `Expected property name or '}' at position 1`）。一切带参数的调用都写成 `.js` 脚本，用 `execFileSync('node', [mcpScript,'call',tool,JSON.stringify(args)])` 传数组。

### 11.4 ★ 同伴的「自保本能」会抢戏

`get_self_status` 的工具描述里写明了同伴自带 6 项反射：落水自浮、坠落水桶、岩浆上浮、被卡住自己挖方块、憋气上浮换气、被冰封游向透气处、**身边有危险自动开打**。但**显式动作永远优先**（`equip_item` 显式穿戴会钉住槽位，`item_id="auto"` 解除）。

真机踩到的：
- 同伴淹死 → 所有工具调用被拒 `她刚死了,正在复活途中——等复活事件到了再派`；复活要 `SafeSpawn.findNear` 在**主人附近**找到安全落点，主人旁边是水就永远出不来。
- 主人手动杀了同伴 → 背包全丢（0/41）、`rdd_status` 的子任务卡 FAILED、primary 一直 REPLANNING。
- 想让 AC 独占身体，正门 `rdd_standby action=pause` 只在子任务 RUNNING/PENDING/STALLED 时有效（失败文案：`cannot stand by: the current subtask is FAILED`）；更简单的办法是 `task_stop`（停当前身体任务）+ `fc_control action=disable`（关自保反射层）。

### 11.5 三种结果形状（解析前必须认清）

Numen 的工具回执**不统一**，解析写错就会误判「什么都没发生」：
1. 严格信封：`{success, message, timed_out?, interrupted?, data?}`（`TaskResult`）
2. **裸 JSON 无 success 字段**：`get_self_status`、`scan_blocks`、`scan_nearby_entities`、`inspect_block`、`get_world_info` 都是这一类
3. 纯人类文案：`lookup_recipe`、`list_companions`、MCP 级工具

安全写法：`const es = r.entities || (r.data && r.data.entities) || []`（2026-10-02 我写成 `(r.data && r.data.entities) || []`，结果把「扫到 3 个实体」报成 0 个，差点误判成世界有问题）。

### 11.6 花钱看哪里

`latest.log`（**GBK**，用 node `new TextDecoder('gbk')` 读）里搜 `[numen-llm]`：`client initialised: provider=… model=…` 和每次 `chat done`（含耗时/finish 原因/token 累计）。2026-10-02 实测一个卡死的同伴一分钟内 5 次 `chat done`、累计 token 30072→31604 —— 这种就是纯烧钱，`delete_companion` 掉。
