## 〇 · 为什么需要这个机制（事故记录，不是理论）

**事故**：`61-任务链功能线全景与回归固化方案-20261002.md` 同一天里有两节 ——
§二 是「T1–T9 **动工前**的洞点审计表」，§八 是「T1–T9 **已实施**（9 个测试类 / 154 项）」。
我（AI）只读了 §二/§2.1/§2.3 就下结论：

> 「RL-2/3/4/8/9/11/12/14/18 这 9 条红线的实现改了不会有任何测试变红」
> 「M1 / M4 / M5 完全裸奔」「🟢3 / 🟡7 / 🔴12」

用户当场质疑：**「你是说没有补红线测试？怎么可能？你去核实一下」**。
实测：PinTest 从 2 个变成 **7 个**，另有 4 个契约类，共 11 类 / 154 项。**整段结论是假账。**

**根因不是记错，是文档没有「核对时点」这个维度。**
一份文档里同时存在「某天的快照」和「今天的现状」时，读者**没有任何办法**从文档本身分辨。
`30` 开头「数字引用规约」和 `50` §三「已知过期」都警告过这件事，但那是**给人看的警告**；
本次事故证明**警告挡不住**——因为当时根本没读那两节。

⇒ 结论：**警告不算机制。** 机制必须能被机器判、且默认阻断。

## 二 · 台账字段与填写纪律

```jsonc
{
  "file": "61-任务链功能线全景与回归固化方案-20261002.md",
  "role": "锚",                    // 锚=真源 / 索引 / 纪实 / 参考
  "ttlDays": 3,                    // 距上次核对超过这个天数就 OVERDUE
  "lastVerified": "2026-10-03",    // 只允许在「本人本次真的逐条核过」时填
  "verifiedBy": "opencode:stealth/space-bunny-alpha",
  "scope": "§二 固化审计 + §八 T1–T9 实施态；补 §2.4 对照表",
  "evidence": "11 个测试类逐类 grep + gradle 实测；本轮补 2 个 pin 类 17 项",
  "found": "RL-4 与 RL-7 原判 🔴 裸，本轮补 pin 后转 🟢"
}
```

### 五条硬纪律

1. **读一遍不算核对。** 必须「逐条对着判据验一遍」，判据要能被别人重跑。
2. **`scope` 必须写清覆盖到哪一节**，不许写「全文」。`61` 这种 400 行的文档，
   只核了 §二 和 §八 就在 `scope` 里写这两节 —— **不许让它冒充「整份已核」**。
3. **`evidence` 必须写清判据**（grep 计数 / gradle 实测 / jsonl 实测 / 实机），
   「看过了」「已确认」不算。
4. **核对之后又改了文档 → 该条核对自动作废**（`STALE_EDIT`）。这不是苛刻：
   本次事故正是「文档被改过，而结论还挂在旧时点上」。
5. **git 最后改动日期不能代替 `lastVerified`** —— 见 §七。

### `ttlDays` 怎么定（按「被引用次数 × 过期危害」定，不按篇幅）

| role | 默认 ttl | 判据 |
|---|---|---|
| `锚`（红线/总纲/契约/审计） | **3 天** | 别人会直接照它写码 / 下结论 |
| `索引`（`00` / `50` / `README`） | 7 天 | 指向别的文档，指向错了全错 |
| `纪实`（运维/证据/实机纪要） | 14 天 | 记录当时发生了什么，事后核对即可 |
| `参考`（评审意见/外部对照/基线快照） | 90 天 | 不作为决策依据 |

## 三 · 它查的五种过期形态（每种对应一种真实的翻车方式）

| 代码 | 含义 | 对应的真实翻车 |
|---|---|---|
| `MISSING_FILE` | 台账登记了但文件不在 | 文档被删/改名，台账变成指向虚空的地图 |
| `UNREGISTERED` | 目录里有文档但台账没登记 | **新增文档忘了进机制 ⇒ 机制立刻对它失效**（这正是本次事故的形态） |
| `NEVER_VERIFIED` | 登记了但 `lastVerified` 为空 | 读者分不清「这是现状」还是「这是某天的快照」。默认只报告，`--strict` 才阻断 |
| `OVERDUE` | 距上次核对超 `ttlDays` | 文档没变，但**代码变了** —— 文档悄悄过期 |
| `STALE_EDIT` | ★ **核对之后这个文档又被改过** | 那次核对的结论不再覆盖当前内容；**本次事故就是这个** |
| `DUP_NUMBER` | ★ 两份文档用了同一个编号 | **2026-10-03 实测发生**：我建「64-未接线审计」的同时，并行会话建了「64-两条数据流总览-大白话」⇒ 编号撞号（本工作区常态）。已把本文的配套审计文档改号 `66`。**编号是这套文档唯一的排序与引用键**，撞号会让「见 64 §三」指向不明 ⇒ 建档前必须先确认号没被占 |

`STALE_EDIT` 是这五条里最有价值的一条：它把「核对时点」和「内容时点」绑在一起，
杜绝了「核对一次、之后随便改、结论还挂着」。`DUP_NUMBER` 是**建档那一刻**就该拦的东西 ——
它是本机制建起来之后**当场逮到**的第一个真问题（不是演练出来的）。

## 四 · 怎么接进门禁

`check-doc-freshness.js` 返回 `2` 时**阻断**。建议挂两处：

1. **`stager check` / `loop-gate` 之前** —— 收口阶段必须过（文档过期就不许收工）。
2. **任何一次改代码之后** —— 改代码会让「代码现状」变，而锚类文档的 `lastVerified` 不会自动变，
   于是 `OVERDUE` 会自然逼近。这是有意的：**改代码就该顺手核一次文档**。

> ⚠️ **不许为了让门禁过而把 `ttlDays` 调大或把 `lastVerified` 刷成今天。**
> 那等于把机制改回「警告」，而本次事故已经证明警告挡不住。
> 真核不动就降级 `role`（从「锚」降成「参考」）并写明理由 —— 那是诚实动作，不是赖账。

## 七 · 为什么不能用 git 日期代替「最后核对日」（实测数据）

台账建立时顺带统计了全目录 74 份文档的 git 最后改动日：

```
2026-10-01（入库日）：67 份
2026-10-02：7 份
2026-10-03：2 份
从未被 git 跟踪：7 份
```

**67 份挤在同一天不是巧合 —— 那是知识库入库的那一天。**
所以 git 日期回答的是「什么时候进库的」，不是「什么时候最后核对的」。
用它当核对时点 = 用「2026-10-01 全部已核对」冒充事实。**这就是必须显式记 `lastVerified` 的原因。**

### 顺带查出一条更严重的问题：7 份文档从未入库

其中 **`62-统一队列契约与自学习闭环.md`（85 行）** 正是第二批队列字段契约的真源，
`git status` 显示是 `??` 未跟踪。**未入库 = 无历史 = 磁盘故障全没**
（`AGENTS.md` 记载「317 份文档已入 git」之后新增的文档都在这个坑里）。

**纪律：新增文档当天就要 `git add` + `commit`，不要攒。** 台账机制的 `UNREGISTERED` 只管漏登记，
管不了漏提交 —— 后者要靠提交纪律。
