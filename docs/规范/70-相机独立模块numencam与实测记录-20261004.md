## 一、为什么要抽出来

原来的 `CameraRig` + `MixinCamera` 躺在 `api/common/src/client/java/` 里，是引擎的一部分：

- `CameraRig` 291 行，纯客户端策略层（读 `cam.json` → 模式 + 参数 + 阻尼）
- `MixinCamera` 215 行，`@Inject` 到 `Camera.setup()`，**把原版 `Camera` 的
  `setup` / `move` / `getMaxZoom` 逐条搬过来变成自己的算法**
  （类注释里明写「用户要的是后面能改算法，所以整段搬进来自己算」）

它不 import 任何 Numen 引擎类（只依赖 Minecraft 客户端 + Gson + 一个 MOD_ID 常量），
和引擎其它部分零耦合 —— 所以能干净地拆出去。

### ★ 怎么把指令送进游戏（最容易卡住的一步）

**不要用 OpenClaw 发指令。** `neoforge-mod\InputHandler.java` 只有 7 个分支
（`W A S D SPACE LEFTSHIFT LEFT_CONTROL`），而 `CommandHandler` 的名字→键码表映射了 20+ 个键 ——
`t` / `escape` / `enter` / `ctrl+a` / `delete` **全部落空**，回执照样 `success:true` 但什么都不会发生。
所以 `oc-send.js --chat`（t→ctrl+a→delete→typeText）**设计上就不可能通**。

可用配方（实测 20+ 条指令全部送达）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File `
  "D:\rdd\harness\rdd-harness\bin\send-mc-command.ps1" -Text "/cam status"
```

= `Focus-MinecraftWindow`（`mc-focus.ps1`，AttachThreadInput + ALT 抬落抢焦点）
→ `Set-Clipboard` → `SendKeys 't'` → `^a` → `^v` → `{ENTER}`。
文本里不能含 SendKeys 元字符 `^ % + ~ ( ) { } [ ]`（`/cam` 系列不含）。

## 四、三个子系统的设计要点

### `CompanionTether`（绑定 + 牵引）

| 决策 | 理由 |
|---|---|
| 「离开加载区」的判据 = **客户端** `entitiesForRendering()` 里找不到（`CameraRig.resolveTarget()` 返回 null）连续 **40 tick(2s)** | 服务端有整套加载区体系（`CompanionChunkLoader` 票据 / `ChunkLoadedTest` / `LoadedOnlyView`），但客户端侧 0 命中。**且必须连续 40 tick** —— 否则「刚传过去→那格还没加载→再传」每 2 秒抖一次死循环 |
| 传送后冷却 **100 tick** | 同上 |
| 传送走 `sendCommand("/tp @s <x> <y> <z>")` **传坐标不传名字** | `LocalPlayer` 没有 `teleportTo`/`setPos`，客户端改坐标会被服务端反传送拉回 → 只能用 `ClientPacketListener.sendCommand`。**按名字传会落在它脚下正中**，它站窄处/墙边时会把玩家挤进方块里 |
| 无 `hasPermissions(2)` 时明确报「单人游戏要开作弊」 | 不静默失败 |
| `mc.screen != null` 时不动玩家 | 别在玩家看菜单时把人拽走 |

### `FastMove`

- **自动疾跑**每 tick 直接 `player.setSprinting(true)`，**不是** `keySprint.setDown(true)` ——
  后者只是「获得许可」，原版还有 7 tick 的 `sprintTriggerTime` 窗口 + 5 个前置条件
  （有前进 impulse / 饥饿>6 / 不在水中 / 未用物品 / 未失明）。
- **飞行必须每 tick 重申** `mayfly=true; flying=true; onUpdateAbilities()` ——
  原版 `LocalPlayer` 有 `if (onGround() && abilities.flying && !isAlwaysFlying()) flying = false;`，**一落地就自动关**。
- 速度：`abilities.setFlyingSpeed(0.05f * 倍数)`。**`Abilities` 没有 `setWalkSpeed`** → 只能加速飞行，不能加速行走。

### `VideoRecorder`

- 抓帧：`Screenshot.takeScreenshot(mc.getMainRenderTarget())` → `RenderSystem.recordRenderCall` 做 GL 读回 → `Util.ioPool()` 线程写盘。
  **`NativeImage.close()` 必须放在 IO 任务的 finally** —— 放早了下一帧读到已释放内存，整段视频花掉。
- **落盘序号 `outIndex` 与抓帧计数 `frameIndex` 必须分开**（见下面 bug 1）。
- 去重默认**关**（见下面 bug 2）。去重实现用 8×8 采样点哈希（逐像素是 92 万次 JNI，太贵）。
- 找 ffmpeg：先查 PATH，再扫 `~/AppData/Local/Microsoft/WinGet/Packages/*FFmpeg*/**/ffmpeg.exe`
  （**不写死版本号**）。编码 `libx264 + yuv420p`，**yuv420p 要求偶数宽高** → 加 `-vf scale=trunc(iw/2)*2:trunc(ih/2)*2`。
- 封盘三步**全异步**（轮询 pendingWrites → 写 `numencam.txt` → 守护线程起 ffmpeg → 轮询 `Process.isAlive()`），
  `/cam rec stop` 才能立刻回执不阻塞游戏线程。

## 五、修掉的三个 bug（都带复现证据）

### bug 1 · 录像只出 1 帧

ffmpeg 的 image2 解码器把 `%05d` 当**连续序列**读，遇到第一个序号缺口就停止解码。
我原来用「抓帧序号」当落盘文件名，去重后留下 `f_00000,f_00010,f_00011,…,f_00068` → **160 帧只编出 1 帧**。
修法：落盘序号 `outIndex` 与抓帧计数分开，文件名用 `outIndex++`。

> ★ **验收录像必须看 `ffmpeg.log` 的 `frame=` 是否等于 PNG 张数**，不能只看 mp4 文件存在。
> 这类故障的特征是「回执正常、PNG 都在、mp4 也生成了」，只有一行 `frame= 1` 暴露真相。
> （这条已写成时间锁 `TL-2026-10-04-01`，并做成了 harness 门禁的 `Q7` 自动检查。）

### bug 2 · 视频退化成定格动画

8 秒 10fps 只落 12 帧（`dropped=70`）—— 站着不动画面完全静止，去重默认开启把视频变成了 1.2fps 定格动画。
**录视频要的是连续时间轴，站着不动也是一段真实画面。** 去重改成可选参数（`/cam rec start [fps] [dedupe]`），默认关。

### bug 3 · `oc-send.js --walk` 的位移判据从 2026-09-30 起一直无效

`posOf` 写死了 `/"position":\{"z":…,"y":…,"x":…/`，但 mod 侧用 `java.util.Map.of(...)` 造这个 Map，
而 **`Map.of` 的迭代顺序是 JVM 次序随机化（SALT）** —— 这次回 `x,y,z`，下次回 `z,y,x`。
后果：`--walk` 几乎总是走 `pos parse failed`、退出码 8，位移判据形同虚设。
没人发现，因为它的失败方式是「报 parse failed」而不是「报错」。

> **通用教训**：凡是「解析上游 JSON 再算判据」的脚本，都要先确认上游 JSON 的字段顺序真的稳定 ——
> LLM 生成的 JSON 和 `java.util.Map.of` 生成的 JSON 都不稳定。
> （时间锁 `TL-2026-10-04-02`）

## 七、★ 最重要的一个发现

**live 实例 `cam.json` 里的 `target: "RDD"` 从来没生效过。**

`CameraRig.resolveTarget()` 只在客户端 `entitiesForRendering()` 里找 `AbstractClientPlayer`，
按名字做 `equalsIgnoreCase` 匹配；**找不到就返回 null，mixin 不取消 → 静默退回原版第一人称，不报任何错**。
而真实同伴叫 `ACX` / `DDD` —— `"RDD"` 匹配不到任何人。

这正是「配了跟拍相机、截图却全是第一人称」的根因。改成同伴真名后 5 模式全部正常。

> 这是一次典型的**智能性错误**（看起来做对了 / 静默通过，实际没生效）。
> 已记为时间锁 `TL-2026-10-03-01`，guard = 「相机 status 打印『（渲染范围内）』；不在就明确说匹配不到」。
> 防复发：`/cam status` 会打印 `target=ACX（3 档（渲染范围内））`，
> **匹配不到时打印的是明确的失败文案，不是静默退化成第一人称**。
