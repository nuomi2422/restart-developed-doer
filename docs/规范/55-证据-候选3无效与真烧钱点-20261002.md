## 三、为什么没生效（根因，两条）

### 3.1 `slimStaleExpansions` 的「保留最后一次」规则把要压的东西全留下了

代码逻辑：倒序找**最后**一个含展开块的 `Msg.Tool` 作 `last`，只压 `last` 之外的。

实测：`slimmed` 标记在 245 条请求里只出现 **3 次**（1.2%）。
原因：replay 窗口中位只有 12 条消息，而 `find_tools` 是**每轮都在调**的工具
（`select:rdd_status` 单独就出现 10 次）—— 窗口里**几乎永远只有 1 个展开块，而它就是最后一次**。
「陈旧展开块」这个概念在实测的会话模式里**几乎不存在**。

### 3.2 真正烧钱的是「一次展开太多」，不是「放太久」

`probe-expansion.js` 量到历史里 **101 个** RAW 展开块实例，规模分布：

| 次数 | 规模 |
|---|---|
| 31 | 1 工具 / <1500 tok ← 正常 |
| 19 | 3 工具 / 1500–4000 |
| 15 | 2 工具 / **>8000** |
| 9 | 3 工具 / 4000–8000 |
| 7 | 4 工具 / 1500–4000 |
| 5 | **8 工具 / >8000** |
| 4 | 5 工具 / 4000–8000 |
| 其余 | 3–7 工具 / >8000 等 |

**最大单块 = 17,041 字符 = 4,260 tok**，一次展开 8 个工具，拆开看：

| 工具 | 字符 | est tok |
|---|---|---|
| **`build`** | **8,657** | **2,164** ← 占一半 |
| `interact_at` | 1,639 | 410 |
| `mine` | 1,352 | 338 |
| `attack` | 1,258 | 315 |
| `craft` | 1,070 | 268 |
| `equip_item` | 1,089 | 272 |
| `inspect_gui` | 1,012 | 253 |
| `lookup_recipe` | 788 | 197 |

合计 101 个实例 = **124,805 token**，平均 1,236 tok/实例。

**模型在反复要同一批工具**（从 `find_tools` 的 query 反查）：
- `select:rdd_status` × **10**
- `select:equip_item,interact_at,mine` × **8**

## 五、局限（不藏着）

1. **只验了一个会话、一种模型**。换模型后 `find_tools` 的调用频率会变，结论可能不适用。
2. **est tok 是我自己估的**（CJK/1.5 + ASCII/4），不是 provider 报的 `promptTokens`——`llm_request` 事件里**没有** `promptTokens` 字段（只有 `llm_response` 有），所以这里只能估。真实降幅要以 `latest.log` 的 `tokens=` 为准，而那个我没有做同会话严格配对。
3. **没跑单元测试**。本轮及上一轮改的 4 个 `RddV32DirectivesTest` 至今未执行（`run-mutation.ps1` 不跑 test task）。
4. **候选 3 的代码仍在 jar 里生效**（它只是几乎不命中，没有副作用）。要撤有备份 `.pre-slimtooldef-20261002.bak`。
5. **归因链断在「为什么模型这么爱 find_tools」**：是 system prompt 的 `<deferred_tools>` 目录不够用（我上一轮把摘要从 96 字砍到 40 字，可能反而加剧了），还是模型习惯性探索——**这一条本轮没查**。
