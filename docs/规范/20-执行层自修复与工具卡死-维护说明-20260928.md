## 一、「工具卡死」：症状 / 根因 / 怎么验

### 症状
游戏退出后，调用它的 shell 命令**永久不返回**（上层 AI 的 Bash 调用一直等）。用户 2026-09-28 报。

### 两个根因（叠加，缺一不成立）

| # | 根因 | 机理 |
|---|---|---|
| 1 | `numen-mcp.js` / `redline-watch.js` 的 `post()` **无任何超时** | Node 的 `http.request` **默认永不超时**。游戏关闭中途 8765 仍在 `LISTEN` 却不再应答 → `end` 与 `error` 都不触发 → Promise 永不 settle → node 永不退出 → shell 永不 EOF。`redline-watch.js` 一轮发 3 次请求，任一卡住整条挂死，而它按规范是**常开巡检**，必然复现 |
| 2 | 启动 bat 结尾是 `pause` | 游戏退出后 `cmd.exe` 永远等按键；`launch-mc.ps1` 当时既没隐藏窗口也没重定向输出，那个永不退出的控制台会占住调用方管道 |

### 改了什么
- `scripts\numen-mcp.js`、`scripts\redline-watch.js`：`post()` 加 `req.setTimeout(CALL_TIMEOUT_MS)`、
  整体 `guard` 定时器、`settled` 去重；文件头加一条整命令 `RUN_DEADLINE_MS` 兜底（到期 `exit 2`）。
  默认单次 20s / 整条 120s（redline-watch 15s / 60s），可用环境变量覆盖。
- `scripts\launch-mc.ps1`：启动器输出**重定向**到 `mutations\launch-<instance>.log`（+`.err`）、
  `-WindowStyle Hidden`、记 `launcher.pid` 进 `phase-launch.json`；看门狗也加了输出重定向，
  并把 `-LauncherPid` 传下去。
- `scripts\mc-watchdog.ps1`：新增 `Remove-StaleLauncherConsole`，游戏一走就回收残留 `cmd.exe`；
  顺带修好了**从来没生效过**的重复检测（见 §三）。
- 新增自检三件套（见 §四）。

### 怎么验（不用开游戏）
```powershell
node "E:\restart developing doer\rdd-selfcompile\scripts\_selftest\test-mcp-timeout.js"
```
- 期望 `SELFTEST_RESULT pass=3 fail=0`，三条都是 `usedTarget=true viaTimeout=true`、耗时 ≈3s、`exit=1`。
- 第三条 `legacy-hang.js (causation)` 是**因果证明**：修复前的 `post()` 复刻件必须 `exit=null`
  被 SIGKILL。如果它自己退出了，说明根因判断错了，要重查。
- ⚠️ 判据不能只看 `exit != 0`：第一版就假通过了一次（`redline-watch` 没遵守 `NUMEN_MCP_PORT`，
  靠 `ECONNREFUSED` 蒙对）。必须同时要求打到了目标端口、且是靠超时脱身。

## 二、执行层四修（core/common，编进 `numen-neoforge-*.jar`）

四个判据都按 `SurvivalDecisions` 的既有约定抽成**可无头单测的纯类**（不碰 Minecraft），
测试放 `core/common/src/test/.../task/{collect,mine,chain}/`。

| 缺陷 | 旧行为 | 新行为 | 判据类 / 测试 |
|---|---|---|---|
| 拾取假成功 | 见 `ItemEntity.isRemoved()` 就 `collected++`：被烧/被抢/despawn 一律算战果 → 「扫完了 n 件」而背包里没有 n 件 → 上层看 SUCCESS 就打勾 | 归属**只由背包增量证明**（同 `MineCompanionTask` 的 baseline 机制）；新增 `SETTLE` 相等 `SETTLE_TICKS=3` 让原版结算完再对账；分项记 `vanished`/`unreachable`/`left_behind` | `CollectDecisions` / `CollectDecisionsTest`（10） |
| 落地水丢账 | 快窗口到点**或被更高优先级反射抢占**时一律 `placed=null`：水既没收回也没记录，永久留在世界里；软方块分支连台账都没有 | 快窗口**只让身体不销账**，水还在就转 `CLEANUP_BUDGET_TICKS=200` 清理窗口；`stop()` 不再无条件销账；收不回来**必须留日记**；软方块只记位置、**不自动拆**（她可能正站在上面） | `TempResourceRules` / `TempResourceRulesTest`（8） |
| 上浮反复无熔断 | 反射做完就休眠，被打断的任务恢复后再做一遍同样的事（下水→上浮→又下水），无任何一句话说清原因 | 记同一片水域的反复上浮，第 3 次起把「这儿做不成，换个法子」报给上层。**只报告不阻断**——氧气见底就得浮 | `BreathEpisodeRules` / `BreathEpisodeRulesTest`（10） |
| 部分收工不可判 | 工具 SUCCESS 契约是**有意**的「附近采不到更多，采到部分也算成功」，未改；但上层没字段可判，只能看 SUCCESS 打勾 | `resultData` 增 `partial`/`shortfall`/`note`，把缺口变成机器可判 | `PartialGather` / `PartialGatherTest`（8） |

### ⚠️ 部署到哪个 jar（最容易踩）
执行层类**不在**插件 jar 里，在 **`core:neoforge`**：
```powershell
gradle :core:neoforge:jar     # -> core\neoforge\build\libs\numen-neoforge-*.jar
```
现成的 `build-jar.ps1`/`deploy.ps1` 由 `config.ps1` 的 `PLUGIN_MODULE=plugins:selfcompile` 驱动，
**只覆盖插件层**，照它走会部署错 jar 然后验证了个寂寞。core 层改动必须手工构建。
部署后必做：打开 jar 确认新 `.class` 都在（本次验了 4 个），否则「编译成功」与「行为生效」之间没有保证。

## 三、顺带修掉的两个既有缺陷

1. **`mc-watchdog.ps1` 重复检测从来没生效过**。它拿 `$SelfMarker='rdd-watchdog-'+Instance` 去匹配
   子进程命令行，可 `launch-mc.ps1` 从来没把这个标记传下去 → 判据永远匹配不到。实测同一 gpt 实例
   并存两个看门狗。已改为匹配真实存在的 `-Instance <值>`，实测手动再跑立刻返回
   `WATCHDOG_EXIT_DUPLICATE`。
   **教训**：进程互斥判据必须落在子进程命令行里**真实存在**的字符串上。
2. **`mc-watchdog.ps1` 缺 UTF-8 BOM**。PS 5.1 无 BOM 时按 GBK 解码，UTF-8 多字节序列会吞掉换行
   导致解析失败（表现为「表达式或语句中包含意外的标记 }」，而文件内容是合法 UTF-8）。已补 BOM，
   与本项目 `launch-mc.ps1`/`every-10min-drive.ps1` 的既有约定对齐。注释里别写反引号。
