## 一、结论

**这套架构值得继续做，不需要推倒重来。** 几种职责已经分开：

| 角色 | 干什么 |
|---|---|
| 规划 AI | 选目标、组织路线、查高层经验 |
| 执行 AI | 面对现场、选工具、用脚本、记下值得复盘的事 |
| 脚本状态机 | 接管已明确的步骤/分支/循环，**减少每步都等模型回答的延迟** |
| 学习者 | 复盘现场材料，形成可复用的候选产物 |
| 经验库 | 保存 / 检索 / 呈现 / 接受验证与反例 |
| 携带器 | 在合适时机提醒执行 AI |
| 外部编程工具 | 改源码、编译、部署、验证 |
| 监测台 | 把过程展示出来供人工审核 |

★ **两处分工最值得继续保持**：
① **「现场执行」与「事后学习」分开** ② **「模型决策」与「程序实时执行」分开**

### ★ 当前阶段的准确定位

> **主要模块已经成形，进入「跨模块契约 + 真实闭环」的验收阶段。**
> **不是「只差几行收尾」。**

⚠️ 此前「剩余代码约 2000–3000 行 = 现有 9.8 万行的 2–3%」这个估算**不足以代表完成度**；
**测试行数占比高也不能证明架构健康** —— 两者都只说明「代码量」，不说明「契约对不对、真机跑过没有」。

## 二、要守住的六条边界

### 边界 1 ·「被呈现过 ＋ 后来任务成功」≠「这条经验被证明有效」

**现状**：配对规则是「给 AI 看过一条经验 → 找它之后第一个结束的任务 → 供回报时参考」。

**风险**：★ 这是当前最重要的风险。**它只能提供候选关联，不能证明因果。**
例如：刚看过一条挖矿经验、随后完成的是走路任务；或挖矿成功但根本没采用那条经验
—— **两种情况都不该给这条经验增加成功验证**。

**应该分开的五步**：
```
被呈现 → 明确采用了哪条 → 用于哪个任务/哪次尝试
        → 动作与结果是否支持它 → 才决定加支持或记反例
```
⇒ **固化底线：仅凭时间相邻，不得自动升级或降级经验。**
现配对规则可保留为**辅助信息**，但必须标成「可能相关」而不是「成敗判据」。

### 边界 2 · 模拟通过 ≠ 真实成功 ≠ 可以自动上线

**现状**：此前的说法是「把真端口换成假的返回值，就是不碰世界的模拟运行」——**这个说法需要收窄**。

**假端口能验什么**：分支与循环是否正确、参数引用是否正确、暂停/恢复/失败处理是否正确。
**假端口验不了什么**：真能走到目标、真能挖到东西、真不会破坏世界、真实异步动作的时序。

**必须分四级**：
```
结构校验通过 → 模拟执行通过 → 受控实机验证通过 → 满足上线条件
```
★ **「连续三次成功」还必须属于同一脚本版本 + 明确的验证条件** ——
脚本改过就**不能拿旧版本的成功次数给新版本背书**。

### 边界 3 · 脚本状态机最危险处：受理 / 完成 / 暂停 / 失败混在一起

**现状**：此前的判据是「暂停没带原因 = 正常受理；失败一定带原因」。
⚠️ **这个判据不够可靠，不许固化为红线。**

**必须守住的红线**：
| # | 红线 |
|---|---|
| 1 | **接下任务 ≠ 完成任务** |
| 2 | **脚本在等 ≠ 身体动作已停** |
| 3 | **等回执超时 ≠ 世界里的动作一定失败** |
| 4 | **恢复执行不能重复发出已经受理的动作** |
| 5 | **取消后，迟到的成功回执不能把这次运行重新变成成功** |

⇒ 这一组的优先级**应当高于页面统计与中文提示** —— 它直接决定会不会**重复挖、重复走、重复消耗资源**。

### 边界 4 · 学习者要保留现场材料，但**不能把执行 AI 的归因当事实**

**现状**：owner 的方向是「执行 AI 写带现场归因的草稿 → 学习者编辑、校验、补全，不重写正文」。
**这个方向对，但不要定成「绝对不许重写」。**

★ 建议改成：
> **原始材料保留；整理后的经验可以修订，但要能看出改了什么、依据是什么。**

**必须分开的三样东西**：
| 内容 | 性质 |
|---|---|
| 实际发生的动作 / 位置 / 结果 | **证据** |
| 执行 AI 认为为什么发生 | **现场假设** |
| 学习者整理出的规律 | **待验证结论** |

⚠️ 同一个队列存这几类材料**本身不是架构错误**；
**缺的是来源标识、关联依据、以及不同的处理规则**（见 68 号 D-3）。

⚠️ 顺带更正一句话：「系统日志不能造假」**说得太绝对** ——
**日志也会漏写、错写、截断、串对象**（此前已实测抓到过多起）。

### 边界 5 · 世界状态要统一口径，但不必强制全部绕磁盘

**现状**：owner 的意图是「统一一个地方抓取世界状态并落盘成只读快照」——**统一是对的**，
但前面推导成「必须统一落盘、其他插件只读文件」**不是唯一答案**。

**真正需要统一的是口径，不是介质**：
- 这是**谁**的状态
- **哪个世界、哪个时刻**采的
- 哪些字段**来自同一次采样**
- 哪些字段**未知或已过期**

⇒ **文件适合留证与事后复盘；执行时的实时判断需要明确的新鲜度。**
否则虽然大家读同一个文件，也可能**共同读到过期状态**。

⚠️ **未核实**：目前不能仅凭「存在一个世界事实模块」就认定**全项目已经有统一出口**。

### 边界 6 · 三种「分级」要分别验收，不许用一句「已经分级了」带过

| 分级 | 控制什么 | 现状 |
|---|---|---|
| **目录 → 正文** | 一次给 AI 看多少内容 | ✅ 有证据 |
| **受众（规划者／执行者）** | 给谁看什么内容 | ⚠️ **未核实是否所有入口都生效** |
| **携带器提醒顺序** | 什么情况下先提醒什么 | ⚠️ **「擅自填了留白」这条判断下得太快** —— 要先核当时的批准设计与变更记录，不能只看「代码里有顺序判定」 |

## 三、固化顺序（owner 计划的四步，加一层「先固化语义」）

★ **关键：先固化正确语义，再把现有实现锁住。**
否则会把**今天的误解一起写成红线**。

| 优先级 | 要守住的红线 | 关键回归场景 |
|---|---|---|
| **第 1 组 · 执行不出错** | 受理不算完成；恢复不重复执行；取消不会被迟到回执翻转；异步时序不被误判 | 长动作、超时、取消、连续恢复、迟到回执 |
| **第 2 组 · 数据不串不丢** | 同伴隔离；任务与版本关联；失败后队列可恢复 | 两只同伴交错写入、重启、日志轮转、复盘失败 |
| **第 3 组 · 经验不被错误强化** | 展示 ≠ 采用；无关成功不升级；叫停不算反例 | 召回后执行不同任务、无状态结果、被动目录重印 |
| **第 4 组 · 契约不漂移** | 七字段往返不丢；身份规则稳定；草稿→落库字段一致 | 保存再读取、改成熟度、合并重复、旧格式读取 |
| **第 5 组 · 观测不误导** | 未知不显示成零；历史不显示成当前；**被提及 ≠ 被调用** | 数据过期、采样截断、日志缺失、同名不同内容 |
| **第 6 组 · 真实闭环** | **点名会用**与**自主会用**分开验 | 现场投料 → 复盘 → 落库 → 召回 → 采用 → 回报 |

⇒ **做法**：把现有测试归入这六组 → 找覆盖缺口 → **不是再机械新增一批重复测试**。
其中关键回归测试还要证明一件事：**把对应行为改坏时，它确实会失败。**

## 四、清理「垃圾代码」的纪律

清理放在固化与回归**之后**是对的，但 ⚠️ **前文有两类判断下得太快**：

| 前文说法 | 为什么太快 | 该怎么判 |
|---|---|---|
| 「页面在当前服务上访问不到 = 死页面」 | 可能在别的入口或离线工具有用 | 先查**所有**引用与访问路径 |
| 「接口零调用方 = 应该删」 | 可能是**明确保留**的扩展口 | 先看当初有没有写下「留这个口」 |

⇒ 先分三类再动手：**① 确认废弃 ② 保留扩展 ③ 实现未接通**。
第三类**不是垃圾**，是欠的活。

### ⚠️★ 回退点的真实覆盖范围（这条最要紧）

**Git tag 只保存「已提交的源码」。它不保存：**

- **未跟踪文件**（未 `git add` 的新文件）
- **运行配置**（各实例的 `config/`）
- **脚本库与经验库数据**（`acx/`、`experience-*.jsonl`、`learner-memos-*.json`）
- **存档与日志**（游戏存档、监测台日志）

⇒ 「安全网已经建好」这句话**只在源码层面成立**。
⚠️ **若要把「随时可以回来」变成真的，需要额外做一次：把上述内容单独打一个归档包。**
