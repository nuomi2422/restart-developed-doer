# 73 · 最终接线架构与分批实机验收方案

> 日期：2026-10-04。性质：**目标架构、施工顺序、验收契约**，不是完成报告。
> 用户目标：整合现有模块和 72 号经营脚本第一批，让施工 AI 连续按「实现→审核→实机验证→下一批」推进；用户回来能亲眼看出这些能力是否真正影响 AI。
> 本文编写轮只做文档与只读核对，没有改 Java/AC、没有编译、没有启动游戏。下述新增接口/字段/证据格式是施工要求，不冒充已有工具。
> 决策来源：63 §8（后续拍板优先于旧禁令）、68（保留待决）、69（语义边界）、72（第一批范围）。71 是调查材料，不作最终架构依据。72 的机制假设以本文 §3 的纠偏和实机探针为施工前提。
> 本文不启动 stage。用户明确要求开 stage 时，才按 harness 的 stage 真源执行；普通任务也必须逐批留证。编号现场扫描至 72 后分配 73。

## 0 · 最终要得到什么

**一个会选目标、会用已有能力连续干活、失败能说清、能从真实经历积累并再次使用经验的同伴。** ACX 用确定性程序减少逐动作等待模型；学习者负责整理和复审；Harness 负责外部施工、验证和取证。三者不互相冒充。

用户回来时第一交付应有三样：
1. 可复演场景：同伴自行选用吃饭/夜间后勤/单轮种收存能力，而非外脑逐步遥控。
2. 同条件前后对照：自主选用次数、任务完成、人工干预、LLM 往返、真实工具调用、耗时、产物数量；没有提升也如实呈现。
3. 一段完整的学习证据：真实失败→现场记录→学习者复审→经验落库→另一轮取用并改变行动→世界结果核验。

不以脚本数量、代码行数、总测试数或录像看起来热闹作为完成度。整体未闭环时，已经验过的子能力可单独交付，整条链仍标未验。

## 1 · 总体架构与职责

```text
用户目标
  ↓
规划 AI ← 规划侧经验（PLANNER/BOTH，目录→按需正文）
  ↓ 目标、约束、完成判据、任务身份
任务链 / Supervisor（生命周期、监督、重规划，不抢身体）
  ↓
执行 AI ← 执行侧经验（WORKER/BOTH） + 携带器现场提示
  ├─ 选择原子工具
  └─ 选择已发布 ACX 脚本（条件、版本、预算）
          ↓ 单一身体所有权 / 执行动作身份
      执行层工具 → Minecraft 权威状态
          ↑ 受理 / 进度 / 最终结果（不混为 success）

系统事件 ─┐
现场体感 ─┴→ 同伴隔离的素材队列 → 学习者多轮复审
                                   ├─ 经验含记忆 → 校验/入库 → 规划与执行
                                   ├─ AC 草稿 → 校验/沙盒/实机/发布 → ACX
                                   ├─ 携带器候选 → 能力与策略校验 → 现场提示
                                   └─ 自编译请求 → 外层工程队列 → Harness 施工

世界事实采样/动作/队列/产物/采用/结果 ─→ 统一关联证据 ─→ 只读监测台
外部 Harness：布置小场景、审核、编译部署、回归、观察、录像、回滚、交付
```

### 1.1 每个模块负责什么

| 模块 | 输入→输出 | 禁止越界 |
|---|---|---|
| 规划 AI | 目标+世界事实+高层经验→可验收任务 | 不把脚本不存在的能力当现成能力 |
| 任务链/Supervisor | 执行反馈→推进/暂停/终止/重规划 | 不因「受理」标完成；不绕过单驾驶员直接动身体 |
| 执行 AI | 当前任务→选择原子工具或 ACX | 不把发布草稿等同立即上线；不与自己启动的 AC 同时发冲突动作 |
| ACX | 有界脚本+参数→真实动作及终态 | 不成为第二个规划 AI；本轮不新增周期经营调度器 |
| 执行层 | 一个有身份的动作→世界变化+完成回执 | 不将超时/观察不到/还在飞统一写失败；不让旧回执污染新任务 |
| 世界事实 | 同伴/世界/维度/采样时间→带新鲜度的事实 | 统一语义与身份，不强制实时操作绕磁盘；缺失字段不是零 |
| 素材队列 | 系统事件和 AI 现场材料→可恢复待复盘项 | 同一队列可以保留，必须可区分来源与证据；不能串同伴 |
| 学习者 | 原始材料+先前轮次→四类可并列候选 | 事实、执行者假设、复审结论分开；修订不抹掉原材料 |
| 经验库 | 候选/采用证据→版本化经验、受众过滤、目录与正文 | 呈现≠采用≠有效；时间相邻不是因果 |
| 携带器 | 触发条件+引用内容→及时提醒 | 不另造经验数据库，不预设未经实测的提醒优先级 |
| 外层工程 | 自编译请求→实现/审核/验证/可部署版本 | 不接活游戏内闲置 MutationPipeline；不让游戏内 AI 任意改源码 |
| 监测台/相机 | 证据→观察与回放 | 不承担生产经营调度；外脑点名执行不能记成内脑自主 |

### 1.2 跨模块最小契约（目标字段，映射现有名字，避免重复建模）

统一携带 `companion_id / world_id / dimension / task_id / execution_id / action_id / timestamp`；脚本另有 `script_id / version / content_hash`，经验另有 `experience_id / version`，学习另有 `memo_id / review_round / artifact_id`。同一含义已有字段时复用并明示映射，不为了拼写一致全仓改名。

- 投料身份指纹用于去重，适用场景指纹用于检索：两者不是一个键。
- 来源区分系统事件与 AI 主观材料；附原事件引用、现场原文、采样窗口及缺失项。
- 完成结果包含目标判据是否满足及其世界证据，不只保留 handler 返回值。
- 经验回流至少区分呈现、选择采用、关联任务/动作、支持证据、反例、证据不足。未知不加支持数。
- 列表/队列要能持久化往返，重启恢复不重复消费；多轮复审和产物分流使用已有 Verdict/PriorRound 接口。
- 观测引用可以旁路；用于上线或强化的证据必须可追溯、耐重启。耐久写入失败时该次不计为合格证据，并明确报告。

## 3 · 整合 72 号：保留范围，先纠正机制

### 3.1 用户已定边界

周期调度器继续待决；本轮 AC 是单次有界动作。种田只负责种、收、存箱，不做加工分配。`night_watch` 本批不做。AI 在既有任务回合里按需再次选择某脚本不等于新增周期调度器；验收外部重复发起只算重复试验，不算自主经营。

### 3.2 不能直接固化的假设

| 72 号陈述 | 本方案纠偏/施工探针 |
|---|---|
| 丢小麦→走开→牛羊跟随，且这是唯一方案 | 原版牛羊的食物引诱依赖玩家持合适物品，地上掉落小麦不是该引诱机制；牛羊用小麦，不是小麦种子。`interact_entity` 源码参数有 equip-and-use 语义，尚不能由此推出移动时持续持物。先验持物是否保留、动物目标是否识别同伴、移动后是否跟随。失败则记能力缺口，不用随机走动假装成功 |
| 丢床=把床放到围栏 | 丢的是物品实体，不是床方块。应真实放置床，核两格床、朝向、上方空间与可达性；床搬运、村民入住分别验 |
| 敲钟把村民叫出来/叫进指定围栏 | 原版钟可触发村民避难行为，不保证指定路径或归属；门、床寻路和实际进栏要独立验证，不以敲钟回执算完成 |
| 右键村民用面包=喂繁殖 | 原版村民繁殖食物通常靠拾取合适食物，而非右键交易交互；需核拾取/gamerule、床和空间、成年与冷却。单次投料不宣称出生 |
| 床必须在村庄/建筑旁才安全 | 不是通用原版睡眠条件。按 live 模组和 Sleep 工具实际语义验证，区分敌怪、时间、维度、距离等拒绝原因 |
| build 拒液体⇒所有浇水原语不存在 | 只能证明 build 路径限制；水桶交互须另核。第一交付使用已验证水源农田，水工程不阻塞单轮种收 |
| 16地≈100调用⇒200 max_steps 必不够 | 调用次数与 AC 控制步、子 AC 累计步数不同；实际展开后计预算，不能从100直接推出大于200。30秒也不是每次 goto 固定耗时 |
| 工具目录没outputs⇒完全不能写脚本 | 桥接与运行解析已存在；应该先验证本批使用字段。按依赖逐批补，不强迫先测完七种工具才能开始吃饭小链路 |
| 循环变量变化=经营有进展 | 重试计数增加可以是调度进展，但不等于世界任务进展。另测物品/坐标/成熟度/目标数量，不能靠自增计数躲停滞 |

以上原版机制纠偏不代替 live 实机；若模组行为不同，记录模组、版本和复現条件。72 原文保留作为规划历史，不静默覆盖另一窗口的工作。

### 3.3 八个脚本的落点

| 原脚本 | 接入方式 | 独立完成判据 |
|---|---|---|
| eat_if_hungry | 最先实现单次检查→有食物才吃→复核 | 低饥饿上升；已饱不浪费；无食物明确停，不循环耗材 |
| night_sleep_check | 单次条件化检查/睡眠；不满足条件报原因 | 主世界安全夜晚睡眠结果；白天无动作；其他维度绝不尝试危险睡眠；陌生区域缺覆盖不报“无床”定论 |
| farm_batch_wheat | 显式单轮模式：播种；或收成熟作物→拾取→按约定补种→入指定箱 | 地块实际状态+背包/箱子增量；未成熟不毁；种子保留与存放品类明确。等待生长不在循环空转 |
| herd_cattle_sheep | 保留有限状态机，但替换错误引诱机制；按实体身份追踪 | 同一目标真实进入目标区域，不能每次 nearest 换一头冒充已跟随；失败有限重试/拉黑并解释 |
| bed_and_bell_routine | 分开搬运/真实放床/验证入住；钟只作经验证辅助 | 目标床方块正确、村民位置与可达性证据。床物品在地不算 |
| breed_villager_loop | 本轮限定一次条件检查与有效投料，命名/描述明确 one-round | 消耗/拾取证据；观察到出生才报出生，否则 pending，缺判据明确不可判 |
| farm_supply_check | 已通过子脚本的单次组合；危险动作需参数/前提 | 子结果逐项汇总，父预算覆盖子预算，不把首个暂停当成其余全检过 |
| night_watch | 本批不实现 | 不能在夜检里偷塞自动战斗策略 |

## 4 · 分批施工图：尽早交可见结果，再补全学习闭环

每批状态：`PLANNED → IMPLEMENTING → REVIEWED → OFFLINE_PASS → DEPLOYED → LIVE_PASS → CLOSED`。发现缺陷回到实现；环境阻塞记 `BLOCKED_ENV`，证据不足记 `UNVERIFIED`。这些是交付台账状态，不擅自替换 ACX 运行枚举。

依赖：`B0 → B1 → B2 → B3 → B4 → B5 → B6 → B7`。B3 后先产出用户可看小结；B4 某机制阻塞可跳过该分支继续 B5，必须写明缺失脚本及依赖，不能宣称 B4 全完成。

| **B6 四产物全部有出口** | 经验、AC草稿、携带器候选、自编译请求各有接收方/状态/回执；AC候选按版本走结构→模拟→受控真机→阈值发布 | 对每个 action 测有效/拒绝/重复/失败；阈值配置及版本隔离；承认 sandbox/发布计数缺口须实现，不能用类名存在销账 | 候选未验不能 active；同版本达标才发布；失败/介入/换版按明确规则清零；携带器真触发；自编译请求到外层待办但不自动任意改源码 |
| **B7 总验收与交付** | 复测小经营和学习前后变化，做一次跨重启与完整回归；整理可复演入口 | 关键红线破坏性验证能抓错（在隔离夹具中做，不向 live 部署故意坏版） | 对照指标、世界结果、录像、动作日志互相吻合；完整演示后停机、写交接、跑 postflight |

### 4.1 B1 的具体接线，不再堆另一个大类

- 用现有 TaskDispatch/任务回执与 ACX 会话身份建立关联；检查实际宿主协议后选字段，不凭“PAUSED 没 reason”猜受理。
- 暂停时记清动作仍运行还是已停止；恢复先对账 action_id，再决定等回执或重新发起。取消/超时终态不能被迟到 success 覆盖。
- 单驾驶员覆盖执行 AI 原子调用、ACX、RDD和外部MCP；仅关闭 RDD 不是全局互斥。复用现有身体任务通道先核所有权，缺口才补仲裁。紧急生存动作的抢占/取消关系要明示，不能被普通脚本锁饿死。
- reload 先完整校验候选快照，再原子切换供新运行使用；已在运行的脚本固定旧内容哈希直到结束。坏库拒绝并保留上一有效版本；不得混用新旧子 AC。reload 不等于批准草稿。
- 成功结果耐久来源优先复用现有事件/质量台账接缝；明确唯一发布判据来源并测试写盘失败。不要简单把同一事件同时接两条计数线路。
- `AcxRunner` 按生命周期、控制流、绑定/上下文、持久化接缝分责任；`EntityAgentLoop` 按工具发现、模型回合、派发/回执、上下文拼装分。先补外部行为回归，再逐段抽离；不在同一补丁里混重构和机制变更。不追求拆成到处共享可变状态的小文件。

### 4.2 AC 自动上线的目标边界

用户已选择游戏内 AC 可自动上线：**草稿→结构校验→模拟→受控实机→连续 N 次有效成功→上线**。N 可配，未批准具体值时实现配置与测试，但不擅自开生产自动批准。测试夹具可显式指定 N，并标明不是生产决策。

连续计数按同伴、脚本内容版本及明确验证条件隔离；旧版成功不搬到新版，失败/人工介入/无效证据不得算成功。声明“连续”的重置条件需在实现前写清并审核。现有监测事件是 `type=acx_event`、`data.kind=RUN_FINISHED` 的历史形状，施工仍要用当前原始样本核实，不能使用旧文档的 `type=run_finished`。

经验/携带器/源码变更不自动继承 AC 发布特权。D1 写权限和携带器策略未决部分保留为显式配置/硬拒绝边界，不让施工 AI 代用户拍板。

### 5.1 现成能力怎么用

真源：`D:\rdd\harness\rdd-harness\registry.json`、`standards.md`、`进游戏前必读-游戏内能力清单.md`。工具参数以当前实现/list 返回为准，不复制文档里臆测的 JSON。

所有 shell 后台脱离启动，输出日志+PID+进度，轮询读产物；超时先查状态不重发。长任务续航先核已有 watchdog 确实在跑且不会注入目标打断试验。不得把 chat 回复后的“会继续跑”当真实持续执行。

### 5.2 剧本模板（字段设计，尚非已实现的 runner）

每个 case 保存：`case_id, batch, mode, companion_id, world_id, versions, setup, preconditions, goal, steps, assertions, time_budget, call_budget, intervention_policy, cleanup, evidence_paths`。

- mode：`PROBE`（原语探针）、`DIRECT`（外部直接调AC）、`NAMED`（让内脑点名用AC）、`AUTONOMOUS`（只给目标）、`FAULT`（故障注入）。禁止混算。
- assertions 必须写世界可观察事实；回执成功只能作中间断言。
- 每个结果记录 `PASS/FAIL/BLOCKED_ENV/UNVERIFIED`、实际值、日志时间窗和ID、原因。不把缺字段补成0。
- 新case先写预期与预算再运行，不能跑完回头把预期改成实际以制造通过。场景随机性需多次复验，记录每次，不仅保留成功视频。

## 6 · 判断“对 AI 产生大量影响”：分清能力与采用

### 6.1 三层验收

1. **能力层**：DIRECT 能跑通，证明执行器可用。
2. **发现层**：NAMED 内脑能找到并正确调用，证明工具/脚本发现接线。
3. **自主层**：AUTONOMOUS 只给目标，内脑自主选择、遇前提不满足会拒绝/换路、结果回到任务链，才证明行为受影响。

再加学习层：新经验改变后续同类任务的行动，不是只往库里多写一条。不要在自主试验前连续演示同一提示而不记录污染；使用独立同伴/可恢复相同基线或明确标注历史上下文。

### 6.2 A/B 试验与指标

建议最低：吃饭/夜间后勤/农田三类，各3组配对试验；小样本只报方向，不宣称统计显著。A是保留原子能力的原有行为、B是已接入脚本/发现链；再用独立对照测“有/无新经验”，不要把脚本和学习收益混在一起。B0若拿不到可比A，就标仅后测，不编造提升百分比。

每对固定模型/provider、提示目标、难度、物资、场地和时间条件，使用可恢复场景并记录A/B执行顺序；测完整耗时但将加载/布置排除。身份不同但环境等价也要注明。任何外脑中途提示/传送/补物都算干预。

| 指标 | 判据 |
|---|---|
| 自主采用率 | 自主选择并实际启动合适脚本的机会数 / 可用且前提满足的机会数；明确分母与不可判 |
| 完成率/产出 | 完成判据达成的任务数、实际成熟收割/入箱/入栏数量，不用文字自报 |
| 人工/外脑干预 | 每次纠偏、点名、补给、停止分别记；干预后结果不算自主成功 |
| LLM 往返与token | 实际模型请求数、真实usage；拿不到usage就记未知。脚本减少LLM轮次不等于减少原子工具调用 |
| 工具调用与预算 | 实际桥接调用、脚本控制步、重试分别计；避免把一次acx_execute当一次世界动作 |
| 耗时/停滞/资源浪费 | 端到端任务耗时、无进展持续段、重复动作、额外耗材、伤害/死亡 |
| 学习效果 | 真实采用相关经验后是否改变关键决策、避免已知失败；支持/反例/不足分别统计 |

**建议验收方向**：B不能靠显著增加失败/干预换取更少token；至少看到自主选择、任务结果正确、LLM编排往返下降的可追溯样本。具体“大量”的数值阈值尚未由用户设定，施工前可记录试验目标，但不得跑完后选有利阈值冒充预定标准。无明显收益时交负结果和根因，不为了交差强制AI调用AC。

## 7 · 连续施工、审核与稳定推进

### 7.1 每一小批固定动作

1. 刷新当前版本/文件归属/部署；写本批契约和case，不依据旧状态重复修。
2. 实现最小闭环；已有入口优先接线；新增消费者要有真实调用点。复杂类按责任拆，相关行为先钉住。
3. 审核补丁：语义、边界、调用点、版本/身份、持久化、失败可观察、预算、是否偷加周期调度。修完再核关键差异。
4. 离线测试要读真实子用例；已有 known-red 不可用绿色包装测试遮住。本批相关红项未解决就不能部署为稳定能力。
5. 唯一通道编译部署→核jar和脚本active→重启→执行实机case→保存原始证据。
6. 正常/失败/恢复关键case过且证据完整才 CLOSED；记下待决和局部阻塞，然后自主继续下一无阻塞批，不每步问用户。
7. 每批更新用户入口的进度、录像链接、当前版本、能演示什么；完整结束跑收工门、实际停机、写交接。

“审核”不是实现者一句自评通过：优先使用当前可用独立审阅上下文，提供限定diff和契约而非整仓倾倒；用户本次要求分批审核，可由施工AI安排审阅。不强制指定付费模型；GPT-6额外额度默认不用，Codex/provider不可用就记录并使用可用审阅渠道。只能自审时显式标注，不能伪称独立审核通过。所有审查发现都要回到补丁和实机case。

### 7.2 继续条件与止损

- 同一个case同一根因连续2轮修改仍失败：停该分支，提交最小复现和证据；先审因再第三次改。两轮是本方案建议施工止损值，不是已有全局配置。
- 401/402/持续5xx、游戏不可达、部署不符：按环境问题处理，不改业务逻辑“碰碰运气”。预算到期正常停机留续跑点。
- 阻塞只影响一条经营分支，可继续无依赖批；阻塞单驾驶员/取消/证据真实性等共用底座，则暂停所有依赖批。
- 周期调度器、未定写权限、携带器策略、生产自动上线阈值，不由无人值守施工偷偷决定；标出准确问题，继续已授权边界内的工作。
- 并行窗口改相同文件时先对账补丁归属；施工默认一个实现者串行推进。分批审核不意味着开多个实现者抢同一live身体。
- 脚本真源 `rdd-selfcompile/scripts` 改动仍须用户批准；优先复用现有入口。提交/push仍按用户明确授权执行，未授权就交付精确文件清单和可回滚数据，不把未提交改动说成已在tag内。

### 7.3 证据包与回退

每批证据包包含：计划与版本清单、diff摘要/审核记录、离线真实结果、部署/加载证明、case逐项结果、原始JSONL时间窗和ID、世界前后快照、干预表、截图/录像、失败复现和续跑点。

回退同时覆盖源码差异、部署jar、运行配置、AC库/脚本版本、经验与队列、测试存档。git tag只覆盖已提交源码，不能代替运行数据归档。不得用清空经验库来制造“回归通过”。

建议证据目录：`rdd架构\验收证据-73\Bxx\`；用户可看的录像/总表放 `rdd存放\73-接线验收成果\`。这是施工输出约定，当前还没有这些证据或视频。
