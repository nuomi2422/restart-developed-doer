## 一、为什么要统一术语

**现状问题：同一个东西有三种叫法，导致「明明做过了却查不出来」。**

已实测踩到的三例：

| 例 | 现象 |
|---|---|
| 1 | `context.jsonl` 里搜「experience」有 131 行命中，**但 `<experience>` 标签是 0 次** —— 131 全是**工具名**（`experience_recall`/`experience_learn` 的 schema）。**名字撞了** |
| 2 | 一次把「<rdd> 标签在上下文里」当成「RDD 块注入了」，实际那是**工具 schema 里的描述文本** |
| 3 | 知识库大小被当成「记录条数」，实际 KB 和字节数是两回事 |

**⇒ 术语不分清，监测台的数字就全是假信号，验收会验在假东西上。**

### 2.2 ★ 硬编码实践的统一说法（用户明确要求统一的部分）

用户原话：「翻译硬编码实践上我们需要统一术语。」

**核心歧义：「硬编码」这个词在当前工程里指三件不同的事。必须分开叫：**

| 统一叫法 | 定义 | 例子 |
|---|---|---|
| **事件级判定** | 单个动作/单个方块是否达成 | 「这次挖掘是否产出了黑曜石」 |
| **目标级判定** | 一个**子目标**是否达成 | 「护甲达到铁甲」 |
| **任务级判定** | 整条**任务链**是否完成 | 「通关条件全部满足」 |

**统一句式：「X 完成」必须指明是哪一级判定。** 禁止只说「完成了」。

**另一组必须分开的词：**

| 统一叫法 | 定义 | 反例（不要混用） |
|---|---|---|
| **触发** | 够格把某条经验**捞出来看** | 「目标是黑曜石 + 附近有岩浆」 |
| **判定 / 证明** | 够格说某条经验**是对的** | 「背包黑曜石 +1」只能证明目标完成，**不能证明「铺水导致成功」** |
| **检测** | 程序读取世界状态 | 「生命值 = 6」 |
| **判定为成功/失败** | 拿检测结果对比目标 | 「血量 6 < 阈值 8 → 不满足安全条件」 |

> ⚠️ **「触发」≠「判定」是本工程最容易出错的一处。**
> 详见 `59` §4.3。

## 六、★ 监测台「可验证化」规范

用户判断：「监测台我认为是比较标准的一个东西，因为我可以直接肉眼看到经验究竟是怎样的，人类验收会非常方便。」

**⇒ 可验证化的硬要求：每条断点卡片必须能回答三问，缺一不可。**

| 问 | 要求 | 缺了会怎样 |
|---|---|---|
| **① 判据是什么** | 一句话，能判真假 | 缺 = 只是感想，不是断点 |
| **② 证据在哪** | 文件+行号（静态事实）**或** 文件+实测数字+采样窗口（实测事实） | 缺 = 传言，会漂 |
| **③ 怎么自己复现** | 一条命令，或面板上一个按钮 | 缺 = 不可维护，下次没人知道怎么验 |

### 6.1 「实测」和「静态」必须分开标

```
measured: 真跑出来的数字 —— 会过期，但真实
static:   代码里读到的结构 + file:line —— 不会过期，但没验证运行期
```

**混在一起就是把代码结构当运行期事实** —— 2026-10-01 已经栽过一次
（RL-19 源码对了、测试绿了、文档写「已改」，但游戏里跑的还是旧版）。

### 6.2 「0」的三种含义必须能区分

| 显示的 0 | 真实含义 | 怎么在面板上区分 |
|---|---|---|
| 真的没有 | 功能从没运行过 | 无历史事件 |
| 采样窗口没覆盖 | 有，但在窗口外 | 显示「尾部 N 条采样」，并给全文件计数 |
| **上游断了导致读不到** | 有数据，但代码读不出来 | 同时显示磁盘条数与代码可读条数（59 vs 0 就是这种） |

> ⚠️ **第三种最危险** —— 显示 0 会让人以为「功能没做」，实际是「做了但读不出来」。
> 这正是 B1 当年被漏掉的原因。

> **RL-21** 不得为省 token 截断工具说明/schema（已回退 3 刀验证）——
> **做分级注入时最容易犯**：把工具目录摘要砍短来省 token，等于砍掉 AI 的判断力。
> **RL-22** `rdd_submit` 建链必须拍 acquire 基线（已修并验证）——
> 规划者侧任何「判定目标是否具备」的逻辑都要照这条的判停摆口径写。

**⇒ 监测台的可执行化只能到这个程度：**

```
监测台断点卡片
   ↓  「生成工单」
工单（文本，含模块 / -Requirement / -Module / 验收判据）
   ↓  人工或外层 AI 审查
run-mutation.ps1 -Requirement "<工单里的需求>" -Module <模块>
   ↓
编译 → 部署 jar → 重启游戏 → 回监测台看断点是否变绿
```
