## 一、为什么要接线（不做就是个空壳）

34 号页交付的 PAUSED 只是状态机 + 单测 + 字节码，**AI 没有任何途径说出「先放着」**。
而本轮实机恰好撞上它要治的病：

```
10:46:27  subtask_stalled  re-nudge      （找村庄那条二级）
10:46:52  subtask_failed   stalled after nudges
10:46:53  subtask_retry    retry=1 max=2
10:46:59  llm_idle_stall                 ← 提前 10 秒拍
10:47:09  subtask_stalled
10:47:34  subtask_stalled  re-nudge
10:47:59  subtask_failed   stalled after nudges
10:48:00  subtask_retry    retry=2 max=2   ← 预算烧完
```
前提（附近有村庄）根本不成立，它却在**白烧重试预算**。这正是"暂停"要治的病。

**接线方式**：复用士兵已有的上报通道 —— `report_task_concern` 加 `kind=PAUSE`。
理由：PAUSE 是**士兵的意图**（我做不到，先放着），不是指挥官的命令，所以该由士兵说出口。

改动面（单模块 `plugins:rdd` + `rdd-core` 的一个 record）：
| 文件 | 改什么 |
|---|---|
| `rdd-core/.../fail/TaskNegotiation.java` | `Kind` 加 `PAUSE`；加 `isPauseRequest()`；`kinds()` 收录 PAUSE |
| `plugins/rdd/.../RddDetector.java` | `tickNegotiation` 加 PAUSE 分支（先 `clearBody` → `pauseSubtask` → 发 `subtask_paused`；按住失败则退回重规划并发 `subtask_pause_rejected`）|
| `plugins/rdd/.../RddConcernTool.java` | 工具 description + schema 写清 **COUNTER 与 PAUSE 的选择依据**（AI 选 kind 的唯一依据，不写就选不到）|

## 二、实机暴露的两个真 bug（都是"想得到但活不下来"的那种）

### Bug 1 · 只改了消费侧，漏了生产侧 → 静默失败

第一版改了 `tickNegotiation` 的守卫（认 `isPauseRequest`），**没改** `RddNegotiationInbox.accept`：

```java
if (n.needsSupervisorAction()) { PENDING.put(...); } else { PENDING.remove(...); }  // PAUSE 落进 else，被当场删
```

实机表现极具欺骗性：
```
11:04:47  task_negotiation  kind=PAUSE   ← 事件照发，工具回 "concern recorded"，看着像成功
11:04:47  SNAP st=STALLED                 ← 指挥官根本没收到
11:04:58  subtask_failed                  ← 照旧判失败
```
**入队条件与消费条件必须同时认 PAUSE**。已加单测 `pauseAndCounterAreBothRoutable` 锁死。

### Bug 2 · 守卫的时序假设错了（最典型的一个）

Bug 1 修好后，PAUSE 终于进到了 `pauseSubtask`，立刻被挡：
```
11:13:37  subtask_pause_rejected
          "current subtask cannot be paused from STALLED"   fallback: replan
```

我原本只放行 `RUNNING/PENDING`。**但真实时序是**：
```
做不到 → 资产无变化 → 15s grace → STALLED → 士兵才察觉"我做不到" → 上报 PAUSE
```
**STALLED 才是上报时最常见的状态**，而我的守卫恰恰把它挡了。
> 单测当时只覆盖 RUNNING，一跑就露馅 —— 设计与真实时序不符，不是代码写错。

已放行 `STALLED` 并加单测 `pauseIsAllowedFromStalledBecauseThatIsWhenSoldiersActuallyReport`。

## 四、卡死检测被外脑推翻后的修正（GLM 5878 字审稿）

W 层问题修复后（见下节），GLM 出了**实质审稿**，直接反驳我 5 秒阈值：

| GLM 的论点 | 我的处置 |
|---|---|
| 5s 低于实测分布下沿（5.5s）→ 命中 100%，是"每轮税"不是检测器 | **阈值 5 → 10**，并加单测锁 `>= 6 && <= 15` |
| **致命约束**：空转 35.6s < 有效 44.0s → **任何纯时间阈值都无法区分"卡住"与"慢"** | **写进 javadoc 诚实标注**：这只是压低假阳性，不是解决问题。真正的判据在响应本身（`finish=stop && tool_calls=[]`），属 `:ai` 层跨模块改动，**本轮未做** |
| nudge 在请求在飞时根本到不了模型（只会排到下一轮） | 记录；未改（要改得动 `:ai`）|
| **"立刻调用一个工具"是 content-free 紧迫感，nudge 本身可能就是漂移的原因** —— 模型按 recency 服从它 → 挑任意工具 → 覆盖原计划 | **nudge 文案重写**：① 必须点名当前子目标 ② 必须给合规的不作为出口 ③ 必须允许上报 PAUSE/COUNTER/已完成 |
| 假阳性清单：生成中 / 长工具执行 / 合法等待 / **对话轮** / **等规划器批准**（拍醒会产生**未授权动作**，比卡住更糟）/ 工具拒绝循环 / 轮询相位抖动 | 记录；`source=idle` 已天然排除"多步身体任务在跑"（`body_task:*` 不触发），其余留待下一轮 |

> **我保留的判断**：GLM 批评的是"in-flight 计时器"，而我的判据是
> 「身体无在途任务 + 资产指纹连续不变」，两者不是同一个信号。
> 但它关于「阈值无法区分 35.6 与 44」这一点是对的，已照办（抬阈值 + 诚实标注）。
