## 0. 为什么有这一份

四个模块是**分四条线并行做出来的**，每条线都把自己的接口、工具、文档写好了。
问题不在「有没有做」，在**四份文档各自成立，合起来看有几处说不清**：

| 说不清的地方 | 表现 |
|---|---|
| 产物有几样、谁写 | `62` 初版把「编译请求」画成另外三样的下游 ⇒ 与 `38` v2 的 D1 冲突（已修正） |
| 队列是一个还是多个 | 「统一队列」听起来是全局一个，但 `MemoQueue` 是**按同伴隔离的文件** |
| 「多次写任意一种」能不能做 | `Verdict.action` 是**单值**，一条 memo 只能声明一种产物 |
| 成功的素材要不要投 | 投，但样本量远大于失败，全字段投料会淹掉队列 |
| AC 那条自动上线路 | 与 D1「只有它能写」+ B9「全经门禁」冲突，`62` 已降级为待拍板 |

**本文的作用就是把上面每一行钉成一句话**，让下一次读的人不用再猜。

## 1. 整条线（唯一正确表述）

```
AC / 经验库 / 携带器  ──投料──▶  统一队列(MemoQueue)  ──读──▶  学习者（plan-only）
                                                              │
                                              判断「值不值得沉淀」
                                                              ▼
                                    五个并列产物：可多选、可只选一个、可反复写
                                    ① 记忆  ② 经验  ③ AC 脚本  ④ 携带器实现  ⑤ 自编译请求
                                                              │
                                              五样全部经门禁 + 人工批准（B9）
```

**依据**（原文照抄，不改写）：

> **D1**（`38` v2）：plan-only **只禁身体动作**；学习者**自己写产物**（记忆 / 经验 / AC 脚本 /
> 携带器实现 / 自编译请求）。**只有它能写，干活 AI 只能派单**
> **B9**：学习者写的**全部产物**经 `flow-gate` / `loop-gate` + 人工批准才生效。**不得**自行入库生效
> **B10**：**只有学习者能写代码**。干活 AI **只能派单**，不紧急的进常规队列，**紧急的插队首**
> **B11**：自编译下游**不自动化**。学习者请求 → 落成结构化待办 → **写码由外层 agent 接手**
> **B12**：`MemoQueue` 加优先级，紧急单插队首，`review` 先清紧急

> **★ 这五个是并列的，不是流水线。** 编译请求**不是**另外四样的下游 —— 它自己就是产物之一。
> （`62` 初版把它画成下游，已按 D1 修正。）

## 2. 四条线的边界（一句话各一条）

| 模块 | 插件 | 它负责 | 它**不**负责 |
|---|---|---|---|
| **AC** | `plugins/acx` | 编排已有原子工具（算法型流程） | 不接管目标、不反写任务完成；不硬凑缺失的原子能力 |
| **经验库** | `plugins/experience`（底座 `experience-core`） | 经验的存 / 读 / 检索 / 分级注入 | 不决定「值不值得写经验」（那是学习者的判断） |
| **携带器** | `plugins/learner`（与学习者同住，`B13`） | 判断「什么时候该提醒什么」 | **只携带不存储**（`B4`）；承载器不是记忆库 |
| **学习者** | `plugins/learner` | 读队列 → 判断值不值得 → 写五样产物 | **不发身体指令**（plan-only，`B2`）；**不自行让产物生效**（B9） |

> **B4**：携带器 = **一个接口 + 多个实现类**，可同时携带（记忆 / 工具 / 备忘录 / 浮现），**只携带不存储**
> **B6**：记忆库**不新建**，`ExperienceStore` 就是底座
> **B8**：同一个库 + `audience` 标签（`WORKER` / `PLANNER` / `BOTH`）⇒「同一件事两边都检索得到」

## 3. 跨插件为什么必须走文件 / JSONL（这条决定了后面所有接线的形状）

`numen-plugin.gradle:37-44` 只给瘦 api jar + `:ai` + `:ui` ⇒ **跨插件 import 编译期封死**。
且 `experience-core` 的类被**内嵌进 `plugins/experience` 自己的 fat jar**
⇒ `plugins/learner` 不能依赖它（split-package / JPMS ResolutionException）。

⇒ **既有先例就是「只读 JSONL + 字节游标」**，且这个先例已经踩过坑：

- `FeedbackChannel` —— 只读 `monitor/rdd.jsonl`（`learner_feedback`）＋ `monitor/instrumentation.jsonl`（`learner_intake`）
- `LearnerIntakeTool` —— 只读 `monitor/instrumentation.jsonl`

⇒ **接线一律照这个形状**：在**投料方**写文件，在**学习者侧**只读。不要为了「统一」去开跨插件依赖。

## 4. 队列：字段契约统一，存储仍按同伴隔离

**契约**（字段定义、去重规则、成功样本的轻量形状）以 `62-统一队列契约与自学习闭环.md` 为准，本文不重复。

**但有一处必须说清，否则下次还会有人问**：

| | 现状 | 结论 |
|---|---|---|
| 存储 | `MemoQueue` → `learner-memos-<uuid>.json`，**按同伴隔离** | **保持隔离**。一个同伴的经验不该被另一个同伴学到 |
| 「统一」的含义 | **字段契约统一 + 去重规则统一 + 产物格式统一** | 不是「一个全局队列」 |
| `signature` 计数 | 现在是**会话内**（`LearnerIntakeTool.SEEN`，上限 512） | ⚠️ 跨会话会丢。这是已知缺口，不假装它准 |

## 5. 五个产物各自的落地口（谁写、谁审、谁生效）

| 产物 | 学习者怎么写 | 门禁 | 生效方式 |
|---|---|---|---|
| ① 记忆 | `Memo` / 经验条目 + `audience` 标签 | `quality_gate`（Q0–Q6） | `experience_learn` → `ExperienceStore` |

### ⚠️ 6.1 「多产物并列」目前**做不到**（已定位，未改）

`62` §4 把「一次复盘产出多个产物」列为待确认需求。**实测确认它现在做不到**，卡点有两处：

1. **`Verdict.action` 是单值** —— 一条 memo 只能声明一种产物
2. **`Verdict.parse` 只解析 `experience` 一个结构化对象** —— 另四种产物没有结构化载荷位

⇒ 要「多产物并列」**必须改 `Verdict` 的载荷形状**（跨 learner / experience / acx 三处）。
**这不是配置能开的开关，是形状改造。** 未改，等架构 owner 拍板。

### 8.1 第 1 条的实现口径（落地前先钉死，否则会写成假绿）

| 要点 | 口径 |
|---|---|
| **「成功」的判据** | 只能读 `monitor/acx.jsonl` 的 `type=run_finished` + `status=SUCCESS`。⚠️ **不能用「跑完没抛异常」当成功** —— `AcxLifecycleState` 里 PAUSED/REJECTED 都不抛异常 |
| **「连续」怎么算** | 中间**任何一次非 SUCCESS（含 PAUSED/FAIL/TIMEOUT）就清零**。⚠️ 不能累计 —— 「累计 3 次成功」会让一个 10 次里成 3 次的脚本被上线 |
| **`dry_run` 沙盒边界** | **只派只读工具**（`look_around` / `get_self_status` / `scan_*` / `inspect_block` 等）、**不写生产库**、**不落 `acx-library` 的 STABLE**。⚠️ 当前 `plugins/acx` 里 **`dry_run` 0 处命中**（完全不存在），要新建 |
| **失败缓冲区** | 失败时把 `failed_step` / `why` 写进 `status_note`，**留在 PENDING**（不删草稿）—— 那是下一次改的输入 |
| **自动上线的范围** | **只对「游戏内 AI 自己写的 AC 脚本」开这个例外**（B9 的例外），**其余三样产物不变** |
| **人介入后怎么办** | 人工介入（approve/rollback/改草稿）**立即清零连续计数** —— 「无人工介入」是这个例外成立的前提 |

### 8.2 第 3 条的实现口径（「多轮循环 + 喂自己的案例」）

**owner 2026-10-03 拍板：循环由 (a) 驱动 —— AI 自己在下一轮 `learner_review` 里看着上轮结果再改。**

| 要点 | 口径 |
|---|---|
| **循环的驱动力** | **(a)**：不是学习者内部自动循环、也不是人工喊下一轮。**每一轮都是一次独立的 `learner_review`**，AI 在那一轮里读得到上轮结果，于是能决定「改还是不改」。<br>★ 这个选择的直接好处：**不需要定「循环几次」**，也不需要定收敛判据 —— 改到满意为止是 AI 自己的判断，判断不了就不改。 |
| **上轮结果必须可见** | `learner_review` 的上下文里要带**上轮产出 + 上轮之后的真实结果**（产物试了之后成没成）。⚠️ 现在 `Verdict` 只在当轮存在，**跨轮什么都看不到** ⇒ 这是第 2 步要补的第一件事 |
| **多轮循环不许变成无限自改** | 每一轮都要**落进队列**（可查、可回滚），**不许在内存里循环到满意为止**。⇒ 判据：任何一轮的产出都能在 `learner-memos-*.json` / `learner.jsonl` 里查到 |
| **喂案例的形状** | 每个产物类型一份**案例库**（59 §5.3 W1/W2/W3 各管一类，**互不干扰**）。⚠️ **代码 0 实现** —— `plugins/learner` 里「案例库 / 指导」作为概念 0 命中 |
