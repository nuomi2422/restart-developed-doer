## 五、★ 任务效率监察 + 视觉下现场（用户 2026-09-28 定；本节即用户口述思路的落档）

> 目的：**人不用一直盯着**。系统自己发现"推进不动"，自己下现场看究竟发生了什么。

### 5.1 四层监察，从便宜到贵

| 层 | 看什么 | 手段 | 成本 |
|---|---|---|---|
| ① 对话/决策链 | 同伴自己在想什么、反复想同一件事 | 监测台 `ai.jsonl` / 8776 的「Numen AI」页 | 只读 |
| ② 任务状态 | 当前 subtask / primary 状态与打勾 | `rdd_status`（只读） | 只读 |
| ③ **任务效率（新增）** | 效率是否过低 | `task-efficiency-watch.js` | 只读 |
| ④ 视觉下现场 | 画面上究竟发生了什么 | OpenClaw 客户端控制器 + `mc-screenshot.ps1` | 只读 |

**顺序很重要**：③ 只在便宜层都看不出所以然时才升级到 ④。不要一上来就截图。

### 5.2 ③ 任务效率监察：三个独立信号

判据（`scripts\task-efficiency-watch.js`，全部只读）：

| 信号 | 含义 | 默认阈值 |
|---|---|---|
| `subtask_flat` | 同一个 subtask id 挂了太久，轮次不换 | 600 秒 |
| `assets_flat` | 规划层的目标数长期不变 | 900 秒 |
| `inv_flat` | **背包指纹长期不变**（工具/盔甲/盾牌等静态件已排除） | 900 秒 |

外加滚动效率 `per_min`（每分钟完成子任务数）。裁决：
- 无信号 → `OK`
- 有信号但 `per_min >= 0.15` → `SLOW`（慢但在动）
- 有信号且 `per_min < 0.15` → **`STUCK`（该下现场了）**

> 三个信号**互相独立**是刻意的：任务状态在动但背包不动 = 执行层在假装忙；
> 背包在动但轮次不动 = 规划层卡住。只看一个都会漏。

```powershell
# 单次采样
node scripts\task-efficiency-watch.js rdd --once --tag <runTag>
# 常驻监察（Ctrl-C 退出；状态与输出按 tag 隔离，多实例不串味）
node scripts\task-efficiency-watch.js rdd --tag night-1
```
输出：每采样一行紧凑摘要 + 追加落盘 `task-efficiency.<tag>.jsonl`（事后可画效率曲线）。
可调：`SAMPLE_SECONDS` / `STUCK_SECONDS` / `FLAT_SECONDS` / `NUMEN_MCP_TIMEOUT_MS`。

> ⚠️ 任何 MCP 调用**必须有超时 + 整命令 deadline**（`NUMEN_WATCH_RUN_DEADLINE_MS`）。
> 游戏正在退出时端口"活着但不答"，无超时 = 永久挂死 = 上层 shell 卡住。
> 这条已由 `scripts\_selftest\test-mcp-timeout.js` 守住（4/4）。

### 5.3 ④ 视觉下现场（升级到这一层之后）

| 手段 | 入口 | 说明 |
|---|---|---|
| 实体追踪 | `node mc-openclaw-controller\scripts\oc-drive.js getVisibleEntities` | 操作**客户端玩家**，**不经 Numen MCP → 同伴内置 AI 照常跑，可真正共存**（这是能一边盯一边让它干活的唯一路子） |
| 画面 | `powershell -File scripts\mc-screenshot.ps1` → 用 Read 看图 | 多角度；最小化窗口会被跳过 |
| 世界快照 | 只读 `rdd_whereami` / `scan_nearby_entities` / `rdd_get_inventory` | 补事实，不替代画面 |

**已核实的结论（2026-09-28）**：
- `oc-drive.js` **自带 20 秒超时**，不会卡；`getVisibleEntities` 可用。
- **Flashback 模组在本链路里没有现成的实时实体追踪接口可用**——它是回放录制模组
  （`mods\Flashback-0.39.7-for-MC1.21.1.jar`，210MB），其能力面向录制/回放，不是给外部
  实时读实体状态的。所以**实时追踪走 OpenClaw 控制器**（上表第一行），不必依赖 Flashback。
  → 若日后真要从 Flashback 取，需要反编译该 jar 找 API，属独立议题。

### 5.4 发现效率过低之后的标准动作

1. 先排**网络/provider**（§四 纪律：网络异常与代码缺陷分开记录）——LLM 401/402/5xx 会让同伴
   完全没有脑，此时任何"它不动"都不是执行层 bug。**2026-09-28 实测就是这样**：
   DeepSeek 余额不足 → 连续 49 次 `HTTP 402 Insufficient Balance`、0 次成功 → 同伴原地空转，
   看起来像"任务下位很慢"，真因是**没钱**。所以第 0 步永远是查 402/401/5xx。
2. 再看 ①② 两层的证据，落到具体哪个环节。
3. 仍看不出 → 升 ④ 视觉下现场，并**留下截图 + 当时的世界快照 + 相关日志行**。
4. 结论写进巡检文档，**分清是「已修」「待修」还是「不是代码问题」**。

### 5.5 纪律（补充）

- 效率监察与视觉下现场**都只读**，不代替派活通道。
- 截图/快照要**带时间戳与 runTag**，否则事后无法归因。
- 一次异常一条记录，别把多轮采样压成一句"最近不太好"。
