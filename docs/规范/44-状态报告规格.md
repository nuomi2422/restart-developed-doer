# 44 · 状态报告规格（卡住时 / 收口时写）

> 来源：2026-09-30 那个实机任务（`筐1六项缺陷`）自己写出了 `07-状态-verify卡4门待用户拍板.md`，
> 写得很好 —— 但**它不是规则要求的，是那个 AI 自己想到的**。本文件把那套写法固化成规格。
>
> **为什么要固化**：AI 卡在门禁上时最该干的两件事是①把事实摊开给人看 ②说清"差的原因是不是我的问题"。
> 这两件事没有 AI 每次都做。没有规格 = 看运气。

## 什么时候写

| 时机 | 写不写 |
|---|---|
| **卡在门禁、等用户拍板** | ★ **必写**（哪怕只卡一条） |
| **④ 记录收口开始时** | ★ **必写**（作为交接） |
| 其他阶段一切正常 | ✗ 不写 |

判定：门禁没过 且 需要用户做决定 → 写。纯自己就能修完的 → 不用写。

## 骨架（照这个结构，别自创）

```markdown
# 状态 · <任务> · <阶段> 未完成，卡在 <N> 个需用户决定的门 · <日期>

> 依据 AGENTS 第 <N> 条：<引用哪条规则导致卡住>
> 本文件诚实记录"做完了什么 / 还差什么 / 差的原因是不是我的问题"。

## 一、已完成（有证据）
| 项 | 状态 | 证据 |

## 二、顺手修掉的真缺陷（不在原计划内）
| # | 缺陷 | 影响 |

## 三、还差 N 项（都不是"我懒得做"，请用户拍板）
| # | 门禁项 | 卡在哪 | 需要什么 |

## 四、我没做但已登记的
## 五、代码状态    ← 改动文件数 / HEAD / 建议分几个回退点
```

## 五条硬要求

| # | 要求 | 反例（不合格） |
|---|---|---|
| **1** | **每行都要有证据** —— 写「✅ 回归 1657 项/0 失败」不写「已修复」 | `F2 ✅` 后面什么都没有 |
| **2** | **区分「我没做」和「我做了」** —— 第四节专门放"没做但已登记"的 | 把没做的悄悄混进"已完成" |
| **3** | **明说「差的原因是不是我的问题」** —— 是我的就写是我的 | 「因环境限制暂无法验证」实际是自己没跑 |
| **4** | **卡住要说清"需要什么"** —— 要批准？要跑多久？要哪家的外脑？ | 「卡住了，等你处理」 |
| **5** | **代码状态单列** —— 未提交文件数 / HEAD / 建议分几个可回退点 | 完全不提代码处于什么状态 |

## 为什么这套能防止"AI 摸鱼"

- 要求 1 → **写不出证据就等于没做**，不能靠自我评价过关
- 要求 2 → 没做的必须单列，**藏不住**
- 要求 3 → 责任归属明确，不许把"没做"说成"做不到"
- 要求 4 → 把球明确踢给人，**不是无限期停工**
- 要求 5 → 交接时对方一眼知道代码在哪、有没有提交

## 存哪

**报告本体放这个任务自己的 `docs\` 目录**，不要写进 `rdd架构\自编译统一版\`（那是规则正文，不是任务产物）。

```
44-状态报告规格.md  →  read[]  ✅  菜谱：教 AI 怎么写，全项目就这一份，值得每次看
07-状态-....md      →  docs\   ✅  菜：某次任务的报告，一任务一份，不进 read[]
```

- 默认 `stager ctx` 只给路径 + 每份最多 3000 字符（`stager.js:454-462`）
- 只有 `stager ctx --full` 才给全文
- ★ **只有「规格」才进 `read[]`**。任务报告**禁止**加进任何阶段的 `read[]` ——
  每份都不一样、而且会越攒越多，进必读就变成纯占地方。
