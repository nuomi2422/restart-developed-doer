## 1. 整条线（唯一正确表述）

```
AC / 经验库 / 携带器  ──投料──▶  统一队列(MemoQueue)  ──读──▶  学习者（plan-only）
                                                              │
                                       判断「值不值得写」＋选产物（★可多选）
                                                              ▼
        ┌──────────────── 五个并列产物（不是流水线！）────────────────┐
        │  ① 记忆   ② 经验   ③ AC 脚本   ④ 携带器实现   ⑤ 自编译请求  │
        └──────────────────────────┬──────────────────────────┘
                                   ▼
                      门禁 + 人工批准（B9）才生效

> 措辞依据 38 号 v2 的 **D1**：plan-only **只禁身体动作**；学习者**自己写产物**
> （记忆 / 经验 / AC 脚本 / 携带器实现 / 自编译请求），**只有它能写，干活 AI 只能派单**。
> **B10**：只有学习者能写代码，紧急的活可插队首。**B11**：自编译下游不自动化，
> 落成待办、由外层 agent 写码。**B12**：`MemoQueue` 有优先级，紧急单插队首、review 先清紧急。
```

三条线**在架构上是同一种东西**：都产生「值得沉淀的素材」并投进同一个队列；学习者是唯一的消费者。

**AC 的特殊之处**：除「学习者写」外，**游戏内 AI 自己也能现写 AC**，现写现用现执行现验证——用来拼装现有原子工具做不到的事（算法型流程）。这条路的终点**不是人工逐条批准**，而是沙盒试跑通过后自动上线（见 §5）。

## 2. 统一队列条目（所有投料方必须写的字段）

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `source` | string | ✔ | `ac` / `experience` / `carrier` |
| `signature` | string | ✔ | **可复用签名**：从这次素材里抽象出来的「同一类问题」标识。去重与「值不值得写工具」都靠它 |
| `repeat_count` | int | ✔ | 同 `signature` 在队列里累计出现次数（投料方按自己看到的历史统计，队列侧也会再核） |
| `problem` | string | ✔ | 一两句人话：出了什么问题 / 卡在哪 |
| `tried` | string | | 之前试过什么（避免学习者重走弯路） |
| `failed_step` | string | ac 必填 | 具体哪一步（AC 的 step id） |
| `why` | string | ac 必填 | 失败原因原文（不要改写，保持可检索） |
| `env_snapshot` | string | ✔ | `key=value` 逗号分隔：位置/血量/背包/附近方块/维度…（学习者判断可行性的依据） |
| `ac_name` / `ac_version` | string | ac 必填 | 哪个脚本的第几版 |
| `success` | bool | ✔ | **成功样本也要投料**——「这次这么做成功了」是最值钱的模板来源 |
| `trace_ref` | string | | 监测台那次运行的可查标识（`run_id`），用于回看时间线 |

**AC 侧现成可取的值**：`failed_step` / `why` 来自 `AcxRunRecord`（`failedStep` / `errorMessage`）；`trace_ref` = `run_id`，在监测台 `/acx.html` 可视化。

## 3. 去重规则（所有投料方一致）

- 同 `signature` → **合并计数**（`repeat_count++`），保留最早一次与最近一次的 `env_snapshot`。
- `repeat_count ≥ 3` → 标记「**建议考虑写成产物**」（只是建议，**判断权在学习者/AI**）。
- 阈值可配置（队列侧），默认 3。

## 4. 学习者的五个并列产物（可多选）

| 产物 | 草稿形态 | 落地方式 |
|---|---|---|
| ① 记忆 | 记忆条目 | 记忆库入口（B6 底座 = ExperienceStore；B8 用 audience 标签区分受众） |
| ② 经验 | 经验条目（`experienceType` 等七字段） | 经验库入口 |
| ③ AC 脚本 | `.ac`（或增量步骤：见 §6） | `acx_publish` → PENDING → 通过则 STABLE |
| ④ 携带器实现 | 携带器声明 | 携带器侧自身的发布流程 |
| ⑤ 自编译请求 | `selfcompile_request` 载荷 | **B11：下游不自动化，落成待办、由外层 agent 写码** |

> **五样全部经门禁 + 人工批准才生效（B9），自编译请求本身也在内。**
> 「一次复盘产出多个产物」是**待确认需求**：当前 `Verdict.action` 是单值、`Verdict.parse` 只解析 `experience` 一个结构化对象 —— 若要「多产物并列」，**载荷形状要改**（跨 learner/experience/acx 三处）。

**编译请求**：统一格式 `{产物类型, 目标模块, 草稿指纹}`，由 `selfcompile_request` 承接。**AI 只发请求，不直接改生产代码**（这条不破）。

## 5. ★待拍板冲突项：游戏内 AI 自己写 AC（与 D1/B9/B10 冲突，勿当既定结论）

```
游戏内 AI 判断「这事我老做」→ acx_publish(草稿) → 状态 PENDING
   → acx_execute { dry_run: true }   ← ★沙盒试跑：只派只读工具、不写生产库
   → 自动判定：连续 3 次成功且无人工介入 → 自动 approve → STABLE（可被按名执行）
              任一次失败 → 留在 PENDING，把 failed_step/why 写进 status_note（=缓冲区）
```

- **冲突点**：D1/B10 说「只有学习者能写产物，干活 AI 只能派单」，B9 说「全部产物经门禁 + 人工批准」。
  而「游戏内 AI 自己现写 AC」这条路若成立，等于给 AC 脚本开一个**绕过学习者与人工批准**的例外。
- **两种收敛方式（需架构 owner 拍板）**：
  - (a) **保守**：游戏内 AI 写的只是**草案**，仍走「学习者审 → 人工批准 → 上线」，终点回到人工；
  - (b) **激进（本文上一版的写法）**：AC 脚本在 `dry_run` 沙盒里连续 N 次成功且无人工介入 → 自动上线，
    这需要**为 AC 脚本在 B9 上开例外**，其余四产物不变。
- 拍板前只把 `dry_run` 当**能力**建设（对 (a)(b) 都有用），**不预设自动上线**。
