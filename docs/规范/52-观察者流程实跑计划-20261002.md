## 三、刚跑这一轮就已经抓到的候选 bug（10:38–10:47 实测，非推测）

模型已换回 `deepseek-v4-flash`（OpenCode Go），延迟 907ms–14.0s，工具调用判断力正常。

### 候选 1 · `goto` 无法表达「走到某个已知坐标的那一个方块」 ★最有价值

```
execute_tool rejected  tool=goto
reason=invalid arguments: block means 'walk to the nearest one of these' — no coordinates with it.
       To reach one specific block you know the position of, goto its location (x+z) and interact there.
args={"block":"minecraft:spawner","x":-878,"y":14,"z":-908}
```

**这是工具契约的缺口，不是模型的错**：模型想做的是「走到 (-878,14,-908) 那个刷怪笼旁边」，
但 `block` 和坐标**互斥** —— 给了 `block` 就必须让工具自己找「最近的一个」，
不给 `block` 就只是裸坐标，**没有任何方式指定「那一个」**。
于是它反复重试同一个悬空的刷怪笼（见候选 2）。

### 候选 2 · `goto` 对悬空目标反复失败，同一句错误

```
t="20:02" id="t3" task="goto" status="failed">blocked: got within 24.2 blocks of lo...
t="20:47" id="t5" task="goto" status="failed">blocked: got within 24.2 blocks of lo...
```

同一个目标 `(-878,14,-908)`、同一个 24.2 格。
**与 2026-10-01 已定位的 Bug A/B 同源**（到达判定不看 Y / 异步失败不走拒答漏斗），
但那次用户判「先不修，认为是模型问题」。**本轮要重新判定**：现在证据更全了
（有 `task_finished` 原文、有 `may_alter_terrain` 缺失这一层），可能确实是工具 bug。

### 候选 3 · prompt token 尖峰到 27,639 后掉到 11,980

```
26515/541 → 27127/238 → 27639/2717 (find_tools) → 11980/2767   ← 中间触发了一次压缩
```

`find_tools` 一次展开就吃掉 2,717 completion token，且**展开内容永久留在历史里**
（上一轮量过 = 2,177 prompt token/请求，占 19%）。这是上下文最大单笔，尚未动。

### ★ 候选 4（视觉通道抓到的，埋点量到的）· 模型每轮往聊天里灌 1,700~2,000 token 废话

**这是截图看出来的**：`mc-screenshot.ps1` 拍到聊天栏被 `RDD:` 长段文字刷满，
一段接一段，每段都在自述「刷怪笼在头顶 24 格高，需要塔方块上去……」。

埋点量化（68 次调用）：

| 指标 | 值 |
|---|---|
| completion 总计 | **137,848 token** |
| 单次平均 / 中位 / 最大 | **2,027 / 1,725 / 12,102** |
| 相对同窗口 input 的比例 | **27%** |

极端例子：`compl=3360` 而 `tool_calls=[todowrite]` —— 写一份待办清单花了 3,360 token。

**关键事实：这是原版模型在违反原版 system prompt 的明文要求。**
`ENTITY_PROMPT` 里写着「Be capable and concise: get the owner's intent done,
then say what happened in a few words.」——**原版就要求它简短，它没照做。**
不是我们加的。

**所以成本要重新拆**（原来只算了 input）：

| 项 | token | 占比 | 谁的 |
|---|---|---|---|
| input（system + tools + history） | ~13,000/次 | ~73% | 原版架构 |
| **output（灌给 owner 的散文）** | **~2,000/次** | **~27%** | **原版模型的违反** |

**这也回答了用户「原版这么烧钱吗」——原版烧钱的一半在输出端，而这一半几乎全是废话。**

顺带一个正面证据：截图里模型自己推理出了
「刷怪笼在头顶 24 格高，需要塔方块上去」「地表 y=-8/-9，目标 y=14」——
**它没再原地打转了**，`PlayerNav` 的文案修复 + 换回好模型是有效的。

### ⚠️ 观察者装备的已知缺口（本轮实测确认）

OpenClaw 服务端已起（`127.0.0.1:8080` pid 12552），但**游戏里的 mod 连不上**：

```
10:37:28  [client_controller/] 正在连接 OpenClaw 控制器: ws://127.0.0.1:8080/minecraft
10:37:28  [WebSocketConnectReadThread-134/ERROR] WebSocket 连接失败: Connection refused
10:37:28  [client_controller/] 已 OpenClaw 控制器断开，将持续重连: Connection refused
```

**游戏 10:36:13 启动，OpenClaw 10:48 才起 —— 顺序反了。**
日志说「将持续重连」但 10:37:28 之后**再无任何重连记录**，
`oc-send.js --probe` 报「ERROR 没有连接 Minecraft 客户端」。

**这不是本轮要修的 bug**（是启动顺序问题，文档已记），但它让观察者少了「镜头锁定」这一路。
当前退路：`mc-screenshot.ps1` 单张截图（不依赖 OpenClaw）——本轮的截图就是这么拿到的。


**纪律**：
- 一个模块一个 wrapper（`run-mutation.ps1` 结尾的 `exit` 会把 wrapper 一起带走）。
- 编译前确认代理 7897 在听（**10-02 上午编译静默死亡的唯一真因就是它**）。
- 部署后用 `javap` 解 jar 验证方法真在里面，不信 `DEPLOY_OK` 一句话（RL-19）。
- 崩溃只写 stderr，`latest.log` 无声截断 ≠ 没崩；正确判据见 `12-进游戏验证工具集.md`。
