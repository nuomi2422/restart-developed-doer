## 三、根因（纯代码推导，100% 确认）

### 根因 1：`rdd_submit` 那条路不拍 acquire 基线 ⇒ `acquire` 恒 false

| 位置 | 事实 |
|---|---|
| `HardCodedEvaluator.java:74-78` | `mode=acquire` 时 `if (baseline == null) return false;` → **无基线 = 恒 false** |
| `TaskChain.java:334-337` | `captureAcquireBaseline` 是 **public 且幂等**（`:335` 已有则不覆盖） |
| `TaskChain.java:276-280` / `:306-309` | `activateCurrent` / `activateCurrentWithSnapshot` **都调**了 `captureAcquireBaseline` |
| **`TaskChain.java:313-324`** | **`startCurrent()` 只做状态迁移 + attempts + activeExecutionId + lastStartedAtMillis，不拍基线** |
| **`RddSubmitTool.java:80`** | **调的是 `runtime.startCurrent()`（无参）** |

⇒ **`rdd_submit` 建出来的链永远没有基线 → `mode=acquire` 永远无法满足。**
⇒ acquire 本来的设计意图是「防假完成」（她接活前就有一堆也算交差），但**这个保护自己坏了**，实际效果是**「谁都别想完成」**。

另一个硬事实（`TaskChain.java:287-290` javadoc）：背包资产**不落盘**，`AssetRegistry.usableCounts()` 恒空；持有真相在 `PlanningAssetSnapshot.availableCounts()`。

### 根因 2：停摆看门狗把「干完了在说话」当停摆

`RddStallWatcher` 的判据是「连续 N 次检查没有**工具调用**」，**不是「目标达成了没有」**。AI 做完活在汇报（说话 = 不调工具）→ 判停摆 → 判失败 → 逼重做。
**本轮没修**（改动面大：要改成看条件满足没有）。这是同一个事故的另一半。

## 七、局限（不掩盖）

1. **只验了 hold 和 acquire 各一次、都是合成类任务**。collect / farm 类（acquire 的设计本意）没验。
2. **根因 2（`RddStallWatcher` 不看目标达成）没修** —— 同类事故还可能复发：AI 做完活长时间说话仍会被判停摆。本轮只修了判定器这一半。
3. **`PlanningAssetSnapshot` 取数失败时的兜底只记了空表**（try/catch），没有测过这条分支。
4. **4 个 `RddV32DirectivesTest` 至今没跑过**（`run-mutation.ps1` 不跑 test task）。本次改的 4 个文件里没有测试文件。
5. **降级语义（无基线 → 按持有量判）会让「她早就有了」的任务立刻完成**，这是刻意取舍（宁可放过一次，也不要子目标不可完成），但**没测过这个降级分支**（因为基线现在总能拍到）。
6. 会话里 `condition_groups`（wood/food/blocks）本轮全程没推进，**没查为什么**。
