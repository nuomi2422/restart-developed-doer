## 一、一句话总览

RDD 是一个"**规划—判定—执行**"三层链，跑在一个 Minecraft 女仆（同伴）身上：

```
        ┌──────────────── 规划层（RDD，负责"想"） ────────────────┐
        │  Stage-A 一级目标 → Stage-B 懒展开二级 → 条件/依赖/风险门  │
        └───────────────────────┬────────────────────────────────┘
                                │  写 subtask 条件 + 注入上下文(<rdd>)
        ┌───────────────────────▼────────────────────────────────┐
        │  判定层（Detector，负责"看/催/判"）                        │
        │  每 tick: 扫真实背包 → 判条件 → 推进/失败/停车/重规划/拍醒  │
        └───────────────────────┬────────────────────────────────┘
                                │  nudge 注入上下文
        ┌───────────────────────▼────────────────────────────────┐
        │  执行层（Numen 本体 AI，负责"干"）                          │
        │  模型自己决定调 mine/goto/craft/transfer… （**唯一驾驶员**）│
        └────────────────────────────────────────────────────────┘
```

> ★ **单驾驶员铁律（2026-09-29 定）**：RDD **只规划/管理**，**不得**自动提交身体工具。
> 曾经的 bug：`RddBodyDispatcher` 会自动把子任务翻成 `mine` 派给身体，而 AI 也在派 →
> **两个方向盘互抢 → 原地左右横跳**。已在 `RddPlugin` 把 `bodySubmissionEnabled` 默认改 `false`
> 并加 flag 文件。详见 §六。

## 四、数据流（一次推进的完整链路）

```
① 用户/外部 说目标
     → RddPlugin.submitGoal
       → RddStagePlanner(Stage-A) 拆一级目标
         → RddPlanGuard 护栏
           → RddPlugin.bindCurrent → RddChainFactory 造 TaskChain → RUNTIMES.put
             └ RddRequirementDetector.forPrimary → publish requirement_manifest   ← 只产事实

② 每 tick（RddDetector.tickRuntime）
     ├ refreshSupervisionFlag / refreshBodyDispatchFlag      ← 热加载开关
     ├ countInventory(真实背包) → RddPlugin.cacheInventory   ← 判定/规划的唯一真相
     ├ maybeWarnBackpackFull                                 ← 背包快满提醒(新)
     ├ tickNegotiation                                       ← 士兵 REJECT/COUNTER → 指挥官改单
     └ 判当前二级条件
         ├ 满足 → 打勾 → 下一个二级；一级全成 → 下一个一级
         └ 不满足 → RddGoalDriver 驱动 / RddBodyTools 派发（**默认已关**）
                      └ 失败 → FailureClassifier → RecoveryPolicy
                                 ├ REQUEST_REPLAN → RddPlugin.requestReplan（烧重规划预算）
                                 └ 停车 → RddParkedWatcher（递进催工 60/120/300s）

③ 上下文注入（每轮给 AI）
     RddPlugin.renderStateContext → <rdd>…<subtask><current_task><done_when><instruction>
       + RddV32Directives.harnessHints()（11 条操作提示）
       + withAssets（世界资产）

④ 执行
     AI 自己调工具（mine/goto/craft/transfer/…）  ← **唯一驾驶员**
```

## 五、你（人）怎么和它交互

| 你想干什么 | 怎么做 | 生效时机 |
|---|---|---|
| 给一个总目标 | 游戏内 `/goal …`，或 MCP `enqueue` text=`/goal …` | 立即（走 Stage-A 规划） |
| 看它现在在干什么 | 监测台 `http://127.0.0.1:8776/`（「任务链」「Numen AI」页） | 实时 |
| 只读问状态 | MCP `rdd_status` / `rdd_assets` / `rdd_get_inventory` / `get_self_status` | 立即 |
| 改单/提建议 | 用 `report_task_concern`（AI 侧）；人侧可写 nudge 文本 | 下一轮 AI 上下文 |
| **暂停监督拍醒** | 写 `config/numen/rdd-supervision.flag` = `pause`（或 `0`） | **≤1s 热生效** |
| **恢复监督** | 写该文件 = `run`（或删文件） | **≤1s 热生效** |
| 让它别抢方向盘（默认） | 不建 `rdd-bodydispatch.flag` 即为关 | 默认 |
| 临时开回自动派活 | 写 `rdd-bodydispatch.flag` = `on`/`run`/`1` | **≤1s 热生效** |
| 换模型/额度 | `config/numen/providers.json`（`ctx` 决定上下文预算） | **需重启游戏** |

## 六、热加载 / 开关全清单（哪些能热改、怎么判断、怎么跳过）

### 6.1 可热改（flag 文件，每 tick 心跳刷新，**不用重启**）
| 开关 | 文件 | 值 | 作用 |
|---|---|---|---|
| 监督拍醒 | `config/numen/rdd-supervision.flag` | `pause`/`0`=停；`run`/空=跑 | 停掉后 Detector 退化为**纯观察**：仍检测/推进资产，但**不 nudge、不自动重试、不升级失败**（LLM 空转止血） |
| 自动派身体工具 | `config/numen/rdd-bodydispatch.flag` | `on`/`run`/`1`=开 | **默认关**。开了就回到"双驾驶"（会横跳），除非你确实要让 RDD 自己开车 |

### 6.2 要重启才生效（JVM 系统属性，写在启动 bat 里）
| 属性 | 默认 | 作用 |
|---|---|---|
| `-Drdd.dependencyGate=true` | **关** | 依赖门：缺料就不派工（防越级） |
| `-Drdd.riskGate=true` | **关** | 风险门：下界/末地装备不足就拦（防铁套送死） |
| `-Drdd.parkedEarlyAccept=true` | **关** | 停车态条件已达成时**自动验收**（有伪造完成风险，故默认关） |

> 在图里/日志里怎么**判断**当前状态：起服时会打 `[numen-core]` 与 `[rdd]` 行；
> 开关变化会 publish `supervision_state` / `body_dispatch_state` 事件到监测台。

### 6.3 怎么"跳过"某个环节
- **跳过监督拍醒** → `rdd-supervision.flag=pause`（最常用，止血）
- **跳过自动派活** → 保持 `rdd-bodydispatch.flag` 不存在（默认）
- **跳过风险门/依赖门** → 现在就是关的；要开才加 JVM 属性
- **跳过重规划** → 每级重规划预算只有 `MAX_REPLAN_PER_PRIMARY=3`，用完自动停车（不是配置，是代码常量 `RddPlugin:81`）

## 七、支线任务（灵活的局部修复）

**为什么要有它**：小问题（死亡掉装备、眼前卡壳）**不该烧掉整链重规划预算**（每级只有 3 次，烧完就停车）。
所以有了"支线任务"这条旁路。

| 组件 | 作用 |
|---|---|
| `LocalRepairTask` (policy, 189 行) | 支线任务的**数据**：目标 + **中断风暴护栏**（防持续 critical 源抢占）+ 优先级通道 + `checkpoint` 断点字段 |
| `RddRepairDispatch` (77 行) | **派发**：`onCompanionDeath` → 生成 LocalRepairTask + 护栏判定 → nudge 注入「**先处理眼前，不整链重规划**」 |
| `Deliberation` (policy, 157 行) | 小规划：候选枚举 + 快路径 + 评分卡 + **三出口**（含 `INSERT_RECON` 去侦察）+ 最低分数线（全负分**不硬选**） |
| `RequirementManifest` (93 行) | 需求清单（**只产事实**，裁决交 `DetectionArbitration` —— 该裁决类在另一分支，未合入，见 22 号文档） |

**接线点**：`RddPlugin.onCompanionDeath` 里调 `RddRepairDispatch.onDeath(companionId, goalId)`（2026-09-29 摘入）。
**触发条件**：同伴**死亡**。**尚未实机验证**（要死一次才看得到）。

## 八、模块边界问题与拆解建议（复杂度）

> ⚠️ **行数已过时（2026-10-01 实测）**：本节写于 09-29，此后两批改动都没拆 `RddPlugin`，
> 反而继续长。**以「类名 + 职责」为准，行数看下面的实测列。**
>
> | 类 | 09-29 文档写的 | 2026-10-01 实测 |
> |---|---|---|
> | `RddPlugin` | 1150 | **1554**（+404） |
> | `RddDetector` | 913 | **1160**（+247） |
> | `TaskChain` | 706 | **858**（+152） |
> | `RiskGate` | 197 | **164**（−33，唯一瘦了的） |
>
> **拆解 5 步至今一步没做**：`RddAssetFacade` / `RddFactFacade` / `RddReplanBudget` /
> `RddRuntimeStore` / `RddBedAnchor` 这 5 个类在 `codex/rdd-monitor-v2` 分支上有实现，
> **当前 `redline-1` 分支上一个都没有**（2026-10-01 逐一查文件确认）。

### 8.1 边界病灶
1. **`RddPlugin` 1150 行**（实测 1554）：同时干 6 件事 —— 事件注册 / 目标接管+规划编排 / 上下文渲染 / 重规划预算 / 资产缓存与落盘 / flag 刷新。
   → 与 §22 文档里"C 组拆解 5 步"要做的完全一致（`RddAssetFacade` / `RddFactFacade` / `RddReplanBudget` / `RddRuntimeStore` / `RddBedAnchor` 各自剥离）。
2. **`RddDetector` 913 行**（实测 1160）：监督 + 失败恢复 + 协商 + 拍醒 + 世界观测混在一起。
   → 可剥：**失败恢复**（→ 已有 `fail` 包，接线太重）、**协商**（→ `TaskNegotiation` 已有）。
3. **`TaskChain` 706 行**（实测 858）：状态机本体。**不建议盲目拆**——它是主链路唯一真源，拆错就是 RL-1..RL-8 全崩。若要拆，按"只读查询面 / 状态迁移面"两分。
4. **判定类与接线类混杂**：`policy` 包里多数是**纯函数**（好），但 `RiskGate` 197 行（实测 164）里混了世界查询。

### 8.2 拆解顺序建议（收益/风险比）
| 优先 | 拆什么 | 收益 | 风险 |
|---|---|---|---|
| 1 | `RddPlugin` 的**预算**（`RddReplanBudget`）| 小、边界清晰、有单测价值 | 低 |
| 2 | `RddPlugin` 的**资产缓存/落盘**（`RddAssetFacade`）| 中高（资产是核心） | 中 |
| 3 | `RddPlugin` 的**事实/锚点**（`RddFactFacade`/`RddBedAnchor`）| 中 | 中 |
| 4 | `RddDetector` 的**失败恢复**外移 | 中 | 中高 |
| 5 | `TaskChain` 拆分 | 低（可读性） | **高（红线）** |

> ⚠️ 每条都必须满足：**行为逐字不变 + 全测绿 + 对照 RL-1..RL-8**（这是 §22 里 C 组那批的既有验收口径）。
> 好消息：**不做也行** —— C 组是纯重构，收益是可维护性，不是功能。

## 九、给下一个维护者的三句话
1. **判定归判定、接线归接线、执行归执行**：改判定去 `policy`/`fact`（纯函数好测）；改接线要小心 `RddPlugin`/`RddDetector` 这两个胖子。
2. **单驾驶员**：RDD 不许自己派工具（`bodySubmissionEnabled` 默认 false）。任何"让 RDD 自动执行"的方案，先问一句"这会不会又变成两个方向盘"。
3. **主链路不许回退**：`TaskChain` 的 规划→判定→执行→打勾→下一级 与 RL-1..RL-8 是红线；拆解/重构前先对照 `01-工程规范.md` §四。
